## 3. 已核实但本轮不修的 CI 机制缺陷

| 项 | 证据 | 处置 |
|---|---|---|
| **GitHub Pages 作业不可 `rerun --failed`，且当日多次自失败** | Run `45404420200`：首轮 Pages 作业因 GitHub 侧 `Fetching artifact metadata failed` 瞬时失败；`gh run rerun --failed` 后同一 run 内 `upload-pages-artifact@v3` 又上传了一份同名 `github-pages`，`actions/deploy-pages@v4` 直接报 `Multiple artifacts named "github-pages" were unexpectedly found`，从此该 run 永久失败。同类失败当日复现 5 次（`45404420200` / `45407367911` / `45409922390` / `45411070383` / `45412150709`），错误串包括 `Found 0 artifact(s)`、`Found 2 artifact(s)` + `Deployment failed, try again later.`；成功 3 次（`45405776324` / `45408542920`） | 正法是 **`gh workflow run deploy.yml --ref main` 起一个全新 run**，可提升成功率但并非必成（当日成功 2/3 dispatch）。根因在上游 action：`upload-pages-artifact@v3` 未暴露 `overwrite`，工件 API 又存在可见性延迟，两条叠加使 `deploy-pages` 时而取不到 / 取到多份同名工件。彻底消除需把 Pages 发布改为分支发布（`gh-pages` 分支 + `git push`）或直连 `gh api`，属独立改造项，本轮不动 |
| 其余五作业同步正常 | 同一批 run：质量门禁、Playwright、托管平台同步（CF Pages / Worker / Netlify / Gitee…）、ghcr 均 success；`发布到生产服务器` 在 `45411070383` 因线上接口抽查 `curl` 超时（exit 28）失败一次，随后的 `45412150709` 同作业 success | 属重排部署相互干扰的瞬时现象（`concurrency: deploy-production` + `cancel-in-progress: false` 让多次部署排队连跑，服务重启窗口内的抽查易超时） |
