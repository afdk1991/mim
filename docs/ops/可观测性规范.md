## 1. 现状声明（先讲清楚有什么，再讲缺什么）

| 版本一致性 | `npm run version:check` | `scripts/version-check.mjs` | 版本漂移 |

### 1.2 当前缺口（明确标注为 Phase 2 待建）

| 编号 | 缺口 | 证据 |
| --- | --- | --- |
| OBS-1 | **无集中式 metrics** | 无 Prometheus / StatsD / OpenTelemetry 依赖；`server/package.json` 依赖只有 `pg` |
| OBS-2 | **无 APM / 链路追踪** | 无 trace-id 生成与透传；`main.js` 的请求处理链路无上下文对象 |
| OBS-3 | **日志非结构化** | 访问日志是单行模板字符串 `console.log(\`${req.method} ${req.url} → ${status} ${ms}ms\`)`, 见 `server/src/main.js:240` |
| OBS-4 | **无请求 ID** | 请求链路内无 ID 生成，日志无法串联 |
| OBS-5 | **无告警系统** | 无 Alertmanager / 无 webhook 通知；外部拨测依赖免费档 UptimeRobot（`deploy/README.md:505`） |
| OBS-6 | **访问日志含完整 URL（含 query）** | `main.js:240` 打印 `req.url`，会把查询串（可能含令牌、筛选条件、用户标识）写进 journald |
| OBS-7 | **无业务指标** | 无成功率、延迟分布、业务量计数 |
| OBS-8 | **无慢查询/慢请求识别** | 日志有耗时（ms）但无人聚合、无阈值告警 |
| OBS-9 | **无前端错误上报** | 浏览器侧异常只在本地 `verify-routes` 脚本内捕获，生产用户端异常无回传 |
| OBS-10 | **无 IoT 链路观测** | EMQX 侧指标与设备上下线趋势不在本仓采集范围 |

**结论：当前可观测性等级为「日志 + 脚本级探测」，不足以支撑主动告警。**

## 2. 日志规范

### 2.1 通用约定

| 项 | 约定 |
| --- | --- |
| 输出目标 | 后端走 stdout/stderr，由 systemd 收进 journald；不落文件（因此 logrotate 只管 nginx） |
| 编码 | UTF-8，日志内容用中文，字段名用英文小写 |
| 单行原则 | 一条事件一行，禁止多行堆栈直接混入访问日志（堆栈走 `console.error` 单独一条） |
| 禁止内容 | 密码、令牌（JWT / Device-Token / `x-iot-hook-token` / `x-sync-token`）、完整 URL 查询串、身份证/手机号明文 |

### 2.2 级别定义（当前代码的实际用法）

| 级别 | 用途 | 当前使用点 |
| --- | --- | --- |
| `console.error` | 5xx 响应、连接池异常、定时器任务失败、启动失败、迁移失败 | `main.js:54`、`:269`、`:271`、`:288`；`db.js:29`；`migrate.js:47-48` |
| `console.warn` | 配置风险提示（可继续运行但不应出现在生产） | `auth.js:28`（JWT_SECRET 缺失）、`auth.js:148`（引导管理员授予） |
| `console.log` | 访问日志、启动信息、迁移进度 | `main.js:240`、`:264`、`:265`；`migrate.js:27-55` |

规范约定（当前未完全遵守）：

| 级别 | 应当用于 |
| --- | --- |
| error | 服务不可用、数据损坏、不可恢复的失败 |
| warn | 降级运行、配置缺失、重试成功前的失败 |
| info | 访问日志、启动信息、迁移进度 |
| debug | 排查期专用，生产默认关闭 |

### 2.3 结构化 JSON 建议（Phase 2 目标格式）

后端访问日志建议改为单行 JSON，便于 journald 之后的任何采集器解析：

```json
{
  "ts": "2026-10-30T12:34:56.789Z",
  "level": "info",
  "type": "access",
  "method": "POST",
  "path": "/api/rest/posts",
  "status": 201,
  "dur_ms": 37,
  "req_id": "01J9Z8K7Q2W3E4R5T6Y7U8I9O0",
  "uid": "3f2b...",
  "ua_hash": "a1b2c3d4",
  "ip_hash": "e5f6g7h8"
}
```

错误日志建议格式：

```json
{
  "ts": "2026-10-30T12:34:56.789Z",
  "level": "error",
  "type": "request_failed",
  "req_id": "01J9Z8K7Q2W3E4R5T6Y7U8I9O0",
  "path": "/api/rpc/wallet_debit",
  "status": 500,
  "code": "server",
  "dur_ms": 1204,
  "err": "internal message",
  "stack": "…"
}
```

字段约定表：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `ts` | 是 | ISO-8601 毫秒 UTC |
| `level` | 是 | `error` / `warn` / `info` / `debug` |
| `type` | 是 | `access` / `request_failed` / `db` / `seckill` / `iot` / `migrate` / `auth` |
| `req_id` | 是（请求链路内） | 26 字符 ULID 或 UUID，贯穿日志与响应头 |
| `path` | 是 | **只写 pathname，不写 query**（这是 OBS-6 的直接修正） |
| `method` | 是 | HTTP 方法 |
| `status` | 是 | 响应状态码 |
| `dur_ms` | 是 | 处理耗时毫秒 |
| `code` | 否 | 业务错误码（与 `ErrCode` 对齐） |
| `uid` | 否 | 用户 ID（UUID 本身不含 PII，可记） |

### 2.4 脱敏规范

| 对象 | 处理 |
| --- | --- |
| 查询串 | **不写入日志**（当前 `main.js:240` 违反，须改为只打 pathname） |
| JWT / Device-Token / `x-iot-hook-token` / `x-sync-token` | 一律不记；如需定位，记 sha256 前 8 位 |
| 密码 | 永不记（含登录失败场景） |
| 手机号 / 邮箱 | 记掩码（`138****8000`）；当前系统未强制收集，出现即按 PII 处理 |
| 上传文件名 | 可记（已过 `safeKey` 校验），但内容不记 |
| 用户 ID | UUID 可直接记 |
| nginx 访问日志 | 沿用 combined 格式，含客户端 IP（受 logrotate 14 天保留约束） |

### 2.5 保留期

| 对象 | 保留期 | 依据 |
| --- | --- | --- |
| 后端 journald | 用 `journalctl --vacuum-size=500M` 控制体积 | `deploy/README.md:494` |
| nginx 日志 | 14 天，daily 轮转 + 压缩 | `deploy/logrotate-mim.conf` |
| 数据库备份 | 14 天（脚本默认 `KEEP_DAYS=14`），异地可选 rclone | `scripts/backup.sh` |
| 上传文件 | 不主动清理（另有 `scripts/cleanup-images.sh`） | `scripts/cleanup-images.sh` |

## 3. 指标规范（Phase 2 目标）

### 3.1 核心指标

| 类别 | 指标 | 定义 | 当前可采集 |
| --- | --- | --- | --- |
| 可用性 | `http_requests_total` | 按 `method, path, status` 计数 | 否（日志有但未聚合） |
| 可用性 | `http_5xx_ratio` | 5xx / 总数 | 否 |
| 延迟 | `http_request_duration_ms` | 直方图，关注 P50/P95/P99 | 否 |
| 依赖 | `db_up` | PG 连通性 | **是**（`/api/health` 的 `db` 字段） |
| 依赖 | `db_pool_in_use` | 连接池占用（默认 `max: 10`） | 否 |
| 依赖 | `emqx_publish_failures_total` | 设备下发失败计数 | 否（`sendCommand` 抛错即计异常） |
| 进程 | `process_restarts_total` | systemd 重启次数 | **是**（`systemctl show -p NRestarts`） |
| 进程 | `uptime_seconds` | 进程运行时长 | **是**（`/api/health` 的 `uptime_ms`） |
| 业务 | `rpc_calls_total` | 按 RPC 名计数（20 个） | 否 |
| 业务 | `rpc_failures_total` | 按 RPC 名 + 错误码计数 | 否 |
| 业务 | `iot_commands_total` | 按 `action` + 终态（`acked`/`failed`）计数 | 否 |
| 前端 | `route_blank_count` | 59 条路由的白屏数 | **是**（`verify-routes` 脚本，非持续采集） |
| 前端 | `route_js_errors_count` | 59 条路由的 JS 异常数 | **是**（同上） |
| 测试 | `unit_tests_passed` | 32 用例通过数 | **是**（`npm test`，非持续采集） |

### 3.2 业务量指标

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 注册用户数 / 日活 | `users` 表计数（该表不开放，需经 RPC 或运维直查） | 容量规划 |
| 订单量 / 成交额 | `mall_orders` 聚合（owner 读，需跨用户汇总时走 RPC 或运维直查） | 业务健康 |
| 秒杀锁活跃数 | `seckill_locks` + `seckill_lock_items` | 库存正确性 |
| 钱包流水笔数 | `wallet_txs` | 资金正确性 |
| 设备在线数 | `devices` 表 `status='online'` 计数 | IoT 容量 |
| 指令终态分布 | `device_commands` 按 status 分组 | 设备链路健康 |

**注意**：上述业务量指标当前**只能靠运维直连 PG 查询**（因为这些表要么 owner 读、要么 admin 读、要么不在 REST 白名单），无现成接口。这是 ADR-004 中「表开放是显式决策」的必然代价。

### 3.3 最小可行方案（Phase 2 落地路径）

目标：在不引入外部依赖、不违反「server 依赖只有 pg」的前提下，先拿到最关键的指标。

| 阶段 | 步骤 | 产出 |
| --- | --- | --- |
| M1 | 把 `main.js:240` 的访问日志改为结构化 JSON 单行，且只打 pathname（不打印 query） | 可被任意采集器解析的日志流 |
| M2 | 在 `route()` 入口生成 `req_id`，写入日志与响应头 `X-Request-Id` | 单请求可串联 |
| M3 | 新增 `GET /api/metrics` 端点，进程内累加计数器（无第三方库），输出 Prometheus 文本格式或 JSON | 无需 exporter 的指标端点 |
| M4 | 用宿主机上的轻量采集器（如 node_exporter 的 textfile collector + 一个小脚本把 `/api/metrics` 拉成 textfile）接入现有告警 | 指标入库 |
| M5 | 前端补 `window.onerror` + `unhandledrejection` 上报到后端新端点（需先解决 PII 与鉴权） | 真实用户端异常可见 |

代价与约束：

| 项 | 说明 |
| --- | --- |
| 依赖 | M1-M3 全部用 Node 内置能力，不新增 `server/` 依赖 |
| 性能 | 进程内计数器为内存态，进程重启清零；需在端点文档中标明该语义 |
| 覆盖 | M3 的计数器不跨实例；将来多实例时必须改为外部聚合 |
| 替代 | 若不愿自建，可采购 SaaS APM，但这会引入外部依赖与成本（见成本模型） |

## 5. 链路追踪建议

### 5.1 现状

**无任何链路追踪实现。** 请求在 `main.js:236-259` 的 `createServer` 回调内处理，链路内不存在上下文对象，因此：

| 缺失 | 后果 |
| --- | --- |
| 无 `req_id` | 同一次请求的日志无法串联 |
| 无 `trace_id` / `span_id` | 无法跨服务串联（当前无其他服务，影响尚小） |
| 无上下文传递 | `console.error` 之外的日志拿不到请求身份 |
| 无采样 | 全量与否无从谈起 |

### 5.2 建议（Phase 2，与 M1-M3 同批落地）

| 阶段 | 内容 |
| --- | --- |
| T1 | 入口生成 `req_id`（ULID 即可，无需 OpenTelemetry），挂在 `res` 或局部上下文对象上 |
| T2 | 响应头下发 `X-Request-Id`，前端在 http 层记录并在报错时展示给用户（便于报障） |
| T3 | 所有 `console.*` 调用点带上 `req_id`（至少覆盖 `main.js:54`、`:240`） |
| T4 | 数据库慢查询记录 `req_id` + SQL 摘要（不记参数值，防 PII） |
| T5 | 跨服务时才引入标准 trace 上下文（当前 EMQX 是唯一外部组件，其 webhook 已带 `x-iot-hook-token`，可复用为关联键） |
| T6 | 暂不引入 OpenTelemetry SDK —— 会引入新依赖，与 ADR-003 冲突；若将来引入，必须先修订 ADR-003 |

## 8. 附：命令速查（当前即可执行）

```bash
# 进程状态与崩溃计数
sudo systemctl status mim-server
```
