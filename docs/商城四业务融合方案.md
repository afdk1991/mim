# 优选商城 · 四大业务融合方案（秒杀 / 本地生活 / 直播尖货 / 出行服务）

> 目标：把四种差异极大的业务接进**同一套商城体系**，而不是再建四套电商。
> 原则：**统一基座（商品 / 购物车 / 订单 / 支付 / 钱包只有一套）+ 差异化外挂（业务独有字段进 `OrderExt`，履约语义进 `bizStatus`）**。

---

## 一、现状梳理：已有核心模块与可复用能力

| 模块 | 位置 | 能力 | 四大业务的接入点 |
|---|---|---|---|
| 商品目录 | `src/domain/commerce/model.ts` `useMallGoods()` | 云端 `products` 表唯一来源，无演示商品；`MallChannel` 已含 `gexm/mix/live/laal` | 业务商品仍走 `products`，靠 `channel` 归类；秒杀/直播价作为**成交价覆盖**而非第二个商品 |
| 购物车 | `MallCartItem` | 按身份隔离、云端快照同步 | 新增 `price?`（业务成交单价）与 `ext?`（业务扩展）两个可选字段 |
| 订单 | `MallOrder` + `mall_orders` 表 | 主状态机 `unpaid → awaiting_confirm → paid → done` | **不改主表语义**，新增三列 `biz_kind / ext / biz_status`；老订单为 NULL，行为不变 |
| 支付 | `src/domain/commerce/payment.ts` | 钱包余额 + 收款码人工确认两条通道，`PaymentChannel` 预留扩展位 | 四业务共用，不新增通道 |
| 钱包 / 积分 | `src/domain/commerce/payment.ts`（经 `src/data/client.ts` 调 `wallet_debit` RPC） | 原子扣费、5% 返积分 | 共用 |
| 云端通道 | `src/data/client.ts` | 后端为仓库内自托管 Node+PostgreSQL（`server/src/rest.js` 通用 CRUD + `server/src/rpc.js` 服务端过程）；统一 `Result<T>` 出入口，未配置后端时降级为本地 | 新增业务读写经 `/rest/:table` 与 `/rpc/:fn` |

**关键判断**：原先 `MallChannel` 里的 `gexm/mix/live/laal` 只是**分类标签**——点进去是同一张商品流，没有场次、门店、直播间、日期库存。本方案补的正是这层「业务履约」。

## 二、业务边界与数据模型

统一约定：金额云端存**分**（`*_cents`），前端模型统一**元**；时间云端存 `bigint` 毫秒（出行日期为 `date`）。

### 2.1 秒杀特惠（频道 `gexm`）

| 对象 | 表 / 类型 | 关键字段 |
|---|---|---|
| 限时场次 | `seckill_sessions` / `SeckillSession` | `start_at/end_at`（场次窗口）、`remaining/total`（库存与进度）、`limit_per_user`（限购） |
| 抢购锁 | `seckill_locks` / — | 主键 `(session_id, user_id)` **唯一约束即限购闸门**；`expire_at` 15 分钟 |
| 订单扩展 | `OrderExt{ kind:'seckill' }` | `sessionId`、`seckillPrice`（锁价）、`lockExpireAt` |

**防超卖三重保障（全在服务端 `seckill_grab` 内）**：① `select … for update` 行锁串行化同场次并发；② `update … where remaining >= p_qty` 条件更新，不足即拒；③ `seckill_locks` 主键唯一约束兜底限购。
**前端不做任何预扣**：`placeBizOrder` 的 `hold` 回调先调服务端，成功才建单 —— 售罄/未开抢/超限购时**根本不会产生订单**。

### 2.2 本地生活（频道 `mix`）

| 对象 | 表 / 类型 | 关键字段 |
|---|---|---|
| 商户门店 | `local_merchants` / `LocalMerchant` | `address/category/lng/lat/hours/phone` |
| 套餐券 | `local_vouchers` / `LocalVoucher` | `goods_id`（走统一商品与结算）、`price_cents/value_cents`、`valid_until`、`rules[]`、`remaining` |
| 券码 | `local_voucher_codes` / `VoucherCode` | **一单一码**；`status: unused/used/expired/refunding/refunded` |
| 订单扩展 | `OrderExt{ kind:'local' }` | `merchantId/merchantName`、`voucherId`、`voucherCode`、`expireAt` |

**核销**：`verify_voucher` 用 `where status='unused'` 的条件更新做**一次性状态转移**，第二次核销必然失败（`already_used`），同一码不可能被销两次；券码由 `issue_voucher_code` **服务端发码**（订单未支付不发码），前端不得构造码。

### 2.3 直播尖货（频道 `live`）

| 对象 | 表 / 类型 | 关键字段 |
|---|---|---|
| 直播间 | `live_rooms` / `LiveRoom` | `status: preview/live/ended`、`anchor_id`、`viewers` |
| 货架 | `live_shelf` / `LiveShelfItem` | 主键 `(room_id, goods_id)`；`live_cents`（专享价）、`seq`（讲解序）、`explaining`（讲解中置顶） |
| 订单扩展 | `OrderExt{ kind:'live' }` | `roomId/roomTitle`、`anchorId/anchorName`、`livePrice` |

**边界最轻**：直播间只提供「货架 + 专享价 + 讲解位」，点商品跳统一详情页 `#/mall/goods/<id>`，下单/支付/订单全复用既有链路 —— 直播间数量增长不会带来第二套订单状态机。

### 2.4 出行服务（频道 `laal`）

| 对象 | 表 / 类型 | 关键字段 |
|---|---|---|
| 票种 | `travel_tickets` / `TravelTicket` | `kind: flight/train/bus/hotel/scenic`、`from_city/to_city`、`seat_classes[]` |
| 日期库存 | `travel_date_stock` / `TravelDateStock` | 主键 `(ticket_id, date)` —— **按日期而非件数售卖** |
| 退改规则 | `travel_rules` / `TravelRule` | `refundable/changeable/fee_rate/cutoff_hours/note` |
| 订单扩展 | `OrderExt{ kind:'travel' }` | `ticketId/kindLabel`、`date`、`passengers[]`、`seatClass`、`rule`（**下单即快照**） |

规则快照的意义：运营事后改规则不影响已成交订单。退票走 `travel_refund`，服务端按快照规则算手续费、回滚日期库存、推进 `ticketed → refunding → refunded`，且对 `refunding/refunded` 重复请求直接拒绝（防重复退）。

## 三、统一入口导航与结算链路

### 3.1 双入口并存（互不干扰）

| 入口 | 路由 | 语义 |
|---|---|---|
| 频道商品流 | `#/mall/gexm` `#/mall/mix` `#/mall/live` `#/mall/laal` | **商品归类**（既有能力，完全保留） |
| 业务会场 | `#/mall/biz/seckill` `#/mall/biz/local` `#/mall/biz/live` `#/mall/biz/travel` | **业务履约**（本次新增） |

分开前缀是为避免 `#/mall/live`（频道）与直播会场撞车 —— 两者入口并存，谁都不破坏。

### 3.2 结算链路（只有一条）

```
业务会场 → placeBizOrder({ price, qty, ext, hold })
             ├─ hold(orderId)：服务端占库存（seckill_grab / travel_book）
             │    失败 → toast 服务端原因，不建单
             └─ 成功 → 建 MallOrder{ status:'unpaid', bizKind, ext, bizStatus:initialBizStatus(ext) }
                        → 落云端 mall_orders → 订单中心统一支付（钱包 / 扫码）
```

| 业务 | `initialBizStatus` | 支付后履约动作 |
|---|---|---|
| 秒杀 | `locked`（已锁库存） | 超时未支付服务端释放；用户取消时前端调 `seckill_release` |
| 本地生活 | `pending_verify` | 「取券码」→ 服务端发码 → 到店 `verify_voucher` |
| 直播 | `pending_ship` | 复用既有发货/收货流程 |
| 出行 | `pending_ticket` | 出票 → `ticketed`；「申请退票」→ `travel_refund` |

### 3.3 双状态机正交

主状态（`unpaid/awaiting_confirm/paid/done`）管**资金**，履约状态（`bizStatus`）管**交付**，订单中心并列展示两个徽标。这样四种履约流程不必硬塞进同一个 `status` 枚举，也不会让「已付款但未核销」这类状态无法表达。

## 四、模块划分与目录结构

```
src/domain/commerce/
├── model.ts                  # 中台（MallOrder / useMallGoods，含 bizKind/ext/bizStatus、placeBizOrder）
├── order.ts                  # placeBizOrder / setBizStatus / setBizExt
├── payment.ts                # 支付通道（钱包余额 + 收款码人工确认）
├── biz/
│   ├── seckill.ts            # 场次读取 + grab/release
│   ├── local.ts              # 门店/券/券码读取 + 发码/核销
│   ├── live.ts               # 直播间/货架读取
│   ├── travel.ts             # 票种/日期库存/规则读取 + 占座/退票
│   └── registry.ts           # 入口导航 + 履约状态机元数据（唯一真源）
└── src/pages/commerce/       # MallHomePage / MallSeckillPage / MallLocalPage / MallLivePage / MallTravelPage / MallOrdersPage（四大业务会场 + 履约状态徽标）

server/db/migrations/0004_business.sql   # 10 张业务表 + 服务端归属校验 + 6 个 RPC（server/src/rpc.js）
```

分层约定：**`src/data/client.ts` 只做传输与错误翻译，不做业务建模**（避免第二套业务真源）；行→模型的映射与降级策略全部在 `src/domain/commerce/biz/*`。

## 六、数据模型调整（迁移 0004_business）

- **主表零破坏**：`mall_orders` 仅 `add column if not exists` 三个**可空**列（`biz_kind / ext / biz_status`），老订单与新接入前的普通订单一律 NULL。
- **新增 10 张业务表**：`seckill_sessions`、`seckill_locks`、`local_merchants`、`local_vouchers`、`local_voucher_codes`、`live_rooms`、`live_shelf`、`travel_tickets`、`travel_date_stock`、`travel_rules`。
- **读策略（仿 RLS，落在 `server/src/rest.js`）**：场次/门店/券/直播间/货架/票种/日期库存/规则 `read:'public'`（未登录也能逛会场）；券码与抢购锁 `read:'owner'`（仅本人可读）；所有写操作只开放给 `server/src/rpc.js` 的服务端过程（其余表 `write:'none'`/`owner`/`admin`）。
- **6 个 RPC（`server/src/rpc.js`）**：`seckill_grab`、`seckill_release`、`verify_voucher`、`issue_voucher_code`、`travel_book`、`travel_refund`。
- **幂等**：`server/db/migrations/0004_business.sql` 用 `create table if not exists` / `create or replace function`，可重复执行（由 `server/scripts/migrate.js` 幂等应用）。
- 全部迁移（`0001~0008`）由 `server/scripts/migrate.js` 统一应用，`0004_business` 幂等可重复执行。

**未应用时的表现**：业务表缺失 → 通用 REST 读取（`src/data/client.ts`）返回错误 → 会场显示「业务表未就绪（需应用迁移 0004_business）」空态；订单写入由既有「缺列自动降级」裁剪 `biz_kind/ext/biz_status` 后照常成功 —— **绝不因为新业务把老下单链路搞挂**。

## 七、渐进式接入步骤

| 阶段 | 动作 | 风险 | 回滚 |
|---|---|---|---|
| ① 建表 | 执行 `npm run server:migrate`（幂等应用 `0004_business` 等全部迁移） | 低（纯新增 + 幂等） | 无需回滚 |
| ② 通读 | 前端先只会场读取；无数据即空态，不影响商城 | 无 | 隐藏入口 |
| ③ 单业务试点 | **先上本地生活**（无并发压力，覆盖券码核销全链路） | 低 | 撤入口 |
| ④ 秒杀 | 录入场次后开放；先用小库存场次验证不超卖 | 中（并发） | 关场次 `status='closed'` |
| ⑤ 出行 | 录入票种 + 日期库存 + 退改规则 | 中（退改涉资金） | 下架票种 |
| ⑥ 直播 | 直播间与货架只读，下单复用既有链路 | 低 | 撤入口 |
| ⑦ 运营数据 | 由后台/DB 录入场次、门店、直播间、票种（**项目规则：不内置任何演示商品/演示数据**） | — | — |

## 八、高并发性能与风控要点

**性能**

| 要点 | 做法 |
|---|---|
| 库存扣减不下放应用层 | 全部走 `server/src/rpc.js` 服务端过程的条件更新 + 行锁；任何 read-modify-write 都会超卖 |
| 热点场次行锁争抢 | 同场次串行化是**正确性代价**，可接受；更进一步可拆「库存分片」（多行的 `remaining` 随机取一行扣）——本次未做，作为后续项 |
| 读多写少 | 场次/门店/票种为公开读，可上 CDN 或本地短缓存；本次 `useBizRows` 未加缓存，避免读到过期库存 |
| 前端轮询 | 秒杀倒计时用 `useNow(1000)` 只驱动展示，**不参与任何库存/状态判定** |
| 列表上限 | 所有读取带 `limit`（场次 60 / 门店 100 / 券 200 / 票种 200），防止大表全量拉取 |

**风控**

| 风险 | 防线 |
|---|---|
| 超卖 | 条件更新 + 行锁 + 主键唯一约束（三重） |
| 一人多单破限购 | `seckill_locks` 主键 `(session_id, user_id)` |
| 券码伪造 | 服务端发码（`issue_voucher_code`），前端只展示 |
| 一码多销 | `where status='unused'` 一次性状态转移 |
| 重复退票 | `biz_status in ('refunding','refunded')` 直接拒绝；库存回滚仅在状态推进时执行 |
| 规则事后篡改 | 退改规则**下单即快照**进 `ext`，服务端按快照裁定 |
| 越权读他人数据 | 券码/抢购锁服务端归属校验（`server/src/rest.js` 的 `owner` 注入，等价于 `auth.uid() = user_id`）；写操作只开放 `server/src/rpc.js` |
| 幽灵锁库存 | 锁 15 分钟过期；用户取消时前端主动 `seckill_release`（失败也不阻塞，有过期兜底） |
| 前端伪造业务字段 | `ext` 只用于展示与回显，所有判定（库存/限购/核销/退票）以服务端为准 |
