## 1. 等级定义

| 概率 | 定义 |
| --- | --- |
| 高 | 未来 6 个月内很可能发生，或已经发生过 |
| 中 | 未来 12 个月内可能发生 |
| 低 | 需要特定条件叠加才会发生 |

| 影响 | 定义 |
| --- | --- |
| 严重 | 全站不可用 / 数据丢失 / 资金或安全事故 |
| 较大 | 核心功能不可用，部分用户受影响，可回滚但需停服 |

## 2. 风险登记册

### R-001 0009 迁移空缺导致 OTA 无法落地

| 项 | 内容 |
| --- | --- |
| 风险描述 | 迁移目录序号从 0008 直接跳到 0010，0009 空缺。`0008_iot_device.sql:5` 明确「OTA 相关表（ota_package / ota_report）随下一轮 0009 落地」，但该迁移至今不存在，导致设备固件 OTA 全链路无法建立 |
| 触发信号 | 需要给设备推送固件升级时；或补 0009 时被其它主题占用该编号 |
| 影响面 | 设备 OTA 能力缺失；发版管道 P4 整体不可用；设备侧功能升级只能靠换货或人工 |
| 概率 / 影响 | 中 / 较大 |
| 预案 | 1. 0009 编号**保留给 OTA**，任何其它迁移不得占用；2. 落地 `0009_ota.sql` 时保持 `create table if not exists` 幂等风格，与 `0008` 的 `fw_version`+`build` 防降级基准对齐；3. 迁移必须先在临时库验证，再上生产；4. 在 0009 落地前，P4 管道在发版契约中标注为「不可发布」 |
| 责任人角色 | 嵌入式负责人（提出）+ 后端负责人（实现）+ CTO（放行） |
| 状态 | 开启 |
| 证据 | `server/db/migrations/`（缺 0009）、`server/db/migrations/0008_iot_device.sql:5`、`server/src/iot.js:24` |

### R-002 设备影子缺失

| 项 | 内容 |
| --- | --- |
| 风险描述 | 服务端无设备影子（desired/reported）存储与读写接口。当前影子离线清理「由 EMQX retained 机制承担」（`iot.js:79`），即状态不在本仓内持久化，服务端重启或设备离线后无法读回设备最新状态 |
| 触发信号 | 需要「App 未打开时也能看到设备最新状态」；需要下发离线后生效的配置 |
| 影响面 | 设备状态只能靠在线时即时上报；离线设备的状态不可知；为将来 OTA 与远程配置埋下能力缺口 |
| 概率 / 影响 | 中 / 中等 |
| 预案 | 1. 明确影子落库位置的选择：PG 表（与 0009 同批）vs EMQX retained（现状）；2. 若选 PG，随 0009 一并建表并补读写接口；3. 若继续依赖 retained，需在 ADR-002 中记录该取舍与 EMQX 侧的持久化责任；4. 影子能力未就绪前，不得对外承诺离线状态展示 |
| 责任人角色 | 嵌入式负责人 + 后端负责人 |
| 状态 | 开启 |
| 证据 | `server/src/iot.js:23-26`（明示不做 OTA）、`:79`（retained 承担） |

### R-003 无集中监控与告警

| 项 | 内容 |
| --- | --- |
| 风险描述 | 无 metrics、无 APM、无链路追踪、无请求 ID、日志非结构化（单行模板），无告警通道与值班机制。故障只能靠用户反馈或人工 `journalctl` 发现 |
| 触发信号 | 出现「用户先于我们发现故障」；发布后需要判断灰度指标却无数据 |
| 影响面 | MTTR 显著拉长；发布门禁 Q9（崩溃率）与 Q12（性能基线）当前不可判定；容量问题只能事后感知 |
| 概率 / 影响 | 高 / 严重 |
| 预案 | 按可观测性规范 §7 的 P0 项优先落地：M1 结构化 JSON 日志（顺带修 OBS-6）、T1 请求 ID、M3 自建 `/api/metrics` 端点（不引入新依赖）；告警先用免费外部拨测（UptimeRobot）兜底，再谈自建 |
| 责任人角色 | 后端负责人（实施）+ CTO（优先级裁决） |
| 状态 | 开启 |
| 证据 | `server/src/main.js:240`（非结构化日志）、`server/package.json`（依赖仅 pg，无任何监控库） |

### R-004 单后端实例单点

| 项 | 内容 |
| --- | --- |
| 风险描述 | 后端为单一 systemd 单元承载全部流量，无多实例、无负载均衡、无热备。nginx 的 `proxy_pass` 指向单一 `127.0.0.1:8787`。主机故障、内核升级、PG 故障、部署重启都会造成全站不可用 |
| 触发信号 | 单机 CPU/连接数打满（连接池默认 `max: 10`）；出现一次非计划停机 |
| 影响面 | 全站 API 不可用；前端静态页仍可访问但功能降级为 localStorage 模式 |
| 概率 / 影响 | 中 / 严重 |
| 预案 | 1. 短期：依赖 `Restart=always` + `RestartSec=3` 自愈，并用 `StartLimitBurst=10` 防日志打满；2. 中期：评估第二实例 + nginx 双上游，但**必须先解决对象存储共享**（本地磁盘不满足）；3. 迁移与破坏性操作必须走双人授权（发版契约 §5.4）；4. 成本模型中预留服务器第二台的预算项 |
| 责任人角色 | 后端负责人 + CTO |
| 状态 | 开启 |
| 证据 | `deploy/mim-server.service`、`deploy/nginx-mim.conf`（`proxy_pass` 单一上游）、`server/src/db.js:22`（`max: 10`） |

### R-005 `package-lock.json` 有意不入库导致构建不可复现

| 项 | 内容 |
| --- | --- |
| 风险描述 | 仓库有意不提交 lock 文件（`.gitignore:4`），理由是 npm/cli#4828 会按当前平台裁剪可选依赖。代价是依赖树每次 `npm install` 都可能不同，构建不可复现，上游包发布新版本可能引入未预期的破坏 |
| 触发信号 | 同一提交在两台机器上构建结果不同；某次 CI 突然失败但代码未变 |
| 影响面 | 构建可复现性缺失；供应链风险不可控；`npm ci` 不可用 |
| 概率 / 影响 | 中 / 较大 |
| 预案 | 1. 已生效的缓解：`.npmrc` 全仓库默认 `legacy-peer-deps=true`，CI 与远程脚本显式传该参数，CI 不开 npm cache；2. 关键版本在 `package.json` 中考虑收紧为精确版本（当前均为 `^` 范围）；3. 发布前用 Release zip（`deploy-release.yml`）固化产物快照作为可复现的交付物；4. 严重事故时可临时入库 lock 文件，但需先评估跨平台裁剪问题 |
| 责任人角色 | 前端负责人 + CTO |
| 状态 | 开启 |
| 证据 | `.gitignore:4`、`package-lock.json` 存在于工作区但被忽略、`.npmrc`、`deploy.yml:31-33` |

### R-008 `users` 表不开放导致运营查询只能靠 RPC

| 项 | 内容 |
| --- | --- |
| 风险描述 | `users` 表永久不在 REST 白名单（`rest.js:5-6`），这是防止 `password_hash` 被投影的正确决策，但代价是运营侧无法用通用 REST 查询用户，只能依赖 RPC（当前仅 `admin_user_lookup` 一个入口） |
| 触发信号 | 运营提出批量用户查询、导出、筛选需求 |

| 状态 | 开启 |
| 证据 | `server/src/rest.js:5-6`、`server/src/rpc.js`（`admin_user_lookup`） |

### R-009 备份有脚本无调度，且从未演练

| 项 | 内容 |
| --- | --- |
| 风险描述 | `scripts/backup.sh` 存在（含 pg_dump + gzip + 可选 rclone + `KEEP_DAYS` 保留 + 上传目录打包），但仓库内**无任何 crontab 或 systemd timer 的落地证据**；`deploy/README.md` 只写「建议 crontab 每天凌晨跑一次」。恢复演练同样是建议而非事实 |

| 责任人角色 | 运维 + 后端负责人 |
| 状态 | 开启 |
| 证据 | `scripts/backup.sh:15-19`（建议 crontab）、`deploy/README.md:359-377`、`:374-377`（建议季度演练） |

### R-014 无登录失败限流与账号保护
