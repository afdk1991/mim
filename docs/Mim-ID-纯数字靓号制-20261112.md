# Mim ID 纯数字靓号制交付说明（2026-11-12）

> 用户指令：**「彻底方案 从个位纯数字开始 + 全量重排 把所有靓号保留」**
>
> 一句话结论：对外编号已由 `MIM-10000001`（前缀 + 8 位补零）改为**纯数字**（`1`、`2`、`3` …），存量用户按注册资历一次性全量重排，**七类靓号全部预留、不再自动发放**。服务端 30 个测试文件 / 422 例全过，本地开发库副本（40 个存量用户）实测重排为 `1`～`40`，无靓号占用、无非纯数字残留。

## 1. 改造前后对照

| 项 | 改造前 | 改造后 |
|---|---|---|
| 号码形态 | `MIM-10000001`（前缀 `MIM` + 8 位补零） | 纯数字 `1`、`2`、`3` … `9,999,999,999` |
| 起始号 | `10_000_001` | `1` |
| 位数 | 固定 8 位 | 随用户量自然增长（早期用户天然拿短号） |
| 上限 | `99_999_999` | `9_999_999_999`（仍在 JS 安全整数内） |
| 靓号 | 无预留概念 | 七类全部预留，发号器与重排均跳过 |
| 存量处理 | 启动时只补 `NULL` 号 | 一次性**全量重排**，旧号写入审计表 |
| 私信寻人校验 | `min(6).max(20)` 任意字符串 | `/^\d{1,10}$/` 纯数字 |

## 2. 靓号规则（`services/mim-api/src/member-no.ts`）

| 类别 | 键 | 判定 | 例子 |
|---|---|---|---|
| 豹子号 | `repeat` | 3 位起全同数字 | `111`、`8888`、`99999` |
| 顺子号 | `ladder` | 3 位起连续递增 / 递减 | `123`、`987`、`1234`、`4321` |
| 回文号 | `palindrome` | 3 位起正读反读一致 | `121`、`1221`、`12321` |
| 对子号 | `abab` | 4 位起、两位一组重复 | `1212`、`1313`、`121212` |
| 整百整千 | `round` | 3 位起末尾两个 `0` | `100`、`2000`、`100000` |
| 谐音吉利 | `pronounce` | 含 `520` / `521` / `1314` / `5201314` / `1314520` / `7758` / `5188` / `168` / `888` / `666` / `999` / `886` / `588` / `5200` | `520`、`1888`、`5201314` |
| 生日号 | `birthday` | 合法的 8 位 `19YYMMDD` / `20YYMMDD` | `19900101`、`20000229` |

**口径说明（重要）**：`1～99` 属**短号段**，按注册顺序正常发放，不进靓号库。
理由：指令是「从个位纯数字开始」；若把个位、十位号也全部预留，就永远发不出个位号，指令自相矛盾。若确实要把 `1～99` 也保留，只需在 `classifyPremiumNo` 里加一条 `if (text.length <= 2) return 'short'`（枚举加一项即可），再以 `member_no_meta` 复位重跑重排。

各类典型预留号：整百 `100 / 200 / 1000 / 100000 / 1000000`；回文 `101 / 121 / 1001 / 1221`；豹子 `111 / 888 / 8888 / 88888 / 8888888`；顺子 `123 / 210 / 12345 / 123456 / 654321`；对子 `1010 / 1212 / 121212`；谐音 `168 / 520 / 1314 / 5201314 / 1314520 / 666888`；生日 `19900101 / 20000229`。

## 3. 发号流程

1. 事务内读 `member_no_sequence.next_no`（缺行回落 `MEMBER_NO_START = 1`）。
2. 逐个试探：**非靓号**且**未被任何用户占用**（`SELECT 1 FROM users WHERE member_no = ?`）才发。
3. 命中即把游标推进到 `next + 1`，写库后返回；任一步失败整事务回滚。
4. 连续跳过超过 `MEMBER_NO_SKIP_GUARD = 1_000_000` 个号抛 `MEMBER_NO_EXHAUSTED`，规则写错时快速失败而不是死循环。

## 4. 存量全量重排（`renumberMemberNos`）

- 触发：`createDatabase` 启动期，`member_no_meta.renumber_v1` 不为 `done` 时执行。
- 顺序：`users ORDER BY created_at ASC, id ASC`，老用户优先拿最短可用号。
- 一致性：整个重排包在 `db.transaction(...).immediate()` 里 —— `immediate` 先拿写锁再读开关，多进程同时启动也只会有一个真正改号。
- 唯一索引冲突规避：先把全表 `member_no` 置 `NULL`（部分唯一索引允许 NULL），再逐个写新号；事务失败则整体回滚，开关不落库，可安全重试。
- 审计：每用户一行 `member_no_history(id, user_id, old_no, new_no, created_at)`，旧号（可能已被用户对外告知）可追溯。
- 幂等：完成后写 `member_no_meta.renumber_v1 = 'done'`，之后每次启动直接返回 `[]`。

## 7. 运维说明

- **想改靓号口径**：只改 `member-no.ts` 一处，规则是纯函数，发号与重排共用。
- **想给某个用户授靓号**：直接 `UPDATE users SET member_no = '<靓号>'`（唯一索引会拦住重复占用），发号器会因「已占用」自动跳过该号，不需要改游标。授予前建议在 `member_no_history` 留一条 `old_no → new_no` 记录。
- **想回滚某个用户**：`member_no_history` 里有旧号，按 `user_id` 查即可。
- **想重跑整轮重排**：把 `member_no_meta.renumber_v1` 改回非 `done` 值，重启即按注册顺序重新分配（会追加审计行）。

## 8. 边界与未做

- 未做「靓号选号 / 售卖」入口：当前只做「预留不自动发放」，运营侧尚未有自助授予界面；授号仍需后台 SQL 或后续新增接口。
- 未做靓号池报表（如「100 万以内预留了多少个」）：规则是纯函数，需要时可离线枚举统计。
- 历史文档中出现的 `MIM-100000xx` 为各轮交付当时的取证快照，按铁律三保留，不再代表现状。
