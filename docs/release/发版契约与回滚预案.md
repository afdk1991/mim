## 2. 发布顺序与依赖关系

### 2.1 Web（P1）与后端服务（P3）的同仓顺序

**决策：后端先，前端后。**

| 项 | 内容 |
| --- | --- |
| 顺序 | 1. 后端迁移 + 重启 → 2. 健康检查通过 → 3. 前端构建 + 分发 |
| 依据 | 代码事实：`deploy.yml` 的远程脚本顺序是「`git pull` → 依赖安装 → `npm run build` → `cd server && npm run migrate` → `sudo systemctl restart mim-server`」。即在同一台机器上，**前端构建发生在后端重启之前**，但前端产物生效于 nginx 静态目录，后端重启后才对外提供新接口 |
| 更严格的推荐顺序 | 生产环境应遵循「先迁移并重启后端 → 验证 `/api/health` 与关键接口 → 再让新前端产物生效」，确保新前端不会打到旧后端 |
| 强制的顺序前提 | 迁移必须**只增不改**：全部 `create table if not exists` / `create index if not exists` 风格，新旧代码可以同时对准同一份库结构 |

### 2.2 兼容 ≥2 个版本的约束（硬约束）

前端与后端是**独立部署、独立生效**的两份产物，因此必须满足双向兼容至少一个版本：

| 编号 | 约束 |
| --- | --- |
| C1 | 后端接口只增不改：不得删除已上线的 REST 表、RPC 名、专用端点；不得改变既有响应体键名（成功体只允许 `data` 一个键） |
| C2 | 迁移只增不改：不得 `drop column`、不得改列类型（历史事件：缺列时前端靠 `code='schema'` 自动降级，这是「加列前先发前端」能力的反面证据） |
| C3 | 前端必须能容忍旧后端：新字段缺失时不崩溃，走 `src/core/result.ts` 的 `schema` 错误码与 `writeWithFallback` 降级路径 |
| C4 | 后端必须能容忍新前端：新前端调用的新 RPC/新表在旧后端上不存在时应返回可识别错误码，而非 500 |
| C5 | 错误码契约跨版本稳定：`ErrCode` 与 `server/src/errors.js` 一一对应，新增错误码只能追加 |
| C6 | 前端产物必须能被旧页面缓存击穿：`index.html` 配 `no-cache`（见 `deploy/nginx-mim.conf` 的 `location = /index.html`），`/assets/` 走长缓存 |
| C7 | 后端地址在构建期内联：改 `VITE_MIM_API_BASE` 必须重新 build + `cap sync`（`capacitor.config.ts` 注释明示） |

### 2.3 四管道发布顺序（含依赖）

```text
1. P3 后端服务（迁移 + 重启 + 健康检查）
      │
      ├──▶ 2. P1 Web（Pages 静态站，与 P3 同源仓库、同一推送触发）
      │
      └──▶ 3. P2 原生 App（依赖后端接口已就绪；桌面端依赖 tag 触发）
                 │
                 └──▶ 4. P4 固件 OTA（依赖 0009 迁移 + 设备影子，当前阻塞）
```

| 依赖 | 说明 |
| --- | --- |
| P1 依赖 P3 | Web 前端的 API 指向自托管后端，后端未就绪时前端降级为 localStorage 模式（三态写回的 `skip`） |
| P2 依赖 P3 | 原生壳内的 Web 产物同样打后端；且壳内地址在构建期内联，无法运行时切换 |
| P4 依赖 P3 | 设备 OTA 的服务端表与接口必须在 P3 内先落地 |
| P2 内部 | 桌面端依赖 tag `V*.*.*.*`；移动端（Capacitor）与鸿蒙端当前**无 CI 管道**，须人工 `npm run native:sync` + 各 IDE 出包 |

## 3. 各管道的发布与回滚步骤

### 3.1 P1 Web（GitHub Pages）

**发布**：push `main` → `build.yml` 的 `verify` 作业（禁容器闸门 → 类型检查 → 构建）→ `deploy-pages` 作业（仅 main 分支）。

**回滚步骤**：

| 步骤 | 命令 / 操作 |
| --- | --- |
| 1 | 在 GitHub 仓库 → Actions → 选中上一个成功的 `build` 运行 → Re-run jobs（重跑 `deploy-pages`） |
| 2 | 或本地 `git revert <bad-sha>` → push `main` → 触发新一轮构建 |
| 3 | 验证：`curl -fsSI https://<pages 域名>/` 与关键路由 `#/feed` 的 200 校验 |
| 4 | 影响面：Pages 站是只读展示用途，回滚不影响自托管主站（见 `deploy/README.md:431`） |

```bash
# 命令行方式
git revert <bad-sha>
git push origin main
# 或强制回到旧提交（需 CR 与授权，见 §5）
git reset --hard <good-sha> && git push --force-with-lease origin main
```

### 3.2 P2 原生 App

**桌面端（Tauri）发布**：打 tag `V*.*.*.*` → `build-release.yml` 矩阵构建三平台 → 自动创建 GitHub Release 并上传产物 → 配置签名密钥时同步生成 `latest.json`（Tauri updater 格式）。

| 回滚步骤（桌面端） | 命令 / 操作 |
| --- | --- |
| 1. 下架问题 Release | GitHub → Releases → 编辑问题 Release → 取消「Set as latest」或删除 |
| 2. 回滚 OTA 清单 | 把 `latest.json` 指回上一个版本：重新运行上一个 tag 的 `build-release.yml`，或在 Releases 中把上一版本的 `latest.json` 重新置为最新 |
| 3. 客户端更新地址 | `https://github.com/afdk1991/mim/releases/latest/download/latest.json`（见 `build-release.yml:8`） |
| 4. 验证 | 下载上一版本安装包并启动，确认版本号回退 |

```bash
# 回滚 tag（谨慎：tag 删除会影响已分发客户端的更新检测）
git tag -d V0.0.1.0
git push origin :refs/tags/V0.0.1.0
# 重新发布上一版本
git tag V0.0.0.9 && git push origin V0.0.0.9
```

**移动端（Capacitor）与鸿蒙端**：当前无 CI 管道，发布与回滚均为手工。

| 步骤 | 操作 |
| --- | --- |
| 发布 | `npm run native:sync`（= `npm run build && cap sync`）→ Android Studio / Xcode 出包 → 提审 |
| 回滚 | 渠道侧下架**（受应用商店规则约束，可能不可逆）** |
| 兜底 | 壳内 Web 产物由壳自带，用户不更新壳就无法回滚前端；这是移动端回滚弱于 Web 的结构性原因 |
| 鸿蒙 | `harmony/AppScope/app.json5` 的 `versionCode` 递增（当前 3），出包经 DevEco → 应用市场 |

### 3.3 P3 后端服务（systemd）

**发布**（`deploy.yml` 远程脚本原文，顺序如实列出）：

```bash
cd /opt/mim
git pull --ff-only
npm install --no-audit --no-fund --legacy-peer-deps
npm --prefix server install --omit=dev --no-audit --no-fund --legacy-peer-deps
npm run build                    # SKIP_BUILD=1 时可跳过
cd server && npm run migrate
sudo systemctl restart mim-server
```

**健康检查**（CI 内 20 次重试，间隔 2 秒）：

```bash
P=$(grep -E '^PORT=' /opt/mim/server/.env | cut -d= -f2-); P=${P:-8787}
curl -fsS http://127.0.0.1:$P/api/health
```

健康响应含 `ok` / `db` / `uptime_ms` / `rpcs` 四项（`server/src/main.js:77-85`），其中 `db:false` 表示 PG 未连通，即使 HTTP 200 也应视为发布失败。

**回滚步骤**：

| 场景 | 步骤 | 命令 |
| --- | --- | --- |
| A. 仅代码回滚（无破坏性迁移） | 回到上一个 tag 或 Release zip，重跑依赖 → 迁移 → 重启 | `cd /opt/mim && git checkout <上一个 tag>`；然后重跑 11.1 流程 |
| B. 用 Release zip 回滚 | 下载上一版本 zip 覆盖 | `unzip mim-deploy-v0.0.0.4.zip -d /tmp/mim-release` → `sudo rsync -a --exclude node_modules --exclude .git /tmp/mim-release/ /opt/mim/` → 迁移 → 重启 |
| C. 只要服务恢复（不换代码） | 直接重启服务 | `sudo systemctl restart mim-server` |
| D. 释放崩溃循环 | systemd 的 `StartLimitBurst` 触发后需清计数 | `sudo systemctl reset-failed mim-server && sudo systemctl restart mim-server` |
| E. 迁移造成破坏 | 先备份再回滚结构，最后回滚代码 | `sudo -u postgres pg_dump mim | gzip > /var/backups/mim-$(date +%F).sql.gz`；恢复见 §3.3.1 |

> 依据：`deploy/README.md:346-354` 明示「数据库迁移只增不改，回滚代码通常不需要回滚数据库结构；必要时先按第十二节做备份再操作」。

#### 3.3.1 数据库恢复（仅在迁移破坏数据时执行）

```bash
# 备份（必须先做）
sudo -u postgres pg_dump mim | gzip > /var/backups/mim-$(date +%F).sql.gz

# 恢复
sudo -u postgres psql -c 'DROP DATABASE IF EXISTS mim;'
sudo -u postgres createdb --owner=mim mim
zcat /var/backups/mim-2026-10-28.sql.gz | sudo -u postgres psql mim

# 上传文件一并恢复
tar czf /var/backups/mim-uploads-$(date +%F).tar.gz /opt/mim/server/data/uploads
```

**注意**：此操作会停服并丢弃备份点之后的数据，必须经 §5 的放行授权人批准。

| 无容器化产物 | 不得存在 Dockerfile / docker-compose / .dockerignore / 双扩展名残留 / 内容关键字 | CI 闸门（`build.yml:41-77`） |
| 密钥不入库 | `.env`、`server/.env`、`*.token` 等不得进版本库 | `.gitignore` 静态排除 |
| 依赖清单 | `server/` 的运行时依赖只允许 `pg` | 人工 CR（ADR-003） |
| 错误码契约 | 后端 `errors.js` 与前端 `ErrCode` 一一对应 | 人工 CR |
| 表开放 | 新增 REST 表需评审；`users` 永不开放 | 人工 CR |

## 6. 回滚决策表

| 征兆 | 判定 | 动作 |
| --- | --- | --- |
| 健康检查返回 `db:false` | PG 未连通 | 先排查 PG；回滚代码不能解决 → 不回滚，走 PG 故障处理 |
| 健康检查 200 但关键接口 5xx | 代码缺陷 | 执行 P3 场景 A/B |
| 发布后 30 分钟内 systemd 重启 ≥ 1 次 | 进程崩溃 | 执行 P3 场景 A；先 `reset-failed` 解除崩溃循环 |
| 前端白屏 | 路由/构建缺陷 | P1 回滚 + `verify:routes` 复验 |
| 59 条路由中任一条 JS 异常 | 前端缺陷 | 同上 |
| 核心链路用例失败 | 任一环节 | 回滚对应管道 |
| 迁移执行失败（exitCode=1） | 结构问题 | **不得重启服务**；先修迁移文件。迁移器失败即抛异常，不继续也不回滚（`server/scripts/migrate.js`） |
| 客户端大量报更新失败 | OTA 清单问题 | P2 桌面端回滚 `latest.json` |
