# 商城四业务并发与退款分析

> 分析对象：秒杀（seckill）/ 本地生活（local）/ 直播（live）/ 出行（travel）四业务的端到端链路、并发正确性与退款链路。
> 证据基准：`server/src/rpc.js`、`server/db/migrations/0003_commerce.sql`、`0004_business.sql`、`server/src/rest.js`、`src/domain/commerce/**`、`src/pages/commerce/**`、`src/app/state/mall.tsx`、`src/app/state/wallet.tsx`。
> 所有结论均附 `文件:行号` 与代码引用，未运行时验证的事项在文末「受阻 / 未验证」单列。

---

## 分析结论摘要

1. **防超卖主干是成立的**：秒杀 `seckill_grab` 与出行 `travel_book` 都在同一事务内做「行锁 `for update` + 条件 `UPDATE ... WHERE remaining >= qty`」，库存扣减不下放应用层（`server/src/rpc.js:82,94-98,146,151-155`）。
2. **存在一条不可达的退款链路（最高优先级问题）**：服务端 `travel_refund` 强制要求 `biz_status==='ticketed'`（`rpc.js:202`），前端退票按钮也只在 `bizStatus==='ticketed'` 时显示（`MallOrdersPage.tsx:229`），但全工程**没有任何代码路径把订单从 `pending_ticket` 推进到 `ticketed`**——出票环节缺失，退票入口实际永远不可达。
3. **退票回包字段前后端对不上**：服务端返回 `fee_fen / refund_fen`（`rpc.js:286-287`），前端却读 `fee / refund`（`MallOrdersPage.tsx:115-116`），导致 toast 里手续费/应退恒为 ¥0.00。
4. **退款资金去向与文案不符**：`travel_refund` 无论原支付通道一律把退款加进钱包余额（`rpc.js:250-253`），前端却提示「将按原支付通道退回」（`MallOrdersPage.tsx:119`）。扫码支付的订单退款并不会原路退回。
5. **秒杀锁没有过期清理任务**：`seckill_locks.expire_at` 只写不读（`rpc.js:101-107` 写入；全 server 无任何 sweep/cron），超时未支付的锁永久占用库存，且仍计入用户限购额度。
6. **本地生活套餐库存不做服务端扣减**：`local_vouchers.remaining` 全工程无任何 `UPDATE`，下单 `buy` 也没有 `hold`（`MallLocalPage.tsx:54-82`），券库存纯展示、无超卖控制也无库存账。
7. **出行释放 `travel_release` 信任前端传的 `p_qty` 且不在事务内**（`rpc.js:172,180-183`），可被重复调用或伪造数量多回补库存。
8. **与既有设计文档存在术语/落点分歧**：文档写的是 `src/mall/biz/*` + Supabase definer RPC（`商城四业务融合方案.md:118-128`），实际落点是 `src/domain/commerce/biz/*` + 自建 Node RPC（`server/src/rpc.js`），后端形态已替换，文档未同步。

## 二、并发正确性逐项核对

### 2.1 事务边界与行锁

- **秒杀**：整体包在 `tx(async (c) => {...})` 内（`rpc.js:81`），`select ... for update` 锁场次行（`:82`）。同场次并发被串行化，正确。
- **出行占座**：包在事务内（`rpc.js:144`），按 `(ticket_id,date)` 行锁（`:146`）。正确。
- **出行释放 `travel_release`：不在事务内**（`rpc.js:175-185` 直接用 `one()`/`query()`，没有 `tx()`）。先 `one` 查订单、再 `query` 回补库存，两步非原子，存在读后写窗口。
- **退票 `travel_refund`**：包在事务内（`rpc.js:196`），状态转移 + 库存回补 + 钱包入账 + 审计同事务，边界完整。
- **发码/核销**：均在事务内（`rpc.js:303, 346`）。
- **钱包扣/加**：`wallet_debit`/`wallet_credit` 在事务内（`rpc.js:399, 420`）。

### 2.2 防超卖（库存/名额扣减）

| 业务 | 机制 | 证据 | 评价 |
|---|---|---|---|
| 秒杀 | 行锁 + 条件更新 + 主键限购 | `rpc.js:82,94-98`；`0004:44` PK | 三重闸门成立 |
| 出行 | 行锁 + 条件更新 | `rpc.js:146,151-155`；`0004:147` PK(ticket_id,date) | 成立 |
| 本地生活 | **无** | 下单无 hold（`MallLocalPage.tsx:54`）；`local_vouchers.remaining` 无任何 UPDATE | 库存纯展示，见风险 R6 |
| 直播 | 无（本就不占库存） | `MallLivePage.tsx:49` | 设计如此，可接受 |

### 2.3 幂等键

- **发码幂等**：`local_voucher_codes UNIQUE(order_id)`（`0004:90`）+ 先查后插 `reused:true`（`rpc.js:312-313`）。正确。
- **核销幂等**：`update ... where status='unused'` 条件转移（`rpc.js:356-360`），二次核销 `affected=0` → 抛错。正确。
- **退票幂等**：① 状态闸 `refunding/refunded` 拒绝（`rpc.js:201`）；② 钱包流水用 `snapshot->>'refund_order_id'` 去重（`rpc.js:241-247`）。正确。
- **钱包扣/加**：`wallet_debit/wallet_credit` **没有业务幂等键**（`rpc.js:396-433`），仅靠前端订单状态门（`mall.tsx:261` `o.status!=='unpaid'` 才放行）。网络重试可能造成重复扣款——见风险 R8。
- **秒杀/出行释放**：`seckill_release` 无锁返回 `released:0`（`rpc.js:127`），自带幂等语义；但 `travel_release` 无幂等键（见 R7）。

### 2.4 券码发放并发

`issue_voucher_code` 在事务内先 `select ... where order_id`，命中即返回原码（`rpc.js:312-313`），未命中再 `insert`。库层 `UNIQUE(order_id)`（`0004:90`）兜底：两个并发取码请求，一个插入成功，另一个撞唯一键会抛错（代码未对 `23505` 做兜底捕获，会以 500 返回前端）。功能上不会产生第二个码，但重复点击「取券码」在极端并发下可能偶发 500 而非静默返回原码。

### 2.5 钱包扣款/冲正

- `wallet_debit`：`update wallet_balances set balance_fen=balance_fen-$1 where user_id=$2 and balance_fen>=$1`（`rpc.js:400-404`），余额不足 `affected=0` 抛 `conflict`。原子扣款正确。
- 前端 `walletConsume`：**先乐观扣本地余额** `push('consume')`（`wallet.tsx:75`），再异步 `wallet_debit` RPC，成功后 `hydrate()` 以服务端余额回拉覆盖（`wallet.tsx:76,58-65`）。服务端拒付时本地已扣、靠 hydrate 纠正，存在短暂不一致窗口。
- 退票冲正：`travel_refund` 直接 `balance_fen + refund`（`rpc.js:250-253`），与状态转移同事务。

## 三、退款链路

### 3.1 出行退票（唯一有服务端退款逻辑的业务）

发起入口 → 后端校验 → 状态机 → 回补：

1. **入口**：`MallOrdersPage.tsx:232-234`「申请退票」按钮，**仅当 `o.bizStatus==='ticketed'` 才渲染**（`:229`）。
2. **后端四道闸**（`rpc.js:199-202`）：
   ```
   ① o.user_id!==ctx.uid            → forbidden   (:199)
   ② o.biz_kind!=='travel'          → badRequest   (:200)
   ③ biz_status in (refunding,refunded) → conflict (:201)
   ④ biz_status!=='ticketed'        → conflict     (:202)
   ```
3. **手续费**：取 `ext.rule` 快照优先、否则 `travel_rules` 当前行（`rpc.js:210-219`）；`fee=ceil(amount*feeRate)`，`refund=max(0,amount-fee)`（`:223-224`）。
4. **状态机**：`biz_status → 'refunding'`（`:226`）→ 库存回补（`:229-235`）→ 钱包入账（`:240-267`）→ `biz_status='refunded'`，主 `status` 由 `awaiting_confirm` 回退为 `paid`（`:269-275`）→ 写 `audit_logs`（`:277-281`）。
5. **回补**：日期库存 `remaining + qty`（`:231`）；实退金额入钱包 `income` 流水（`:250-264`）。

### 3.2 本地生活退款

数据库 `local_voucher_codes.status` 预留了 `refunding/refunded`（`0004:87`；`biz/local.ts:93-94` 也有文案），但**服务端没有任何本地生活退款 RPC**（`RPCS` 注册表 `rpc.js:709-737` 无对应函数）。已核销券码不可退，未核销券码的退款在代码层未实现。

### 3.3 秒杀/直播退款

- 秒杀：仅支持「取消未支付订单 → `seckill_release` 释放锁」（`mall.tsx:287-309`）；已支付秒杀单无退款路径。
- 直播：复用普通实物「确认收货 → done」，无专门退款。

## 五、跨业务共性问题

1. **「先 hold 后建单」的顺序把订单行排除在服务端事务之外**：`placeBizOrder` 先调 `seckill_grab/travel_book`（此时订单不存在），成功后才 `mall_upsert_order`（`mall.tsx:236-255`）。好处是失败不建单；代价是「占库存」与「建订单」两个动作不在同一事务——hold 成功但 upsert 网络失败时，库存已扣而订单丢失（秒杀靠锁过期兜底，但 R4 显示过期清理不存在；出行则无兜底）。
2. **履约状态机前后端各写一半**：`biz_status` 既被服务端 RPC 写（`pending_ticket`/`refunding`/`refunded`/`verified`），也被前端 `setBizStatus` 覆盖写（`mall.tsx:322-328` → `mall_upsert_order`）。前端 `MallOrdersPage.tsx:117` 退票成功后本地写 `refunded`，与服务端最终态可能错位。
3. **金额单位铁律执行到位**：全链路「分」整数（`0003:4,47` amount_fen bigint；`model.ts:4-6` Fen 后缀），历史 ¥189/¥1.89 错位的修复在代码中一致（`rpc.js:223` 注释、`MallOrdersPage.tsx:114` 注释）。这是本次重建做对的部分。
4. **RLS/写权限下沉到服务端**：`rest.js:58-67` 业务表 `read:public`、`write:admin/none/owner`，券码与锁仅本人可读（`rest.js:59,62`），写操作只开放给 RPC——与设计文档目标一致，且后端已从 Supabase definer 函数换成自建 Node RPC（`rpc.js`），权限模型等价保留。
5. **设计文档与实现的落点分歧**：`商城四业务融合方案.md` 描述 `src/mall/biz/*`、Supabase/CloudBase 双后端、5~6 个 definer RPC；实际为 `src/domain/commerce/biz/*`、自建 `server/` Node RPC、`RPCS` 注册表（`rpc.js:709-737`）。文档第九节「遗留硬阻塞：Supabase 0008+ 未应用」已不适用于当前后端形态，需同步更新文档，否则后续维护者会按错误路径排查。

### 7.2 本机启动 PostgreSQL 的具体步骤（Windows）

**方式一：winget 安装（推荐）**
