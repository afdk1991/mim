## 1. 背景

Mim 后端当前的真实形态（以 `server/package.json`、`server/src/main.js` 为准）：

| 项 | 现状 |
| --- | --- |
| 运行时 | Node 20+（`engines.node: >=20`）；`.github/workflows/build.yml:35` 固定 CI 用 Node 22 |
| HTTP 层 | `node:http`，**零 Web 框架**（无 Express / Fastify / Koa / Nest） |
| 外部依赖 | 仅 `pg`（`server/package.json` 的 `dependencies` 全表只有它） |
| 源码规模 | `server/src/` 共 9 个文件、约 2257 行 |
| 对外契约 | 通用 REST（`/api/rest/:table`）、RPC（`/api/rpc/:fn`）、对象存储、同步、IoT 网关 |
| 部署 | systemd 单元 `deploy/mim-server.service`，`ExecStart=/usr/bin/node src/main.js`，无容器 |
| 迁移 | 自研执行器 `server/scripts/migrate.js`，按文件名升序执行 `db/migrations/*.sql` |

存量接口规模：

| 类别 | 数量 | 位置 |
| --- | --- | --- |
| REST 表白名单 | 36 张 | `server/src/rest.js:27-74` |
| RPC | 20 个 | `server/src/rpc.js:922-948` |
| 专用端点 | 健康检查 `/health`、`/healthz`、`/hello`、认证 4 条、存储 2 条、同步 1 条、IoT 7 条 | `server/src/main.js:98-184` |

后端技术栈的选型必须同时满足：与前端共用一门语言（TypeScript 已在前端强制）、依赖尽量少（便于自托管与审计）、以及小团队可维护。

## 2. 备选方案

| 编号 | 方案 | 要点 | 评估 |
| --- | --- | --- | --- |
| C1 | Node + `node:http` 零框架 + 手写路由分派 | 现状 | 采纳 |
| C2 | Node + Express/Fastify 等 Web 框架 | 引入路由、中间件、body parser 生态 | 否决 |
| C3 | Go / Rust 重写后端 | 换语言换取性能与内存稳定性 | 否决 |
| C4 | Node + NestJS（含 DI / 装饰器 / 模块化） | 企业级结构 | 否决 |
| C5 | Serverless 化（云函数 / Edge Function） | 按调用计费，免运维 | 否决（已废弃） |
| C6 | PostgREST 之类的通用数据网关 | 零代码暴露 PG | 否决 |

取舍依据：

- **C1 采纳**：后端代码量只有约 2257 行、9 个文件。在这个体量下，框架带来的收益（路由声明、中间件链）被手写 `if (restPath === ...)` 分派覆盖了，而框架的代价（依赖树、升级破坏、安全公告跟进）是实打实的。零依赖让整个后端可以在宿主机上 `npm install` 后直接跑，且与「无容器部署」路线自洽。
- **C2 否决**：引入 Express/Fastify 会一次性带入数十个传递依赖，与「唯一依赖 pg」的可审计性冲突。而且本项目的路由形态是「少量端点 + 表驱动 REST」，框架的核心价值（大量路由的组织）用不上。
- **C3 否决**：Go/Rust 重写需要第二个语言栈与第二次人力投入，且当前后端不是 CPU 瓶颈（瓶颈在 PG 与网络 IO）。收益不足以抵消跨语言维护成本。
- **C4 否决**：NestJS 的依赖注入与装饰器体系对 2257 行代码是过度工程，且要求实验性装饰器元数据支持。
- **C5 否决**：历史上确实存在过依赖 Supabase / CloudBase 的云函数与 Edge Function 流水线，`build.yml:3-5` 的注释明确记录了它们「后端收敛到自托管 server 后已无意义，不再保留」。Serverless 的可观测性与冷启动也不符合当前形态。
- **C6 否决**：PostgREST 能替代通用 REST，但替代不了 20 个 RPC 中的事务逻辑（秒杀抢锁、出行库存、钱包扣款）、也替代不了 IoT 钩子契约与三态写回的内容生态。

## 3. 决策

**采纳 C1：Node 20+ + `node:http` + 零 Web 框架 + 唯一依赖 `pg`。并确立以下硬约束：**

### 3.1 依赖约束

1. `server/package.json` 的 `dependencies` 只允许出现 `pg`。新增运行时依赖必须走本文档的修订流程并说明为何不能用 Node 内置能力替代。
2. 能用 Node 标准库解决的，一律不引依赖。当前已用到的标准库：`node:http`、`node:crypto`（scrypt/HMAC/randomBytes/timingSafeEqual）、`node:fs/promises`、`node:path`、`node:url`、`node:util`、`node:events`。
3. 工具链类依赖（如前端的 vite/playwright-core）不得进入 `server/` 的依赖清单。

### 3.2 编码约束

| 约束 | 说明 |
| --- | --- |
| 响应契约唯一 | 成功 `{ data: … }`；失败 HTTP 状态码 + `{ error: { code, message } }`，`code` 取自前端 `src/core/result.ts` 的 `ErrCode` 枚举 |
| 错误统一收敛 | 一切异常经 `toApiError(e)` 转 `ApiError`（`server/src/errors.js:44-56`），**绝不把 PG 原始错误原样抛给前端**；PG 错误码映射表见 `errors.js:29-40` |
| 缺列降级契约 | 缺列提示文案刻意与 PostgREST 一致（`errors.js:25-27`），前端 `writeWithFallback` 靠文案识别并降级 |
| 鉴权位置 | 读操作允许匿名（`tryAuth`），写操作一律 `authenticate`；表级归属强制注入 owner 列，客户端提交的 owner 值被忽略 |
| 语法自检 | `npm run server:check` 对全部 9 个 src 文件 + 2 个脚本做 `node --check`，作为无类型系统下的最低保障 |

### 3.3 已知代价与补齐手段

后端是纯 JavaScript（`.js` + ESM），**没有 TypeScript 保护**，与前端 `strict` 形成反差。当前补偿手段只有：

| 手段 | 覆盖 |
| --- | --- |
| `node --check`（`npm run server:check`） | 语法，不覆盖运行时类型 |
| `scripts/verify-backend.mjs` 端到端断言 | 接口行为，依赖服务与库已起 |
| `scripts/server-health.mjs` | 健康探测与 RPC 数量核对 |
| 缺列降级契约 | 结构漂移时前端自动降级而非崩溃 |

不引入 TS 编译步骤是刻意选择：避免为后端引入构建产物与 source map 管理，保证「拉代码即可 `node src/main.js`」。代价是重构安全性低于前端。

## 4. 正面后果

| 项 | 说明 |
| --- | --- |
| 依赖面极小 | 供应链攻击面与 CVE 跟进成本接近零；`npm audit` 噪音低 |
| 前后端同语言 | 前端 TS、后端 JS 同属 JS 生态，人员可跨端支援，契约靠 `ErrCode` 对齐 |
| 自托管友好 | 宿主机 `apt install nodejs` 后即可运行，无需构建步骤 |
| 与无容器路线自洽 | 不需要镜像构建，部署包就是源码快照（`deploy-release.yml` 打 zip） |
| 启动与内存开销小 | 无框架初始化，冷启动快 |

## 5. 负面后果

| 项 | 说明 | 缓解现状 |
| --- | --- | --- |
| 路由分派是手写 if 链 | `main.js:98-221` 是一长串 `if (restPath === ...)`，端点继续增长会失控 | 端点数量已达 15 条以上，可维护性正在下降；复审触发条件 1 即为此设 |
| 无类型保护 | 后端是 JS，重构靠人肉与脚本 | 仅 `node --check` + e2e 脚本，弱于前端 |
| 无中间件链 | 日志、鉴权、限流、请求 ID 都必须在 `route()` 内手工编排，容易漏挂 | 当前**无请求级日志结构化、无限流、无请求 ID**，见 R-003 |
| 单点进程 | 单实例 systemd 承载全部流量，无多实例 | 见 R-004 |
| 关键人单点 | 后端领域知识集中在单一主力 | 见 R-012 |

## 6. 复审触发条件

1. 专用端点数量超过 30 条，或 `main.js` 的 `route()` 函数超过 300 行 → 必须复审是否引入轻量路由表（不引入框架，只做 `Map<路径, handler>` 分派）。
2. 需要请求级中间件能力（统一请求 ID、访问日志结构化、限流、超时熔断）且手工编排已出现漏挂 → 复审。
3. 出现 CPU 密集场景（如批量图像处理、报表计算）导致单实例打满 → 复审 C3 或拆分独立进程。
4. `dependencies` 需要新增第二个运行时依赖 → 必须先复审本文档。
5. 后端主力人员变动（关键人单点解除或失效）→ 复审是否需要引入类型系统降低交接成本。
