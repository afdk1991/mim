## 1. 背景

Mim 有四类与音视频沾边的表层形态，但均**不涉及实时通信（RTC）**：

| 形态 | 载体 | 是否 RTC |
| --- | --- | --- |
| 视频列表页 | `#/videos` → `VideosPage`（`src/app/routes.tsx:106-107`） | 否 |
| 直播页 | `#/live` → `LivePage`（`src/app/routes.tsx:128-129`） | 否 |
| 商城直播会场 | `#/mall/biz/live` → `MallLivePage`（`src/app/routes.tsx:158-159`） | 否 |
| 视频卡片渲染 | `src/ui/post-card.tsx`、富文本渲染 `src/ui/rich-text.tsx` | 否 |

经核实，当前仓库的前端依赖清单（`package.json`）中**不含任何 RTC / 音视频 SDK**：

```text
dependencies: @capacitor/{android,app,browser,core,ios}, react, react-dom
devDependencies: @capacitor/cli, @types/*, @vitejs/plugin-react, pg, playwright-core,
                 typescript, vite, vitest
```

后端依赖清单（`server/package.json`）同样只有 `pg`。

`src/ota.ts` 中的 OTA 指**应用版本热更新**（Tauri/Capacitor 应用包更新），与音视频无关。Tauri 配置的 CSP 中 `media-src 'self' data: https: blob:` 只是允许页面播放媒体元素，不构成媒体服务能力。

结论：**Mim 当前未集成任何 RTC 能力，也不自建音视频基础设施。**

## 2. 备选方案

| 编号 | 方案 | 要点 | 评估 |
| --- | --- | --- | --- |
| F1 | Phase 1 不自建，需要时采购 PaaS | 保留业务入口，能力交给第三方 | **采纳** |
| F2 | 自建 SFU（mediasoup / Janus / LiveKit） | 自托管媒体服务器，完全自控 | 否决 |
| F3 | 自建 MCU/转码集群（FFmpeg + 自研信令） | 连转码一起自扛 | 否决 |
| F4 | 云厂商托管 RTC SaaS（如声网 / 腾讯云 TRTC / 七牛等）立即接入 | 现在就接 | 否决（改为 F1 的后续选项之一） |
| F5 | P2P 直连（WebRTC mesh，无服务端） | 点对点，零服务器成本 | 否决 |

取舍依据：

- **F1 采纳**：音视频是重资产能力——需要 TURN/STUN 部署、带宽按流量计费、跨运营商穿透调优、移动端弱网对抗、回声消除与降噪、录制合流与内容审核。在 Phase 1 业务未验证的前提下自建，会把团队拖入一个与主业务无关的高消耗领域。当前先把页面形态留着，能力留给 PaaS。
- **F2 否决**：SFU 需要常驻高带宽服务器与专门的运维知识；与「无容器、宿主机 systemd、单实例」的部署路线冲突。带宽成本也从「无」跳到「按峰值并发计费」。
- **F3 否决**：转码是 CPU 密集任务，会与 API 争抢单实例资源，且与 ADR-003 的 CPU 瓶颈复审条件直接冲突。
- **F4 否决（暂不）**：不是否定方案本身，而是否定「现在就接」。当前无付费用户与明确场景，接入等于提前产生成本与依赖。它作为 F1 触发后的首要候选保留。
- **F5 否决**：P2P 在移动网络与对称 NAT 下连通率不可控，且无服务端就无法录制、无法审核、无法做多人场景。

## 3. 决策

**采纳 F1：Phase 1 不自建音视频基础设施、不集成 RTC SDK。**

### 3.1 决策边界（做什么 / 不做什么）

| 做 | 不做 |
| --- | --- |
| 保留 `#/videos` / `#/live` / `#/mall/biz/live` 页面与内容展示形态 | 不做实时音视频通话、连麦、互动直播推流 |
| 播放静态媒体文件（`<video>` / `<audio>` 标签、blob/data/https 来源） | 不做自建转码、录制、合流、切片 |
| 保持 CSP 中 `media-src` 的当前配置 | 不引入 TURN/STUN、不部署媒体服务器 |
| 成本模型中明确「当前无云音视频/转码支出」 | 不提前接入任何音视频 SDK |

### 3.2 触发重新评审的条件

出现**任一**条件，本文档状态从「已接受」转为「提议」，进入 F1 的后续选项评审：

| 编号 | 触发条件 |
| --- | --- |
| T1 | 产品侧明确提出需要实时通话 / 连麦 / 低延时直播（延时要求 < 3s） |
| T2 | 出现付费用户或明确的付费场景，音视频成为付费点 |
| T3 | 合规要求必须具备录制留存或实时内容审核能力 |
| T4 | 单场并发观众规模达到需要专业分发的量级 |

### 3.3 后续选项（触发后的评审顺序）

| 优先级 | 选项 | 评审要点 |
| --- | --- | --- |
| 1 | 云 RTC PaaS（F4） | 按分钟/按 GB 计费测算；是否与自托管主路线的网络形态兼容；SDK 体积对移动端包体的影响 |
| 2 | 自建 SFU（F2） | 仅当并发规模大到 PaaS 成本显著高于自托管带宽 + 服务器成本时才考虑；需先解决部署路线冲突 |
| 3 | P2P（F5） | 仅适用于一对一且无录制/审核要求的场景 |
| 4 | 转码自建（F3） | 独立评估，必须与 API 进程隔离部署 |

### 3.4 触发后必须同步修订的文档

| 文档 | 修订内容 |
| --- | --- |
| docs/ops/成本模型.md | 新增音视频带宽/转码成本项，重算单用户单月成本 |
| ADR-001 跨端策略 | 若引入 PaaS SDK 需要原生插件，需复审跨端适配层的宿主访问边界 |
| ADR-003 后端语言与框架 | 若 PaaS 需要服务端签名/回调，需复审依赖约束与端点数量 |
| docs/ops/可观测性规范.md | 新增通话质量指标（接通率、卡顿率、端到端时延） |
| docs/risk/风险登记册.md | 新增第三方依赖与成本失控风险条目 |

## 4. 正面后果

| 项 | 说明 |
| --- | --- |
| 成本为零 | 音视频相关的带宽、转码、PaaS 支出当前不存在（见成本模型） |
| 运维面不扩张 | 不需要 TURN/STUN、媒体服务器、转码集群 |
| 移动端包体不膨胀 | 不引入 SDK，Capacitor/Tauri 壳体积保持现状 |
| 依赖清单不变 | 与 ADR-003「唯一依赖 pg」、ADR-001「业务层不碰宿主」两条约束一致 |
| 决策可回退 | 页面形态已保留，将来接入不需要重构入口 |

## 5. 负面后果

| 项 | 说明 | 缓解 |
| --- | --- | --- |
| 直播/视频页是空壳 | `#/live`、`#/mall/biz/live`、`#/videos` 目前只承载展示，无法承载真实互动直播 | 接受；避免对外承诺直播能力 |
| 将来接入有集成成本 | 越晚接入，「页面已有但能力缺失」的时间窗越长 | 保留 T1-T4 触发条件，不做无限期拖延 |
| 一旦触发，成本阶跃 | 从 0 直接跳到按量计费，无中间态 | 触发时必须先做并发与成本测算（§3.4） |
| CSP 与网络形态需复审 | 接 PaaS 会引入新的 `connect-src` 与 WebSocket 域名 | 已列入 §3.4 的同步修订清单 |
| 桌面端 CSP 差异 | Tauri 的 CSP 与 nginx 的 CSP 是两份独立配置，接入时需同步两处 | 见 ADR-001 负面后果「三端壳构建未被 CI 覆盖」 |

## 6. 复审触发条件

见 §3.2 的 T1-T4。任一满足即重启评审。此外：

1. 业务方要求在页面对外宣称「直播」能力 → 必须先完成评审，避免能力与承诺不符。
2. 成本模型出现音视频项 → 同步复审本文档。
3. ADR-001 因原生能力缺失而复审 → 连带复审本文件（音视频 SDK 是需要原生能力的典型场景）。
