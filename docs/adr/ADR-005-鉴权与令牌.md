## 1. 背景

Mim 后端零框架（ADR-003），因此认证与授权全部由 `server/src/auth.js` 自行实现，无任何第三方鉴权库。当前实现（以 `auth.js` 文件头注释与代码为准）：

| 能力 | 实现 | 参数 |
| --- | --- | --- |
| 密码哈希 | `crypto.scrypt` + 每用户 16B 随机盐，存储串 `scrypt$N$r$p$saltHex$hashHex` | N=16384, r=8, p=1, keyLen=64, maxmem=64MB |
| 密码校验 | `timingSafeEqual` 比较等长缓冲 | 见 `auth.js:51-57` |
| 时序侧信道 | 用户不存在时也做一次等价运算（`DUMMY_HASH`） | 见 `auth.js:59` |
| 令牌签发 | 自签 HMAC-SHA256，`base64url(payload).base64url(sig)` | payload = `{ uid, jti, iat, exp }` |
| 令牌校验 | 重算 HMAC + `timingSafeEqual`，再校验 `uid` 存在与 `exp` 未过期 | `auth.js:70-85` |
| 令牌吊销 | 按 `jti` 落 `token_revocations` 表，使登出对已签发令牌真正生效 | `auth.js:5-7` 注释 |
| 有效期 | `TOKEN_TTL_MS`，缺省 7 天 | `auth.js:25` |

授权模型为 RBAC，表结构是 `roles` / `permissions` / `user_roles` / `role_permissions` / `audit_logs`；其中 `roles`、`permissions` 对公众可读，写入仅管理员。`0001_iam.sql` 是身份域的初始迁移。

已知的两处必须闭环的欠账（代码内显式存在）：

```js
// server/src/auth.js
const DEV_SECRET = 'mim-dev-secret-change-me'
const secret = process.env.JWT_SECRET || DEV_SECRET
if (!process.env.JWT_SECRET) {
  console.warn('[auth] 未设置 JWT_SECRET，正在使用开发用默认密钥——生产部署必须显式设置')
}
```

即：**密钥缺失时服务照常启动，只是打一行 warn**。这是本 ADR 必须约束的核心问题。

## 2. 备选方案

| 编号 | 方案 | 要点 | 评估 |
| --- | --- | --- | --- |
| E1 | 自签 HMAC-SHA256 无状态令牌 + jti 吊销表 | 现状 | 采纳 |
| E2 | 引入 JWT 库（jsonwebtoken / jose）+ 标准 JWT | 用生态实现签名与校验 | 否决 |
| E3 | 服务端会话存储（session 表 + Cookie） | 有状态会话，天然可吊销 | 否决 |
| E4 | 引入 OIDC / 第三方身份服务（Auth0、Keycloak、 Clerk） | 托管身份 | 否决 |
| E5 | 令牌无吊销机制（纯无状态，登出即丢弃前端 token） | 最简 | 否决（曾以此为代价，已改为 jti 吊销） |

取舍依据：

- **E1 采纳**：令牌只有四个字段（uid/jti/iat/exp），签名用 `createHmac` 两行即可完成。用库（E2）换来的只是 header 拼装与声明解析，代价是新增依赖与 CVE 面，与 ADR-003 的「唯一依赖 pg」直接冲突。
- **E2 否决**：依赖成本高于收益。且标准 JWT 库常见的算法混淆风险（`alg: none` / HS-vs-RS 混淆）在自签实现里根本不存在——本实现只认 HMAC-SHA256 一种。
- **E3 否决**：有状态会话需要每次请求查库（或引入 Redis 缓存），与 D3 暂缓引入 Redis 的决策一致；且自托管单实例下，会话表会与业务库抢连接池（默认 `max: 10`）。
- **E4 否决**：外部身份服务与自托管路线冲突，且引入出网依赖。
- **E5 否决**：纯无状态令牌的致命问题是「登出后令牌仍可被重放」。项目已改用 `jti` 吊销表解决，这一改动被保留。

## 3. 决策

**采纳 E1：自签 HMAC-SHA256 无状态令牌 + jti 吊销表 + scrypt 密码哈希。并确立以下强制执行项：**

### 3.1 密钥与配置

| 项 | 要求 |
| --- | --- |
| `JWT_SECRET` | 生产部署必须显式设置；未设置时**当前仅 warn**，必须改为启动期硬失败（见 §3.4 欠账 1） |
| 密钥强度 | 至少 32 字节随机值，不使用可猜测字符串 |
| 注入方式 | 由 systemd `EnvironmentFile=/opt/mim/server/.env` 注入，文件权限 600；服务端不加载 `.env` 文件本身 |
| 令牌有效期 | `TOKEN_TTL_MS` 缺省 7 天，生产应显式设置并纳入密钥轮换策略 |

### 3.2 令牌与密码

| 项 | 要求 |
| --- | --- |
| 令牌格式 | `{base64url(payload)}.{base64url(sig)}`，仅一种算法，不做算法协商 |
| 比较方式 | 一律 `timingSafeEqual`，且先比较长度再比较内容 |
| 过期校验 | `parseToken` 内校验 `exp`，过期返回 `null` 而非抛错，由上层转 `no_auth` |
| 密码存储 | scrypt，参数写入存储串，便于将来调参后旧哈希仍可校验 |
| 用户枚举 | 用户名不存在时执行等价运算（`DUMMY_HASH`） |
| 吊销 | 登出写入 `token_revocations(jti)`，鉴权时校验 |

### 3.3 授权模型

| 层 | 规则 |
| --- | --- |
| 端点级 | 读操作经 `tryAuth`（无令牌按匿名处理）；写操作一律 `authenticate` |
| 表级 | REST 白名单声明 `read`/`write` 策略（`public`/`owner`/`self`/`admin`/`none`） |
| 行级 | 写操作强制注入 owner 列，客户端提交的 owner 值被忽略 |
| 列级 | 列名由 `information_schema` 核定；`users` 表永不开放，`password_hash` 不可被投影 |
| 管理级 | `admin` 写权限另有 `adminOverride` 标记（如 `products`），普通管理员覆盖需显式声明 |
| 设备级 | 一机一密 + `x-iot-hook-token`，见 ADR-002 §3.2 |

### 3.4 必须闭环的两项欠账

| 编号 | 欠账 | 现状 | 要求 |
| --- | --- | --- | --- |
| 欠账 1 | 密钥缺失仅 warn 不阻断 | `auth.js:23-28` 打印 warn 后继续 | 生产环境（`NODE_ENV=production`）下未设置 `JWT_SECRET` 必须启动失败退出 |
| 欠账 2 | 令牌吊销的落库与校验路径依赖运维配置 | `token_revocations` 需随 `0001_iam.sql` 落地，且登出接口需可用 | 上线前必须验证：登出后旧令牌再访问写操作应返回 401 |

### 3.5 明确不做的事

| 项 | 原因 |
| --- | --- |
| 刷新令牌（refresh token） | 当前令牌有效期 7 天，业务未提出短令牌需求；引入刷新令牌会引入第二条令牌生命周期 |
| 多因素认证 | Phase 1 无需求 |
| 第三方 OAuth 登录 | 无需求，且引入外部依赖 |
| 令牌内嵌角色 | 角色在请求期由 `authenticate` 装载，避免角色变更后旧令牌仍带旧权限 |

## 4. 正面后果

| 项 | 说明 |
| --- | --- |
| 零依赖 | 全部实现只用 `node:crypto`，与 ADR-003 一致 |
| 无算法混淆面 | 只认 HMAC-SHA256，标准 JWT 的 `alg` 混淆攻击不成立 |
| 登出真正生效 | `jti` 吊销表让无状态令牌也具备吊销能力 |
| 抗时序侧信道 | 密码比较与令牌签名比较均用 `timingSafeEqual`，用户不存在时做等价运算 |
| 密钥可调参 | scrypt 参数写入存储串，将来提高 N 不需要强制全体重置密码 |
| 密码哈希强度达标 | N=16384/r=8/p=1 属可用的 scrypt 参数区间 |

## 5. 负面后果

| 项 | 说明 | 缓解现状 |
| --- | --- | --- |
| 密钥缺失不阻断启动 | 用默认密钥启动会导致任何人可伪造任意 uid 的令牌，属高危 | 仅 warn（`auth.js:23-28`），登记 R-013，必须在生产环境改硬失败 |
| 无密钥轮换机制 | `secret` 在模块加载时读取一次，轮换必须重启进程且会让全部在线令牌立即失效 | 无热加载机制 |
| 吊销表会增长 | `token_revocations` 只增不删，无过期清理 | 无清理任务，长周期运行会持续膨胀 |
| 吊销需要一次查库 | 每次鉴权需查吊销表，抵消部分无状态收益 | 当前实现细节需按代码核对 |
| 无登录失败限流 | 无账号锁定与 IP 频率限制，可撞库 | 未实现，登记 R-014 |
| 令牌有效期偏长 | 缺省 7 天，且依赖 `TOKEN_TTL_MS` 显式配置 | 生产应显式设置 |

## 6. 复审触发条件

1. 生产环境出现「`JWT_SECRET` 未设置」的部署实例 → 立即复审并落实 §3.4 欠账 1 的硬失败改造。
2. 出现令牌泄露事件或疑似伪造令牌 → 复审是否需要引入短有效期 + 刷新令牌。
3. 需要第三方登录（微信/Apple/Google）→ 复审 E4 与令牌颁发路径。
4. 鉴权路径出现可观测的性能瓶颈（吊销表查询成为热点）→ 复审是否需要缓存层。
5. 安全审计提出密码参数不达标 → 复审 scrypt 参数与迁移到 Argon2id 的可行性（注意会引入新依赖或需 Node 内置支持）。
