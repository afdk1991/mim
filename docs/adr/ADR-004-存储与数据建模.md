## 1. 背景

Mim 的数据存储需求横跨四类：

| 类别 | 内容 | 现状载体 |
| --- | --- | --- |
| 业务主数据 | 身份、内容、商城、四业务、成长、秒杀锁、钱包流水、审计 | PostgreSQL 本机 `127.0.0.1:5432` |
| 设备数据 | `devices`、`device_commands` | PostgreSQL（0008 迁移） |
| 上传文件 | 图片 / 音频 / 视频 / SVG | 本地磁盘 `server/data/uploads`（**非对象存储**） |
| 边缘只读副本 | Workers + D1 只读镜像 | `worker/`（可选路线，非主路线） |

数据库访问层的真实约束（`server/src/db.js`）：

```js
const connectionString = process.env.DATABASE_URL ?? 'postgres://postgres:postgres@127.0.0.1:5432/mim'
export const pool = new Pool({ connectionString, max: Number(process.env.PG_POOL_MAX ?? 10), ... })
```

类型解析做了三处定制以省掉前端二次转换：`int8(20) → number`、`numeric(1700) → number`、`date(1082) → string`（保留 `YYYY-MM-DD` 原样，避免时区偏移成前一天）。

迁移机制的现状：

| 机制 | 说明 |
| --- | --- |
| 执行器 | `server/scripts/migrate.js`，按文件名升序执行 `db/migrations/*.sql` |
| 幂等约定 | 全部语句必须是 `create table if not exists` / `create index if not exists` / `on conflict` 形式 |
| 已应用记录 | 表 `schema_migrations(filename, applied_at)` |
| 失败行为 | 打印失败位置并 `process.exitCode = 1` 后抛出，**不回滚也不继续** |

已应用的迁移文件：

```text
0001_iam  0002_content  0003_commerce  0004_business
0005_growth  0006_sync  0007_seckill_lock_items  0008_iot_device
0010_wallet_idempotency
```

**0009 空缺**：该编号预留给 `ota_package` / `ota_report` 两表（`0008_iot_device.sql` 文件头注释明示），至今未落地。

## 2. 备选方案

| 编号 | 方案 | 要点 | 评估 |
| --- | --- | --- | --- |
| D1 | PostgreSQL 单一主库 + 自研迁移 + 表驱动 REST 白名单 | 现状 | 采纳 |
| D2 | 引入 ORM（Prisma / TypeORM / Drizzle）管理模型与迁移 | 用 schema 文件生成迁移 | 否决 |
| D3 | 多库混合（PG 主 + Redis 缓存/锁 + 对象存储） | 按用途分栈 | 暂缓采纳（仅对象存储部分被刻意排除） |
| D4 | NoSQL / 文档库（MongoDB） | 文档模型贴合内容类数据 | 否决 |
| D5 | 继续使用 SQLite 或嵌入式库 | 零运维 | 不适用（历史遗留，当前代码无残留） |

取舍依据：

- **D1 采纳**：业务数据高度关系化（订单-库存-钱包-券码-秒杀锁），需要事务与行级锁；PG 的事务与 `select ... for update` 直接支撑了秒杀锁与出行库存的并发正确性。自研迁移 + 表白名单让「开放哪些表」成为一行配置的显式决策。
- **D2 否决**：与 ADR-003 的「唯一依赖 pg」冲突。ORM 会引入庞大依赖树与生成产物，且本项目的存量为 9 个 `.sql` 文件，手写 SQL 的可读性反而更好。迁移文件的幂等约定（`if not exists`）已经满足可重复执行需求。
- **D3 暂缓**：Redis 能解决秒杀热点与缓存，但会引入第二个有状态组件与新的运维面，在单实例阶段收益有限。对象存储（S3/OSS）被**刻意排除**——`server/src/storage.js` 文件头注释明确：3MB 图片走 `bytea` 会让表体积与 WAL 成倍膨胀、备份恢复时间不可控，因此选本地目录 + 反向代理缓存，且「换成 S3/OSS 时只需替换本文件的 put/get 两个函数」。
- **D4 否决**：钱包、券码、库存这类强一致场景不适合最终一致的文档模型；且与 PG 侧已投入的事务逻辑不兼容。
- **D5 不适用**：当前代码库中已无 SQLite 痕迹（对 `src/`、`server/`、`scripts/` 全量检索 `sqlite` 关键字无命中）。历史上若存在过 SQLite→PG 的迁移遗留，现已清理完毕；该条仅作为历史风险保留在风险登记册中待证。**不得据此认为当前存在混合存储。**

## 3. 决策

**采纳 D1：PostgreSQL 单一主库 + 自研幂等迁移 + 表驱动 REST 白名单 + 本地磁盘对象存储。**

### 3.1 数据建模约定

| 约定 | 说明 | 依据 |
| --- | --- | --- |
| 迁移文件命名 | `NNNN_<主题>.sql`，4 位序号升序，序号一旦分配不得复用 | `server/scripts/migrate.js` 排序逻辑 |
| 迁移幂等 | 每条语句必须可重复执行，序号跳跃需显式声明预留用途 | 0008 文件头注释对 0009 的预留说明 |
| 归属列强制 | 每张业务表都有 owner 列，写操作由服务端注入，客户端提交的 owner 值被忽略 | `server/src/rest.js:1-14` 安全模型三层说明 |
| 保密列 | `visibility` 列名登记（`posts` 表），非本人在读时剔除 `self` 行 | `rest.js:31` |
| 复合主键 | 需要时在白名单里声明 `pk: [...]`（如 `live_shelf`、`travel_date_stock`） | `rest.js:65,67,68` |
| 类型解析 | 金额用 `numeric`、时间戳用 `timestamptz`、日期用 `date`（不做时区转换） | `server/src/db.js:8-10` |
| 幂等键 | 业务单据号优于请求级 nonce；唯一约束用表达式索引 + 部分索引实现 | `0010_wallet_idempotency.sql` 全文说明 |

### 3.2 表开放策略（安全模型三层）

1. **表白名单**：不在 `TABLES` 里的表一律拒绝，`users` 永久不在白名单（因此 `password_hash` 不可能被 `select=*` 带出去），公开资料一律走 `profiles`。
2. **列白名单**：列名由 `information_schema` 实时核定，未知列返回 `code='schema'`，提示文案与 PostgREST 一致使前端自动降级。
3. **归属校验**：写操作强制注入/过滤 owner 列。

当前 REST 白名单为 **36 张表**。注意：`devices`、`device_commands` **不在**其中——设备数据只能经 IoT 专用端点访问，这是刻意的安全选择。

### 3.3 `users` 表的封闭性及其代价

`users` 表不开放，带来一项明确的运营代价：运营侧无法用通用 REST 查询用户，只能依赖 RPC（当前 `admin_user_lookup` 一个入口）。该代价已被接受并登记为风险 R-008。

### 3.4 对象存储

| 项 | 现状 |
| --- | --- |
| 实现 | 本地磁盘，`server/src/storage.js`，写入目录默认 `<cwd>/data/uploads`，可由 `UPLOAD_DIR` 覆盖 |
| 单文件上限 | 3MB（`UPLOAD_MAX_BYTES`，与 nginx `client_max_body_size 3m`、前端 `LIMITS.uploadMaxBytes` 三方对齐） |
| 读路径 | `/api/storage/<key>` 由 nginx 反代；SVG 单独加 `default-src 'none'` CSP + `nosniff` 防 stored-XSS |
| 成本 | 无对象存储费用，占用宿主机磁盘 |

## 4. 正面后果

| 项 | 说明 |
| --- | --- |
| 事务正确性 | 秒杀锁、出行库存、钱包扣款依赖 PG 事务与行锁，无需外部协调 |
| 单一有状态组件 | 除 EMQX（IoT）外，主链路只有 PG，运维面收敛 |
| 迁移可审计 | 9 个 `.sql` 文件即全部结构历史，`schema_migrations` 记录已应用项 |
| 表开放是显式决策 | 白名单是一行配置，新增开放必须改代码并评审 |
| 存储成本可控 | 本地磁盘替代对象存储，无出网流量费 |
| 类型往返无损耗 | `db.js` 的类型解析定制让 JSON 直接可用，前端不写二次转换 |

## 5. 负面后果

| 项 | 说明 | 缓解现状 |
| --- | --- | --- |
| 迁移序号出现空缺 | 0009 空缺导致 OTA 表无法落地，设备 OTA 全链路阻塞 | 登记 R-001；0009 编号必须保留给 OTA，不得被其它迁移占用 |
| 迁移失败无回滚 | 执行器失败即抛异常退出，已执行的前序文件不回滚，需人工介入 | 依赖每个文件自身幂等，重跑可续 |
| 无在线 DDL 规范 | 缺表/缺列靠 `code='schema'` 与前端降级兜底，属于「运行时才发现」 | 前端 `writeWithFallback` 自动降级 |
| 对象存储不可水平扩展 | 上传文件落在单机磁盘，多实例部署时不可共享 | 当前单实例，未触发；多实例前必须先换 S3/OSS |
| 无 Redis，热点靠 PG 硬扛 | 秒杀热点集中在 PG 行锁 | 当前有 `sweepSeckillLocks` 定时器兜底清理过期锁（`main.js:267-272`） |
| 备份依赖外部调度 | `scripts/backup.sh` 存在，但仓库内无 crontab 落地证据 | 登记 R-009 |
| `users` 封闭 | 运营查询只能走 RPC | 登记 R-008 |

## 6. 复审触发条件

1. `0009_*.sql` 迁移落地 → 复审数据建模章节，并同步 ADR-002。
2. 单实例 PG 出现 CPU/连接数瓶颈（连接池默认 `max: 10` 成为瓶颈）→ 复审是否需要读副本、连接池中间件或 Redis 缓存层。
3. 需要多实例部署 → 必须先复审对象存储（本地磁盘不满足共享），并把 `storage.js` 换成 S3/OSS 实现。
4. 单表数据量进入千万级 → 复审分区与归档策略。
5. 出现需要跨表强一致的分布式场景 → 复审 D3（引入 Redis 或拆分服务）。
6. 备份脚本未被调度证实 → 复审 R-009 状态。
