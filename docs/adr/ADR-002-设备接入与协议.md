## 1. 背景

Mim 规划接入自有 IoT 设备（机型标识形如 `mim-s1`，见迁移注释）。设备侧需要一条「App → 服务端 → 设备」的下行指令通路与「设备 → 服务端 → App」的上行回执通路，并预留固件升级（OTA）能力。

当前仓库的真实落地范围（以 `server/src/iot.js` 文件头注释第 23-26 行为准）：

```text
刻意不做的事：
  - 不做 OTA check/report（随下一轮 0009 迁移落地）
  - 不做设备激活/绑定（BLE 配网闭环后签发 Device-Token 时一并实现）
  - 不订阅 MQTT：上行回执走 EMQX 规则引擎 Webhook，本进程不持有 MQTT 连接
```

即：**长连接网关骨架已落地，设备激活与 OTA 服务端未落地。**

已落地的数据库对象在 `server/db/migrations/0008_iot_device.sql`：

| 对象 | 用途 | 关键设计 |
| --- | --- | --- |
| `devices` | 设备档案、在线状态、一机一密 | `id` 即 device_id（出厂写入，非自增/UUID）；`device_token_hash` 存 `sha256(Device-Token)`；`status` 枚举 `pending_activate`/`offline`/`online`；`fw_version`+`build` 为 OTA 防降级基准 |
| `device_commands` | 下行指令单 | `id` 由 App 侧生成（8~64 位字母数字-_），同时是幂等键；状态机 `pending → sent → acked / failed` |

迁移目录现状（`server/db/migrations/`）：

```text
0001_iam.sql  0002_content.sql  0003_commerce.sql  0004_business.sql
0005_growth.sql  0006_sync.sql  0007_seckill_lock_items.sql
0008_iot_device.sql  0010_wallet_idempotency.sql
```

**0009 编号空缺**，正是留给 `ota_package` / `ota_report` 两表的（见 `0008_iot_device.sql` 文件头注释）。

## 2. 备选方案

| 编号 | 方案 | 要点 | 评估 |
| --- | --- | --- | --- |
| B1 | MQTT（EMQX 自托管）+ HTTP 钩子 + 规则引擎 Webhook | 服务端不持有 MQTT 连接，只提供钩子端点与 HTTP 下发 | 采纳 |
| B2 | 服务端自建 WebSocket 长连接网关 | node:http 上自建 WS，设备直连本服务 | 否决 |
| B3 | 直连云厂商 IoT 平台（如 AWS IoT / 阿里云 IoT） | 托管 MQTT 与设备影子、OTA 开箱即用 | 否决 |
| B4 | 纯 HTTP 轮询，不做长连接 | 设备定期拉取指令 | 否决 |
| B5 | MQTT + 服务端同时订阅 MQTT（消费上行） | 本进程持有 MQTT 客户端 | 否决 |

取舍依据：

- **B1 采纳**：服务端退化为「无状态的钩子提供者」。上行由 EMQX 规则引擎 SQL `SELECT clientid, topic, payload FROM "$dev/+/up"` 通过 Webhook POST 到 `/api/iot/uplink`；下行由服务端调 EMQX 5.x HTTP API `/api/v5/publish` 投递 QoS1。好处是 node 进程不维护任何长连接状态，`Restart=always` 可以随便重启而不影响设备连接。代价是引入 EMQX 这一新的有状态组件与它的运维成本。
- **B2 否决**：自建 WS 意味着进程内持有数万连接与心跳，与当前单实例 systemd 部署冲突；一旦进程重启全部设备掉线。缺连接池 multiplexing 之前，这条路会把「后端单点」风险放大成「设备全断」。
- **B3 否决**：与 ADR-003 的「零框架、唯一依赖 pg、可自托管」路线冲突；云厂商 IoT 按消息数计费且数据出域，与自托管主路线不兼容。
- **B4 否决**：指令时延不可控（轮询间隔即最坏时延），且设备侧耗电与流量上升。
- **B5 否决**：服务端持有 MQTT 客户端会引入第二个外部依赖并制造连接状态，与 B1 的核心收益（无状态）相悖；撤回 B1 的收益换取不了任何东西。

## 3. 决策

**采纳 B1：EMQX 自托管 + 服务端无状态钩子。**

### 3.1 Topic 规范

| 方向 | Topic | 设备权限 |
| --- | --- | --- |
| 下行指令 | `$dev/{device_id}/cmd` | 仅 subscribe 自己 |
| 上行回执 | `$dev/{device_id}/up` | 仅 publish 自己 |
| 影子上报 | `$dev/{device_id}/shadow` | 仅 publish 自己 |

授权钩子 `hookAcl`（`server/src/iot.js:81-90`）按最小面原则放行，任何跨设备读写一律 `deny`。

### 3.2 鉴权

| 环节 | 机制 |
| --- | --- |
| 设备 → EMQX | 一机一密。EMQX 5.x http backend 约定 `username = device_id`、`password = Device-Token`；服务端存 `sha256(Device-Token)`，比较在 `hookAuth`（`iot.js:63-75`）完成。未签发 Token（`pending_activate`）一律 deny |
| EMQX → 服务端 | 请求头 `x-iot-hook-token` 共享密钥，`checkHookToken`（`iot.js:48-53`）用 sha256 + `timingSafeEqual` 校验。未配置 `IOT_HOOK_TOKEN` 时端点视为未启用并抛 403 |
| App → 服务端 | 用户令牌，由 `authenticate(req)` 装载（`main.js:173-184`）；`sendCommand` 校验 `owner_id === ctx.uid`，否则 30103 |

### 3.3 指令通路

```text
App ──POST /api/iot/devices/{id}/command──▶ sendCommand
                                           ├─ 落库 device_commands（on conflict 幂等）
                                           ├─ 设备不在线 → 置 failed(fail_reason=device_offline) 抛 30102
                                           └─ POST {EMQX}/api/v5/publish  QoS1（5s 超时 → busy）
                                                    │
设备 ◀── $dev/{id}/cmd ────────────────────────────┘
  │
  └─ $dev/{id}/up ──▶ EMQX 规则引擎 ──POST /api/iot/uplink──▶ 回写 acked/failed
                                                    │
App ──GET /api/iot/devices/{id}/command/{cmd_id}────┘（轮询 commandStatus）
```

关键约束：上行回执只消化 `pending`/`sent` 两态（`iot.js:132-137`），重复回执与超时迟到的回执不会回退终态。

### 3.4 OTA 与设备影子：明确未实现

以下三项**当前代码不存在**，本文档如实标注，不视为已交付：

| 能力 | 状态 | 依赖 |
| --- | --- | --- |
| `ota_package` / `ota_report` 表 | 未落地 | 缺失的 `0009_*.sql` 迁移 |
| 设备影子（desired/reported 状态存储与读回） | 未落地 | 服务端无影子存储表与影子读写接口；离线清理目前依赖 EMQX retained 机制承担（`iot.js:79` 注释） |
| 设备激活 / 绑定（BLE 配网闭环 + Device-Token 签发流程） | 未落地 | 依赖配网协议与机型清单落地 |

`devices` 表已预留 `fw_version` 与 `build` 两列作为 OTA 防降级比较基准，但无代码读写它们。

## 4. 正面后果

| 项 | 说明 |
| --- | --- |
| 服务端无状态 | 不持有 MQTT 连接，进程可随时重启，与 systemd `Restart=always` 天然契合 |
| 依赖清单不变 | 仍然只有 `pg` 一个外部依赖（`server/package.json`），EMQX 用其 HTTP API 与 `fetch` 交互 |
| 下行有幂等 | `cmd_id` 由 App 生成且为指令主键，`on conflict do nothing` 直接回旧单，网络重发不产生重复动作 |
| 权限最小化 | 设备只能触碰自己的三条 Topic，攻击面收敛到单设备 |
| 在线状态有回写 | `client.connected` / `client.disconnected` 事件钩子回写 `devices.status` 与 `last_seen_at` |

## 5. 负面后果

| 项 | 说明 | 现状缓解 |
| --- | --- | --- |
| 引入 EMQX 运维负担 | 新增有状态组件、新端口（默认 API 18083）、新凭据（API Key/Secret），而当前无监控覆盖 | 未配置 `EMQX_API_KEY/SECRET` 时 `sendCommand` 直接抛 503，不会静默失败 |
| 指令结果靠轮询 | App 侧需轮询 `commandStatus`，无推送 | 客户端轮询间隔由前端自定，服务端不提供长轮询 |
| 无离线指令队列 | 设备离线时 `sendCommand` 直接置 `failed`，指令不排队 | 未实现；业务上要求「离线也能生效」时需改状态机 |
| OTA 与影子缺位 | 设备固件升级与状态同步服务端未落地 | 登记为 R-001 / R-002 |
| 设备表不在 REST 白名单 | `devices`、`device_commands` 未被 `server/src/rest.js` 的 `TABLES` 收录，无法走通用 REST；设备数据访问必须经 IoT 专用端点 | 视为刻意的安全选择，非缺陷；但运营查询需另开 RPC（登记 R-008） |
| 无设备侧限流 | 钩子端点无频率限制，异常设备可打满钩子 | 未实现 |

## 6. 复审触发条件

1. `0009_*.sql` 迁移落地（OTA 表到位）→ 立即复审并更新本文件状态为「已接受（含 OTA）」。
2. BLE 配网协议与机型清单落地 → 复审设备激活/绑定章节。
3. 在线设备数超过单 EMQX 节点承载评估值 → 复审是否需要集群与连接数容量规划。
4. 出现「离线指令队列」业务需求 → 复审状态机，可能需要引入 `queued` 态。
5. 设备影子出现明确业务诉求（如「App 未打开时也要看到最新状态」）→ 复审影子存储的落库位置（PG 表 vs EMQX retained）。
