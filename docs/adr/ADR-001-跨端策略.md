## 1. 背景

Mim 是内容与商城聚合应用，需要同时覆盖四类运行端：

| 端 | 载体 | 现状载体文件 |
| --- | --- | --- |
| Web | 浏览器 + GitHub Pages | `vite.config.ts`（`base: './'`） |
| Android / iOS | Capacitor 8 壳 | `capacitor.config.ts`（`webDir: dist`） |
| Windows / macOS / Linux | Tauri 2 壳 | `src-tauri/tauri.conf.json`（`frontendDist: ../dist`） |
| HarmonyOS | 鸿蒙 ArkTS 壳 | `harmony/AppScope/app.json5`（`bundleName: com.afdk1991.mim`） |

三端壳全部指向同一份 Vite 构建产物 `dist/`，前端侧另有一层平台适配层 `src/platform/{web,capacitor,miniprogram,mock}.ts` 屏蔽宿主差异（见 `src/platform/types.ts`）。前端路由是自研 hash 路由（`src/app/router.tsx`、`src/app/routes.tsx`，`resolveRoute` 以 `switch (root)` 分派），全站 59 条可达路由。

约束条件：

1. 团队规模小，不存在为四个端各配一套原生 UI 的人力。
2. 前端已确立分层 `pages → app → domain → data → core`，依赖方向单向向下，不允许平台分支散落到业务代码里。
3. 部署路线全程不使用容器（见 `.github/workflows/build.yml:41-77` 的禁容器闸门），交付形态是「宿主机进程 + 静态产物 + 原生壳」。
4. 已有历史遗留：早期存在小程序适配层 `src/platform/miniprogram.ts`，当前不作为主路线。

## 2. 备选方案

| 编号 | 方案 | 要点 | 评估 |
| --- | --- | --- | --- |
| A1 | 一套 Web 代码 + 三端壳（现状） | React 18 + Vite 产出 `dist/`，Capacitor 打包移动、Tauri 打包桌面、鸿蒙壳加载本地资源 | 采纳 |
| A2 | Flutter / React Native 重写跨端 | 用一套 Dart/RN 代码覆盖移动与桌面 | 否决 |
| A3 | 各端原生开发 | Android Kotlin、iOS Swift、桌面 Qt、鸿蒙 ArkUI 各自实现 | 否决 |
| A4 | 纯 Web（PWA）不做壳 | 只用浏览器，不做应用商店分发 | 否决（部分能力被 Tauri 分流） |
| A5 | 小程序作为主端 | 以微信/鸿蒙元服务为主入口 | 否决，保留适配层备用 |

取舍依据：

- **A2 否决**：Flutter 需要重写全部 UI，等于废弃现存的 React 组件与 59 条路由对应的页面；Dart 侧还要重建 `domain` 层与三态写回协议，迁移成本高于收益。React Native 桌面端支持薄弱，桌面三平台仍需第二套方案，反而变成「两套 UI」。
- **A3 否决**：四倍 UI 工作量与四倍发版链路，与团队人力不匹配。
- **A4 否决**：失去应用商店分发与桌面端形态。但 PWA 的能力并非全废——Web 端仍是唯一无需安装即可触达的入口，`build.yml` 保留 Pages 部署。
- **A5 否决**：小程序容器与自托管后端的直连受域名白名单与审核约束；`src/platform/miniprogram.ts` 保留为适配层，不为它单开路线。

## 3. 决策

**采纳 A1：单一 Web 代码库 + 三端壳。业务 UI 只写一次，平台差异一律收敛到 `src/platform/`。**

具体约束（写入工程规范，机器可校验）：

1. 业务代码不得出现 `window.Capacitor`、`window.__TAURI__`、`navigator.userAgent` 之类的宿主嗅探；全工程仅 `src/platform/` 与 `src/ota.ts` 允许直接触碰宿主全局对象。
2. 三端壳必须指向同一份 `dist/`，壳工程内不写业务代码；`capacitor.config.ts` 的 `webDir`、`tauri.conf.json` 的 `frontendDist` 是唯一绑定点。
3. 前端路由保持 hash 模式：hash 路由不依赖服务端 history fallback，`file://` 或 WebView 本地资源加载均可正常工作（见 `capacitor.config.ts` 注释）。这是三端壳能直接加载 `dist/` 的前提，不得改为 history 模式。
4. Vite `base` 固定 `'./'` 相对路径，使产物可塞进任意路径前缀（Pages 子路径、壳内相对目录）。
5. 后端地址由构建期变量 `VITE_MIM_API_BASE` 注入（见 `vite.config.ts:5`、`src/core/config.ts`）；未配置时前端回退同源 `/api`，数据落 localStorage，云端写回走三态协议的 `skip` 分支。
6. 新增端（如将来的小程序正式启用）必须先补 `src/platform/<端>.ts` 实现契约，再由 `src/platform/index.ts` 的 `getPlatform()` 分派，不允许业务层直接判断。

## 4. 正面后果

| 项 | 说明 |
| --- | --- |
| UI 工作量恒定 | 59 条路由、四类业务域（内容/社交/商城/工具台）只实现一次 |
| 发版链路收敛 | 一次 `npm run build` 产出供四端复用，`cap sync` 与 Tauri 构建均以此为输入 |
| 平台差异可控 | 宿主能力集中在 `src/platform/`，`tests/platform-contract.test.ts` 可对契约做单测 |
| 离线可用 | hash 路由 + 本地产物加载，壳内无网络也能渲染页面 |
| 与无容器部署自洽 | 不需要容器镜像承载多端构建，宿主机 `npm ci` 即可产出全部产物 |

## 5. 负面后果（已知欠账，不粉饰）

| 项 | 说明 | 缓解 |
| --- | --- | --- |
| 性能天花板 | WebView 渲染，长列表与复杂动画弱于原生；Tauri 桌面端同样受 WebView2/WebKit 制约 | 页面级懒加载与虚拟滚动，暂未实现 |
| 原生能力受限 | 蓝牙配网、本地通知、后台定位等必须依赖 Capacitor/Tauri 插件，缺插件即缺能力 | 影响 ADR-002 的 BLE 配网闭环，已登记为 R-011 |
| 包体积 | 每个壳都要内嵌完整 Web 产物，移动端包体积偏大 | 暂未做产物裁剪 |
| 桌面端形态不原生 | Tauri 产物本质是 WebView 窗口，菜单/托盘/文件系统等原生集成度低 | 桌面端定位为「副产物」，主力仍是 Web 与移动 |
| 三端壳构建未被 CI 覆盖 | 当前 `build.yml` 只做类型检查 + 前端构建 + Pages 部署；桌面端构建在 `build-release.yml`（tag `V*.*.*.*` 触发），移动端与鸿蒙无 CI | 见 docs/release/发版契约与回滚预案.md 的待建项 |
| 平台适配层存在未启用实现 | `src/platform/miniprogram.ts`、`mock.ts` 有契约实现但非主路线，易被误改 | 契约单测覆盖，改动需同步 `contract-check.ts` |

## 6. 复审触发条件

出现任一情形，本文档转为「提议」状态并重新评审：

1. 需要 Capacitor/Tauri 现有插件无法满足的原生能力（如蓝牙配网、后台定位、本地音视频采集）。
2. 任一端出现性能基线不达标且优化无解（长列表掉帧无法通过虚拟滚动解决）。
3. 团队新增原生端开发人力，使得 A2/A3 的人力约束消失。
4. 小程序被重新确立为主入口（`src/platform/miniprogram.ts` 转正）。
5. 三端壳的构建产物体积超过分发渠道硬限制（如应用商店包体上限）。
