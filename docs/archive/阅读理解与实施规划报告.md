### 0.2 五个关键结论

1. **项目是「单体全栈内容社区 + 自营商城 + 工具台」，不是「多平台内容分发 SaaS」。**
2. **`全平台.md` 不是产品规格书，而是一份 AI 问答对话的复制粘贴记录**（同一段对话重复约 3 遍，含「内容由AI生成，可能不准确，请注意核实」「共参考 19 篇资料」等 AI 产品痕迹）。它描述的是「uni-app x 一套代码覆盖多端 + 多平台分发中台 + 跨境电商 + 分销体系」，与本仓库实际技术路线**几乎完全不同**。
3. **代码侧真实形态**：React 18 + TypeScript + Vite 单页应用（自研 hash 路由、零 UI 库、零状态库）+ 仓库内自托管 Node 20 / `node:http` / PostgreSQL 后端 + Capacitor / Tauri / Harmony 三套原生壳 + 宿主机 systemd 部署。
4. **功能面已完成度较高的是「站内四业务」**：内容（16 路由）/ 社交（7）/ 商城含四业务会场（14）/ 权益（3）/ 工具台（9）/ 系统与后台（8，含新增商品管理与充值核销），共 **57 条可达路由**。
5. **`全平台.md` 中真正「零实现」的是它最核心的部分**：多平台发布队列、账号矩阵、数据回传、跨境电商铺货、分销结算对账——代码中一行都没有。

## 1. 项目整体目标与定位

### 1.1 官方自述（代码内权威口径）

`README.md` 第 3 行给出定位：

> Mim 是一个「动态 / 文章 / 商城 / 工具台」四合一的内容聚合社区 Web 应用：前端是零第三方状态库与路由库的 React + Vite 单页应用，后端是仓库内自托管的 `server/`（Node 20 + `node:http` + PostgreSQL），**不配置后端时前端依然完全可用**（数据落 localStorage，云端写回自动跳过）。

`src/core/config.ts` 的 `SITE_CONFIG` 进一步给出运营主体口径：

- `owner`：`个人开发者 afdk1991`
- `domain`：`afdk1991.github.io/mim`
- `contactEmail`：`afdk1991@users.noreply.github.com`
- `icp` / `policeBeian` / `creditCode` / `publishLicense` / `opBeian` / `address`：**全部留空**
- `filingNote`：`本站为个人开发学习项目，暂未办理经营性备案。`

### 1.2 定位判断（三条）

| 维度 | 判断 | 依据 |
| --- | --- | --- |
| 产品形态 | 单站点「社区 + 电商 + 工具箱」综合体，非 SaaS、非多租户 | 无 tenant / workspace / 组织概念；`users` 单表 + 角色权限 |
| 用户规模假设 | 个人开发者自用 / 小规模社群 | 站点主体为个人、备案信息留空、部署为单机 systemd |
| 商业模式 | 站内自营商品 + 钱包人工核销 + VIP 订阅；**不做平台抽佣/分销** | `MallWalletPage` 只提交充值申请、`VipCenterPage` 扣款成功才发权益、无分销/供货价模型 |

### 1.3 与「内容聚合」的实质含义

「聚合」在本项目中指**站内多形态内容的统一入口**（动态 Feed / 长文 / 视频 / 代码片段 / 资源下载 / 漫剧片单 / AI 可转载资源），**不是**「从外部平台聚合内容再分发」。这一点是理解第 4 章差距的前提。

## 4. `全平台.md` 规划要点拆解与差距分析

### 4.1 文档性质判定（本章最重要的一条）

**判定结论：`全平台.md` 是一份 AI 问答对话的复制粘贴记录，不是本项目的产品规格书。**

判断依据（可直接在文件中定位）：

| 证据 | 位置 | 说明 |
| --- | --- | --- |
| 同一段对话重复约 3 遍 | 全文 | 每次重复都带同样的开场与结尾，是「复制 AI 回答」的典型形态 |
| `已完成分析，共参考 19 篇资料` | L18 | AI 检索类产品的固定话术 |
| `内容由AI生成，可能不准确，请注意核实` | L53 / L106 / L260 / L305 | AI 产品的免责声明 |
| `已为你把消息转换成文档…创建于 10-28 18:08` | L261-L291 | 「把聊天记录转成 Word / 合并文档」的操作记录 |
| `这两个文档合并…合并为一份完整的 Word 文档《全平台统一架构与实施方案》` | L261-L291 | 说明本文是合并前的原始聊天记录，不是定稿规格 |

因此，本文档的正确用法是：**把它当作「一份外部顾问给出的行业级通用方案建议」来读**，而不是「本项目的需求基线」。第 4.2 节的完成度评估据此展开——评估的是「这份建议在本仓库落地了多少」，而不是「项目是否偏离了自己的规格」。

## 5. 后续实施建议与推进步骤

### 5.1 总体策略

**不建议按 `全平台.md` 改造项目。** 理由：C1（文档非规格）+ C2（uni-app 迁移是重写）+ C4（平台化需要多租户、分销、外部平台 OAuth，是另一个产品）。当前代码完成度高、约束清晰、可运行，正确策略是**「先把自营闭环补齐，再决定是否平台化」**。

### 5.2 优先级排序

#### P0（本周内，低成本高收益，1–2 人天）

| 项 | 动作 | 说明 |
| --- | --- | --- |
| P2-1 | `#/coze` 从「连通性检测」升级为真实智能体调用（服务端新增 `rpc: ai_chat`，密钥存 `server/.env`） | 前端不得持有 API Key |
| P2-2 | 补 `products` / `articles` 的运营侧批量导入（CSV → `/api/rest/products`） | 复用 `#/bom` 已有的 CSV 导出/解析能力 |
| P2-3 | 可观测性：`/api/health` 扩为 `/api/metrics`（请求数 / 慢查询 / RPC 失败率），nginx 日志接入 logrotate 已有 | 不引入新依赖，纯 `node:http` |
| P2-4 | 前端补最小单测（`node:test` 直测 `domain/*` 纯函数：`order.ts` 双状态机、`growth.ts` 记分、`utils.ts` 分/元换算） | domain 层无 React 依赖，天然可测 |
| P2-5 | 若确需移动端体验提升：优先优化现有 Capacitor 壳（安全区 / 返回键 / 离线缓存），**不要迁移 uni-app** | 成本差一个数量级 |

#### P3（评估后再定，不轻易启动）

| 项 | 前置条件 |
| --- | --- |
| 引入 Redis | 单机 QPS 上来、或 PG 行锁成为瓶颈；当前 `SECKILL_LOCK_MS` + 行锁方案已能防超卖 |
| 引入消息队列 | 出现异步任务（发信、分发、AI 生成）后再引入 |
| 多平台分发中台 | 需先明确「分发是自用工具还是对外 SaaS」；若是自用，可先做**单向导出**（Markdown/图片包），成本远低于 OAuth + 发布队列 |
| 跨境电商 / 分销 | 需要企业主体、店铺授权、结算合规，与当前「个人开发者、备案留空」定位冲突 |

### 5.3 推进节奏（建议）

```
第 1 周   P0 全部（清理冲突、统一口径）
第 2-3 周 P1-1 / P1-2 / P1-3（后台三件事，形成运营闭环）
第 3-4 周 P1-4 / P1-5 / P1-6（质量与运维底座）
第 5-8 周 P2-1 / P2-3 / P2-4（能力与可观测）
第 9 周+  由用户决策是否启动 P3（平台化）
```

**每个阶段结束必须跑的验证命令**：

```bash
npm run typecheck          # 类型闸门
npm run build              # 构建闸门
npm run verify:routes      # 57 条路由遍历实测（需 dev 服务在跑）
npm run server:health      # 后端 /api/health + /api/rest/products 真实探测
```
