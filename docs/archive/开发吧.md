**三条不可动摇的约束**
1. `domain` 在内容发布时确定且 immutable，所有分发/审核/计费/SEO 均以此路由。
2. svc-feed 与 svc-search **互相无依赖、无调用、无共享索引**。
3. 广场动态页一律 `noindex`，sitemap 仅提交 `/learn/**`。

### 六、关键代码骨架（把隔离写进框架）

**① 域守卫（编译期约定 + 运行期拦截）**
```java
@Retention(RUNTIME) @Target(METHOD) public @interface DomainGuard { Domain[] value(); }
public class DomainContext { private static final ThreadLocal<Domain> C=new ThreadLocal<>();
  static void set(Domain d){C.set(d);} static Domain get(){return C.get();} static void clear(){C.remove();}}
// 网关按 URL(/learn/**,/plaza/**) 或 header X-Domain 注入 → Filter → DomainContext.set(d)
@Around("@annotation(g)") public Object guard(ProceedingJoinPoint pjp, DomainGuard g){
  Domain cur=DomainContext.get();
  if(cur==null||Arrays.stream(g.value()).noneMatch(d->d==cur)) throw new AccessDeniedException("cross-domain denied");
  return pjp.proceed(); }
```

      WHEN type='collect' THEN 3 WHEN type='forward' THEN 5 ELSE 0 END) AS w,

FROM interact_weighted GROUP BY post_id HAVING score > 50 ORDER BY score DESC LIMIT 50;

### 十、守得住才算成：禁止清单 + 预警指标

**《跨域禁止清单》十条（写进 CI 单测 + 评审签字）**
1. 粉丝数不得参与原力分计算；2. 橙V≠博客专家，禁止一键同步身份；3. `domain` 发布后 immutable；4. 权限判定只用 `has(user,benefit,domain)` 三元组；5. 激励预算分桶，禁设总池自动分配；6. 特征库跨域取特征需白名单（仅 age_group/geo/device）；7. 广场积分不得兑换知识下载次数；8. 知识内容不得进入广场会员免费池；9. 广告库存按域物理划分，报表支持分域导出；10. 所有跨域操作必写 `admin_op_log`。

**污染预警（日看板，触线即自动冻结跨域配置变更并回滚）**
| 指标 | 警戒线 |
|---|---|
| 知识态 DAU 看过广场内容占比 | > 35% |
| 技术作者周均发文数（对比基线） | 下降 > 15% |
| 长文单位收益 ÷ 动态单位收益 N | 低于承诺值或环比下跌 |
| 广告主"投放域不符"投诉 | > 0（立即停投） |
| 知识态收录量周环比 / 死链率 | 收录下降 或 死链 > 2% |
| 会员"权益不符"投诉 | 环比上升 |

### 十一、最后三句实话

1. **这个方案的技术风险低，组织风险高**——最大的死因是“运营为了冲数据临时打通一下”。因此必须将禁止清单转化为单测与集成测试并入 CI 卡点，使其成为不可逾越的硬性约束。
2. **不要一次性开放广场态全量**。采用“知识态 100% + 广场态 30%”（仅动态/关注流/私信，砍掉热搜、直播、超话、竞价广告）先跑通，至少省下 6 个月试错期。

### 三、关键代码：把"隔离"写进框架层

#### 3.1 核心：Domain 上下文 + 路由注解（libs/domain-core）

```java
public enum Domain { PLAZA(1), LEARN(2); public final int v; }

@Retention(RUNTIME) @Target({METHOD, TYPE})
public @interface DomainGuard { Domain[] value(); }   // 方法允许处理的域

public class DomainContext {
    private static final ThreadLocal<Domain> CTX = new ThreadLocal<>();
    public static void set(Domain d) { CTX.set(d); }
    public static Domain get() { return CTX.get(); } // null = 未判定，直接抛
    public static void clear() { CTX.remove(); }
}

// 网关层解析：从 header X-Domain 或 URL 前缀 (/learn/**, /plaza/**) 注入
@Component
public class DomainFilter extends OncePerRequestFilter {
    @Override protected void doFilterInternal(HttpServletRequest r, HttpServletResponse s, FilterChain c) {
        String p = r.getRequestURI();
        Domain d = p.startsWith("/learn") ? Domain.LEARN : p.startsWith("/plaza") ? Domain.PLAZA : null;
        if (d != null) DomainContext.set(d);
        try { c.doFilter(r, s); } finally { DomainContext.clear(); }
    }
}

// 拦截器：方法级域校验 + 自动注入 domain 条件
@Aspect @Component
public class DomainGuardAspect {
    @Around("@annotation(g)") public Object around(ProceedingJoinPoint pjp, DomainGuard g) throws Throwable {
        Domain cur = DomainContext.get();
        if (cur == null || Arrays.stream(g.value()).noneMatch(d -> d == cur))
            throw new AccessDeniedException("cross-domain access denied: " + cur);
        return pjp.proceed();
    }
}
```

> 效果：任何 Service 方法只要标了 `@DomainGuard(Domain.LEARN)`，广场态请求进来直接 403。**这是防止“临时打通一下”的最有效手段。**

#### 3.2 内容发布：一次发布，两条完全不同的下游链路

public class ContentPublishService {

    @Transactional
    public ContentVO publish(PublishCmd cmd) {
        // ① domain 在发布时确定，之后 immutable
        Domain domain = cmd.domain();                       // 前端二选一带上来，后端再校验一次
        long id = Snowflake.next();
        int quality = domain == Domain.LEARN ? qualityScorer.score(cmd) : 0;
        int indexFlag = (domain == Domain.LEARN && quality >= 40) ? 1 : 0;  // 广场动态默认 0 = noindex

        contentMapper.insert(Content.of(id, cmd, quality, indexFlag));
        extMapper.insert(domain, id, cmd.ext());

        // ② 异步分流：各自走各自的引擎，绝不交叉
        eventBus.publish(domain == Domain.PLAZA
                ? new DynamicPublishedEvent(id, cmd)        // → Kafka → svc-feed 建 inbox / 热搜计数
                : new ArticlePublishedEvent(id, cmd));      // → Kafka → svc-search 建 ES 文档 + RAG 向量
        return toVO(id);
    }
}

    sitemapNotifier.notify(c.seoSlug());        // SEO 推送

@Service
public class EntitlementEngine {
    /** 唯一入口：判断 user 在 domain 下是否拥有 benefit */
    public boolean has(long userId, String benefit, Domain domain) {
        var e = entRepo.get(userId, benefit, domain);          // 精确三元组
        if (e == null || e.expireAt().isBefore(now())) return false;
        if (e.totalQuota() != null && e.usedQuota() >= e.totalQuota()) return false;
        return true;
    }
    /** 消费次数型权益：必须带 order 溯源，幂等 */
    public boolean consume(long userId, String benefit, Domain domain, long orderId) {
        return tx.exec(() -> {
            var e = entRepo.lock(userId, benefit, domain);     // SELECT ... FOR UPDATE
            if (!has(userId, benefit, domain)) return false;
            if (seenRepo.exists(orderId)) return true;         // 幂等
            entRepo.incUsed(userId, benefit, domain);
            seenRepo.put(orderId);
            return true;
        });
    }
}

### 先说清楚一件事：合并不是叠加，是解决一个根本冲突

微博和 CSDN 的底层机制存在互斥：

- **微博模式 = 时间驱动**：内容价值随时间衰减，系统追求停留时长和曝光量。
- **CSDN 模式 = 需求驱动**：内容价值随时间累积，系统追求“找到答案即走”的效率。

若简单将两个站的功能堆叠在一起，会产生三种典型失败：搜索流被热点 Feed 淹没导致技术内容无法检索；推荐流被长文拖慢进而降低用户停留时长；创作者既想蹭热点又想沉淀干货，最终两边都不讨好。

因此，整合的正确方案并非“一个站塞两套东西”，而是**一套账号、一套内容库、一套钱包结算，配上两套完全隔离的分发引擎，并在前端通过模式开关进行路由**。以下是具体的落地方案。

**关键交互设计（决定成败）**：

1. **顶部一级 Tab 只有三个**：广场 / 知识 / 我的。禁止将热榜混入知识页，也禁止在广场页展示付费专栏。
2. **发布器二选一**：点击发布时先选“发动态”（短文/多图/视频/话题）或“发文章”（Markdown/专栏/资源）。两种形态的编辑器、审核规则及分发路径完全不同，强行合并成一个输入框会导致体验割裂。
3. **双身份卡片**：个人主页分为“动态墙”和“知识库”两个 Tab。博主同时具备粉丝数与原力等级，两者并列展示且互不换算。

5. **一套通知中心，按来源打标**：互动消息（广场）与技术消息（问答被采纳/专栏收录）分区显示，避免技术用户被娱乐化推送干扰而流失。

#### 3. 结算与对账（合并后最容易出钱的地方）

统一链路：`order → revenue_record(按 content_type 匹配费率快照) → settlement_bill(T+N 跑批) → withdraw_apply → tax_record`。
三条铁律不变：金额存“分”整数；费率取**下单时刻快照**；每日全量对账，差 1 分钱触发告警并冻结该渠道结算。
**合并新增的一条**：必须在 `revenue_record` 里永久保留 `domain` 和 `content_type`，因为两端收入结构差异极大（广场靠广告、知识靠订阅），后续做分部核算、税务处理和融资拆分时都需要这笔数据。

### 四、两套引擎必须物理隔离（唯一不能省的重复建设）

| | Feed 引擎（广场） | 检索/RAG 引擎（知识） |
|---|---|---|
| 目标函数 | 停留时长 + 互动率 | 首条命中率 + 问题解决率 |
| 召回源 | 关注、热门、协同过滤、地理位置 | BM25 全文、标签、代码精确匹配、向量语义 |
| 时效权重 | 极强（小时级衰减） | 极弱（版本/更新时间降权，而非时间衰减） |
| 存储 | Redis ZSet inbox + CK 聚合 | ES index + 向量库 + 服务端渲染缓存 |
| 冷启动 | 选标签 + 全站热门 | 注册选技术栈 + 高赞经典文兜底 |
| 反作弊 | 刷量/水军/刷热搜 | 刷阅读/刷下载/搬运查重 |
| **共享层** | \multicolumn{2}{c}{Flink 实时计数 → 统一特征库 → AB 分流服务 → 统一埋点事件规范} |

**RAG 的红线**：只索引 `domain=2 且 status=已发布 且 index_flag=1` 的内容，并且**强制输出来源链接**。一旦把广场动态灌进知识库，AI 回答的质量会立刻崩塌，连带着知识态的专业口碑一起受损。

### 五、统一的成长与会员体系（把两套身份捏成一套而不打架）

**成长：一条积分引擎，两条成长线。**
规则引擎：`行为类型 × 域 × 上限 × 衰减` 配置化。发动态得经验、发博文得积分，两者不互换、不上榜同一榜单。前端展示为“粉丝数 / 原力等级 Lv”双指标。
关键约束：**任何权益都不能跨域自动授予**。广场的大 V 不等于知识态专家，反之亦然；若想获得双端认证，必须分别满足条件（此举能防止娱乐流量冲刷专业信誉，这是合并后最大的品牌风险）。

**会员：一个 SKU 货架，权益按域打标。**

| 档位 | 广场权益 | 知识权益 | 定价建议 |
|---|---|---|---|
| 基础会员 | 装扮、置顶、免广告、编辑已发 | 免广告、高清视频 | 低（身份型） |
| 超级会员 | — | 订阅专栏库、购课折扣、GEO 报告 | 中（内容型，现金牛） |
| 下载/资源包 | — | 下载次数包（可单独卖，不必绑会员） | 高（CSDN 真正的钱） |
| 企业版 | 品牌号、舆情数据 | 技术推广、简历库、算力 | 定制 |

**广告：一个广告主后台，投放时选“投放域”。** 素材库、账户、充值、发票、报表全部共用；计费模块按域插拔——广场走 CPM/oCPM 竞价，知识走纯 CPC + 点击防刷。这样既能向客户讲清“品效合一”，又避免内部维护两套财务账。

### 六、分期路线图（合并版的正确顺序）

**P0（0–4 月）｜统一地基 + 知识态最小闭环**
共用中台（用户/内容基座/交互/支付/审核/后台脚手架）+ 知识态（SSR 博客、搜索、专栏、付费、结算）+ SEO 全量上线。
*为什么先做知识态*：它对并发要求低、变现路径短、SEO 流量可积累，且能与广场态形成“专业内容供给”壁垒。此阶段目标是**拿到第一笔收入和第一批被收录的页面**。

**P1（5–8 月）｜广场态 + 双态打通**
Feed（先规则后推荐）、热搜/话题、私信、动态发布器、统一通知中心、双身份主页、`user_mode_pref` 偏好设置。
里程碑：**同一个账号能在两态间无感切换，且收益进同一个钱包**。

**P2（9–14 月）｜商业化合并**
统一会员货架、广告主自助平台（双域投放）、分润阶梯可配置、结算对账自动化、创作者统一后台、招聘/外包接入。
里程碑：**月流水为正，且能分清每一块钱来自哪个域**。

**P3（15 月+）｜护城河**
直播、超话、竞价广告、RAG/AI 助手全套、GitCode/InsCode 类基础设施、开放平台、企业版。
**红线**：P3 的任何模块，都必须在 P2 的双域核算跑通之后才允许立项。

**人力估算**：峰值 22–26 人，约 20–22 个月，人力 750–1050 万 + 云与第三方 200–350 万/年。相比分别建两个站（约 700–1000 万 + 420–500 人月×2），**合并能省下约 35%–40% 的成本**，主要节省在用户、支付、结算、审核风控、运营后台和数仓这六块。

### 七、合并特有的 6 个坑（单站不会遇到）

1. **品牌稀释**：技术用户看到娱乐八卦会立刻离开。解法：知识态首页**零娱乐内容**，广场态绝不推荐付费专栏；两态之间只通过“作者主页”和“搜索结果”连通。
2. **SEO 被自己污染**：广场动态若生成海量低质页面，会拉低整站域名权重。解法：动态页一律 `noindex`，sitemap 只提交知识态，且两态使用二级域名或路径隔离（如 `blog.` / `s.`）。
3. **推荐系统互相污染特征**：用户白天搜 Spring Boot、晚上看娱乐八卦，若共用同一个兴趣向量，会导致技术推荐越来越不准。解法：特征库按 `domain` 分命名空间，跨域特征需显式授权才能使用。
4. **创作者动机错乱**：一旦动态的流量远大于博文，作者会放弃写长文。解法：**两态的激励预算分开核算、分开公示**，知识态的分成单价不得因广场流量上涨而下调，并在后台明确告知作者“写长文的单位收益是发动态的 N 倍”。
5. **结算串味**：广告主投了广场却被展示在技术文章里（或相反），引发投诉。解法：广告位资源按域物理划分，库存不共享，报表支持分域导出。
6. **合规双重标准**：广场态适用新闻/舆论类监管（热搜、前台实名、未成年人模式），知识态则涉及出版物/教育/算法备案。解法：合规字段在设计期就写入 `content` 和 `user` 表，绝不在后期打补丁。

### 七、给你的三条实操建议

1. **不要并行做两站。** 技术上 55% 可共用，但产品和运营完全是两套逻辑，同时开工会把团队撕成两半。建议先做 CSDN 型（知识+订阅），因为它的变现路径短、对并发要求低、SEO 流量可积累；微博型的 Feed/直播/IM/竞价广告每一个都是深坑。
2. **用“共用后台脚手架”省钱。** 先把 admin 框架（RBAC/审计/字典/配置/文件/通知）做成内部基建，后面 40 多个后台模块每个只需 3–5 天。这是最容易被忽略、却最能压缩工期的一块。
3. **先定数据契约再写代码。** 用户 ID 体系、内容 ID 体系、订单与结算的幂等键、埋点事件规范，这四样在 P0 第一周就要冻结。后期改任何一项都是灾难级返工。

- ### 先把这件事说清楚：不要真的“全部实现”

你列出的两套功能加起来，相当于**两个成熟公司各做了十年的产品**。微博有上千名工程师，CSDN 也有一百多人以上在维护。一个人或小团队把“所有模块”做完，结果必然是每个都只有 60 分、且互相拖死。

所以正确的做法是：**按同一套技术底座，拆成“必须自研的内核”和“能买就买的外围”**，然后分期上线。下面我按这个思路给你完整的工程方案。

### 一、总体架构：一个底座，两套业务域

```
┌─────────────┬──────────────┐
│  微博域      │   CSDN 域     │
│ (注意力流量) │ (知识交易)    │
│ Feed/热搜/   │ 博客/专栏/    │
│ 超话/直播/   │ 资源/问答/    │
│ 打赏/广告    │ 课程/招聘/    │
└──────┬──────┴───────┬──────┘
       │  共用中台     │
   用户中心｜内容中心｜关系｜搜索｜推荐｜支付｜结算｜风控｜AI
       ┌──────────────┴──────────────┐
       │  MySQL · Redis · Kafka · ES  │
       │  OSS/CDN · Flink · K8s       │
       └─────────────────────────────┘
```

**关键原则**：用户、内容、支付、结算、风控这四个域必须一开始就做成共享服务。否则后期两边数据打架，会员体系和创作者账号无法打通，重构成本极高。

### 二、技术选型（给一套能直接落地的）

| 层 | 选型 | 理由 |
|---|---|---|
| Web 前端 | Next.js + React + Tailwind | **SSR 是 CSDN 域的命门**，SEO 全靠它，SPA 直接出局 |
| H5/App | uni-app 或 Flutter（先 H5 + 小程序，App 延后） | 省一半人力 |
| 管理后台 | React Admin / Arco Pro | 内部用，别自己写 UI |
| BFF/网关 | Node.js(Nest) 或 Spring Cloud Gateway | 聚合接口、鉴权、限流 |
| 业务服务 | Java + Spring Boot（主）+ Go（IM/推送等高并发点） | 生态好招人，Go 处理长连接更省资源 |
| 数据库 | MySQL 8（分库分表 ShardingSphere）+ Redis Cluster | 内容表按 user_id 分片，Feed 表按时间分片 |
| 搜索 | Elasticsearch（主搜）+ ClickHouse（热榜/分析） | ES 做全文，CK 做实时榜单和报表 |
| 消息 | Kafka（业务事件）+ RocketMQ（事务/延时消息） | 结算、通知这类不能丢的用 MQ 事务消息 |
| 实时计算 | Flink（点赞阅读计数、热榜、风控特征） | 微博域的热榜和 CSDN 的热榜都靠它 |

| 推荐/画像 | Python + PyTorch/DeepFM，离线 Spark + 在线 Redis 召回 | 初期规则召回就够了，别一上来上大模型 |
| 部署 | 宿主机 systemd + nginx + GitHub Actions + Prometheus/Grafana | 本项目不使用容器，见 `deploy/README.md` |
| ID 生成 | 雪花算法（Snowflake），全局唯一且有序 | 分页、排序都依赖它 |

### 三、核心领域模型（最关键的几张表）

不用全写，但下面这几个设计错了后面全崩：

**1. 内容表 `post`** —— 一张表承载微博短文 + 技术长文
```
id, user_id, type(short/long/video/resource/course), 
title, content_md, content_html(渲染缓存), cover, 
tags[], column_id(付费专栏), price, vip_visible, 
status(pending/published/rejected/deleted), 
audit_result, seo_slug, created_at, updated_at
```
要点：`content_html` 是 Markdown 渲染后的缓存，写入时生成，读取时零计算。**这是 CSDN 域读多写少的性能命门。**

**2. Feed 流表** —— 采用**推拉结合**
- 普通用户（粉丝 < 1万）：**拉模式**，查关注列表后聚合查询
- 大 V（粉丝 > 1万）：**推模式**，发博时异步写粉丝的 `inbox` 表（Redis ZSet + 持久化兜底）
- 过期时间 7 天，超时降级为拉模式

**3. 分润结算表** —— 最容易出 bug 的地方
```
order(id, user_id, sku_type, sku_id, amount, pay_time)
settlement(id, order_id, author_id, gross, rate, net, status, period)
settlement_log(每一笔变动，用于对账)
```
三条铁律：① 金额用 `DECIMAL(18,2)` 或存分（整数）；② 分润比例**以订单快照为准**，作者后期改等级不影响已下订单；③ T+1 离线跑批生成结算单，**任何实时分润都是坑**。每天凌晨对账，差一分钱都要报警。

**4. 会员权益表** —— 用“权益包”抽象，别硬编码
`member_plan(id, name, price, duration)`, `benefit_def(code, type, quota)`, `user_entitlement(user_id, benefit_code, total_quota, used_quota, expire_at)`
这样下载次数、免广告、课程折扣都是配置项，新增权益不用改代码。微博的 VIP/SVIP/VVIP 和 CSDN 的 VIP/超级会员可以用同一套模型。

**5. 广告位与计费表**
`ad_slot`, `ad_creative`, `ad_delivery(定向规则JSON)`, `impression_log`, `click_log`, `billing_daily`
CPM 按曝光计费、CPC 按点击计费，**点击必须有防刷校验**（IP/设备指纹/停留时长 < 2s 不计费）。

### 四、逐个模块的实现要点（挑难的讲）

#### 1. 发布与编辑器
- 微博侧：富文本 + 多图上传（分片上传 + 秒传 + 图片压缩）+ 话题正则解析 `#xx#` 写入 `topic` 关联表 + @提及写 `mention` 表。
- CSDN 侧：Markdown 编辑器（Monaco / vditor）+ 代码高亮 + LaTeX + 一键粘贴图片上传。**额外要做“文章版本历史”和“草稿自动保存”**，技术作者刚需。
- 公共：发布后走**异步审核流水线**（机器初审 → 疑似违规人工复审 → 通过入库），MQ 驱动，状态机管理。

#### 2. 内容审核与风控（国内上线的硬门槛，优先级比你想的高）
- 文本/图片/视频接第三方：阿里云内容安全、数美或网易易盾，成本几分钱一次。
- 自建策略层：关键词库 + 用户信用分 + 频次限制（新号一天发 20 条直接限流）。
- 合规清单：ICP 备案、公安备案、**算法推荐备案**（有推荐流就必须做）、AI 生成内容标识（深度合成规定）、实名认证（100 万粉前台实名）、个人信息保护合规（隐私政策、注销入口）。**这几项没搞定，功能做得再好也上不了线。**

#### 3. 搜索与 SEO（CSDN 域的生命线）
- ES 建索引：标题权重最高，正文分词用 ik_max_word，标签做 filter，代码块单独 field（可做精确匹配）。
- **查询改写**：用户搜 "java nullpointer" → 同义词扩展 + 拼写纠错 + 历史热门 Query 召回。
- SEO：SSR + 语义化 URL(`/article/12345`) + 结构化数据 JSON-LD + 自动生成 sitemap + 规范标签防重复收录 + 首屏直出 HTML。**技术站的流量 60%+ 来自搜索引擎，这块投入产出比最高。**
- AI 问答（类似"C知道"）：RAG 架构，ES/BM25 召回 + 向量召回混排 → 丢给大模型 → **强制带来源引用链接**（不给引用就是给自己造竞品，把流量送给 AI）。

#### 4. 推荐与热榜
- 阶段一（0–3 个月）：**纯规则**。热榜 = Flink 滑动窗口算 `(点赞*1 + 评论*2 + 收藏*3 + 分享*5) / 时间衰减`，按标签分区出榜。够用，且可解释。
- 阶段二：多路召回（热门/关注/协同过滤/标签）+ GBDT/LR 粗排 + 轻量大模型精排。
- 冷启动：新用户走“注册选标签 + 全站热门兜底”，新内容给固定曝光池，CTR 达标才进大池。
- **埋点先行**：曝光/点击/停留时长/完播四条事件不上线，后续推荐全是瞎的。

#### 5. 社交关系与 IM
- 关注关系用 MySQL 双向表 + Redis 缓存粉丝数，**粉丝数写缓存、读走 DB 定时校对**，不然永远对不齐。
- 私信/群聊：**不要自研长连接协议**，前期直接用腾讯云 IM / 融云（每月几千到几万），验证完模式再考虑自研（Netty + WebSocket + 离线消息存储）。
- 超话/圈子：本质是“话题 + 子社区”，建 `community` 表 + 成员角色 + 签到表，技术上最简单，运营上最重。

#### 6. 直播与打赏
- 直播：接声网/ZEGO/腾讯云直播 SDK，自研推拉流服务器是深坑（CDN、转码、录制、延时、合规全要钱）。
- 打赏/礼物：虚拟币体系（充值 → 金币 → 礼物 → 主播收益 → 提现），**提现要走企业付款到零钱 + 个税代扣 + 提现审核**，这是财务和法务问题不是技术问题。

#### 7. 广告系统（微博域的钱袋子）
最小可行版三层：
1. 广告位管理（开屏/信息流/文末）+ 素材上传 + 排期
2. 定向（地域/设备/标签/关键词）+ 频次控制（每人每天最多看 N 次）
3. 计费与报表（曝光/点击/消耗/CTR）+ 客户自助充值
竞价引擎（oCPM/oCPC）是第二阶段的事，第一阶段人工定价就能收钱。

#### 8. 创作者后台与数据看板
- 看板数据走 ClickHouse 或 ES 聚合，**别打 MySQL**，一个百万粉作者看一次数据就把主库打挂。
- 收益明细必须可追溯到订单级，作者会一笔一笔对账。

### 六、分期路线图（ realistc 版本）

**P0 · 0–3 个月｜最小可用内核（2–4 人）**

→ 目标：**第一笔收入**，验证有人愿意付钱

**P2 · 9–15 个月｜增长引擎（+3–5 人）**
推荐流 + 广告系统基础版 + 问答悬赏 + 等级成长体系 + AI 问答 + 小程序
→ 目标：降低获客成本，提高 ARPU

**P3 · 15 个月后｜护城河**
直播、超话/圈子、企业服务后台、招聘、外包撮合、自建 IM、竞价广告
→ 这些模块**必须在 P1 的收入验证成立之后才值得做**

### 八、五个一定会踩的坑（提前避）

1. **粉丝数/点赞数对不齐**——所有计数器走异步 + 定期校对任务，前端显示接受最终一致。
2. **分润算错钱**——金额用整数分、比例用订单快照、每日对账、有审计日志。错一次就失去创作者信任。
3. **SEO 被 SPA 毁掉**——Next.js SSR + 服务端路由，爬虫拿不到 HTML 等于没有流量。
4. **被搜索引擎/AI 白嫖**——做好 robots、频率限制、内容分级（免费摘要 + 付费全文），否则你的内容是给大模型训练用的。
5. **合规后置**——算法备案、实名、AI 标识，这三项要在设计期就留字段和流程，事后补要改表改架构。

### 二、模块功能逐项对比

#### 1. 内容生产与消费
- **微博**：发布框（文字上限提升至万字级，但主流仍是短内容）、多图、短视频、直播、头条文章、投票、抽奖、话题 #标签#、@提及、微博故事（24h 消失）。消费端有推荐流、关注流、视频沉浸流、同城流。2025 年 7 月首页默认从“关注流”切到“推荐流”，形成“社交+兴趣+热点”三引擎，视频分发从播放量改为**观看时长**主导。
- **CSDN**：博客编辑器（Markdown/代码高亮/公式）、付费专栏、付费资源上传、VIP 可见文章、问答区（提问-悬赏-采纳）、论坛、直播、学生专区（竞赛/题库）、热榜。内容天然围绕“解决问题”组织，生命周期以年计。

> 区别本质：微博的内容价值随时间**衰减**（过期的热搜没人看），CSDN 的内容价值随时间**累积**（一篇部署教程三年后还能被搜到）。这直接决定了两者的变现逻辑。

#### 2. 发现与检索
- **微博**：热搜榜（社会/娱乐/生活等分榜）、热搜落地页（AI 归纳多方立场）、智搜（接入 DeepSeek，支持多轮对话）、发现广场、超话社区。
- **CSDN**：站内搜索 + 标签体系、“C知道”AI 问答、桌面服务卡片、热榜。它的“发现”很弱，“检索”极强——用户多是带着明确问题进来的。

#### 3. 身份与成长体系
- **微博**：普通用户 → 橙 V（个人）/蓝 V（机构）→ 金橙 V（深度阅读纳入评估）；配套微博会员 VIP/SVIP/VVIP（装扮、置顶、免广告、关注上限等身份型权益）；100 万粉以上自媒体需前台实名展示，未实名在推荐流、分成、打赏上受限。
- **CSDN**：原力等级 Lv1–Lv9、博客专家认证、认证讲师、实名认证。**等级直接挂钩钱**：付费资源分成、广告分成比例都随等级提升（Lv8–Lv9 可到 90%）。这是 CSDN 最精妙的设计——把成长体系和供给激励绑在一起。

#### 4. 社交与社区
- **微博**：转评赞、私信群聊、超话（签到/等级/名人堂）、微群、微公益、直播连麦、AI 自主社交“硅基茶水间”。社交密度高，能沉淀粉丝资产。
- **CSDN**：评论、点赞、收藏、关注博主、问答悬赏、打赏。几乎没有私域社交，**它不希望你留在站内聊天，只希望你找到答案后去用**。

#### 5. 创作者工具
- **微博**：V 创作中心（AI 图文生成→视频剪辑全链路）、AIGC 助手、高光识别/配文/封面生成、商业撮合后台、数据看板、商业处置申诉。
- **CSDN**：创作中心（收益明细/分润阶梯）、AI 编程 InsCode、GitCode 代码托管、社区镜像市场、GEO/SEO 检测工具（已做成付费会员权益）。

#### 6. 交易与闭环
- **微博**：微博小店、直播带货（边看边买）、V+ 付费圈子/付费订阅、粉丝通/粉丝头条投放后台、数据 API。

### 四、把两者放在一起看的三个洞察

**1. 变现对象不同：微博赚广告主的钱，CSDN 赚用户的钱 + 企业的钱。**
微博的用户是“被卖给广告主的商品”，所以功能设计一切为了停留和曝光；CSDN 的用户是“付费客户”，所以功能设计一切为了快速找到答案并愿意付钱。同一个“搜索”模块，在微博是辅助消费，在 CSDN 是主要收银台。

**2.  monetization 效率 vs. monetization 深度。**
微博是浅而广：5.6 亿人每人贡献几块钱广告价值；CSDN 是深而窄：800 万活跃里，愿意为一份部署教程付 99 元的人，ARPU 可以很高。这也解释了为什么微博拼命做视频、做时长，CSDN 拼命做等级、做专栏、做企业服务。

**3. 可互相借鉴的地方（如果你是做产品的）**
- 微博可以向 CSDN 学**分层付费**：现在微博会员只卖装扮和功能，几乎没有“内容型付费”的深度（V+ 一直做不大），而它的垂直领域（汽车、数码、财经）其实有很强的知识付费潜力。
- CSDN 可以向微博学**社交沉淀与冷启动分发**：技术内容的传播基本靠搜索，没有裂变机制，导致新作者起号极慢；问答 + 悬赏 + 圈子的组合如果做得更“社区化”，能显著降低获客成本。

### 一、先把两个概念分开

- **平台**：用户在哪用、内容/产品长什么样（承载方），比如 iOS、微信小程序、抖音、淘宝、Steam。
- **分发渠道**：用户怎么找到并拿到它（触达路径），比如 App Store 搜索、应用商店推荐位、KOL 投放、地推扫码、代理商。

同一个平台里可以有很多渠道；同一个产品也可以走多个平台。

### 二、按产品类型对号入座

**1）移动 App**
- 平台：iOS / Android / 鸿蒙 HarmonyOS NEXT
- 渠道：App Store、华为/小米/OPPO/vivo/荣耀应用商店、应用宝、TapTap（游戏）、官网 APK、小程序转 App、运营商预装
- 要点：国内安卓渠道普遍有分成（游戏常见 5:5，非游戏多为免费或低分成）；iOS 统一 15%–30%；鸿蒙正在建自己的分发与支付体系，要单独适配。

**2）游戏**
- 平台：手游端 + PC（Steam/Epic/WeGame）+ 主机（Switch/PS/Xbox）
- 渠道：上述商店 + 买量（巨量引擎、腾讯广告、快手磁力）+ 社区（TapTap、好游快爆、B站）+ 公会/联运代理
- 要点：国内上线需要版号、软著、实名认证与防沉迷接入，这是硬门槛，比选渠道更优先。

**3）内容/自媒体**
- 平台：抖音、快手、小红书、B站、视频号、公众号、微博、知乎、今日头条
- 渠道：推荐流（主）、搜索、关注页、私域社群、跨平台搬运、MCN/达人分销
- 要点：各平台调性和审核尺度差异极大，建议“一主多辅”，别平均用力。

**4）电商/实物商品**
- 平台：淘宝天猫、京东、拼多多、抖音电商、快手小店、小红书、得物、微信小店
- 渠道：搜索流量、直播自播/达播、短视频挂车、分销团长、私域复购、线下门店/O2O
- 要点：抖音偏“货找人”（内容驱动），淘京偏“人找货”（搜索驱动），打法完全不同。

**5）SaaS / ToB 软件**
- 平台：Web + 钉钉/企微/飞书工作台 + 云市场（阿里云、华为云市场）
- 渠道：SEO/内容、直销、代理商/ISV、行业展会、招投标、老客户转介绍
- 要点：ToB 的“渠道”本质是信任链，代理商体系和交付能力比流量更重要。

### 三、选渠道时通用的四个判断维度

| 维度 | 问什么 |
|---|---|
| 用户重合度 | 你的目标用户真在这个平台上活跃吗？别凭感觉 |
| 获取成本 | CAC 多少、回本周期多长，能不能算清账 |
| 分成与规则 | 抽成比例、结算周期、是否强制用平台支付、下架风险 |
| 可控性 | 流量是平台的还是你自己的？能不能沉淀到私域 |

一个实用原则：**先用 1–2 个渠道跑通转化模型，再横向扩量**。多数项目死在同时铺五个渠道、哪个都没跑透。
