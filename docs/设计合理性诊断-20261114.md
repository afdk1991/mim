# 设计合理性诊断（2026-11-14）

> 对象：`F:\合并项目\Mim` 全仓（`apps/web` / `services/mim-api` / `packages/*` / `scripts/*`）
> 方法：静态盘点（文件行数、路由表、DDL 表名、门禁脚本断言），不含主观偏好。
> 结论一句话：**不是「功能不够」，而是「同一件事被建模 2–3 次」+「单个文件把多职责焊在一起」**。

## 1. P0：域模型重复（成本最高）

### 1.1 交易域有三套并行模型

| 商品线 | 商品表 | 订单表 | 结算 / 履约 |
|---|---|---|---|
| 数字功能模块 | `modules` + `module_prices` + `module_categories` | `module_orders` | `cart_items` → `entitlements` + `entitlement_events` |
| 实物 / 卡密（社区商城） | `shop_products` + `shop_card_keys` | `shop_orders` | `wallets` 余额 + `coupons` / `coupon_redemptions`，履约 `shipments` / `after_sales` |
| 付费资产 | `paid_assets` | `asset_purchases` | `payment_intents` / `payment_events` |

**为什么不合理**：

- 三套订单表意味着「我的订单」「退款」「对账」「GMV 统计」都要写三段并手工合并；个人中心页面事实上已经在做三源聚合。
- 购物车只有模块线有（`cart_items`），实物线没有购物车模型，只能用「直接下单」凑。
- 支付抽象只覆盖第三套（`payment_intents`），模块订单与商城订单各走各的余额 / 权益路径，接真实支付通道时会出现三种对接方式。

**建议改法**（一次建模、分线用 `kind` 区分）：

```
products(id, kind ENUM('module','physical','card','asset'), title, price_cents, stock, meta_json)
order_items(order_id, product_id, qty, unit_price_cents)
orders(id, user_id, status, total_cents, channel ENUM('cart','buy_now'), created_at)
payments(order_id, provider, status, amount_cents, refunded_cents)
fulfillments(order_id, type ENUM('entitlement','shipment','card_key'), payload_json)
```

模块的 `entitlements` 保留为「数字交付」结果，不再兼任订单；`shop_card_keys` 降为 `fulfillments.payload_json` 的一种。
迁移方式：新增上述表 → 回填三套历史数据（`module_orders` / `shop_orders` / `asset_purchases`）→ 旧接口读视图保持 100% 兼容 → 逐条切换写入 → 旧表冻结只读 → 下线。

### 1.2 内容域有两套同构模型

- 社区：`community_boards` / `community_threads` / `community_posts` / `community_board_memberships` / `community_thread_likes` / `community_purchases` / `community_poll_*`
- 圈子：`circles` / `circle_members` / `circle_posts` / `circle_notices`

**为什么不合理**：两套帖子结构几乎同构（标题 + 正文 + 作者 + 时间 + 可见性），但圈子没有点赞 / 举报 / 收藏 / 评分，社区有的能力圈子全缺。统一搜索要分别查两张表（`Search.tsx` 的五来源聚合里，社区与圈子是两条独立分支）。

**建议改法**：`topics(container_type='board'|'circle', container_id, ...)` + `posts(topic_id, ...)` + `memberships(container_type, container_id, user_id, role)` + `reactions(target_type, target_id, kind)`。圈子退化为 `container_type='circle'` 的一种容器，`circle_notices` 并入 `topics(kind='notice')`。

### 1.3 消息域有两套

- IM：`im_conversations` / `im_conversation_members` / `im_messages`
- 私信：`direct_messages`

**建议**：`conversations(type='dm'|'group'|'circle')` 单模型；私信是 `type='dm'` 的会话，不单独开表。

### 1.4 导航域有三套入口目录

| 来源 | 形态 | 消费方 |
|---|---|---|
| `nav_links` 表 | 运行时可编辑的站外链接 | `/api/v1/navigation` → `Navigation.tsx` |
| `site_module_items` 表 | 44 入口的运行期业务条目 | `/api/v1/sites/*` → `Sites.tsx` |
| `packages/core-domain/src/siteModules.json` | 静态契约（入口 / 业务域 / 占位） | `/api/v1/entries/*` + `/api/v1/sites/*` 同时读 |

**为什么不合理**：`entries.ts` 与 `sites.ts` 两个路由读同一份 JSON，只是切片角度不同；`nav_links` 又是第三种「链接」。三个页面（导航站 / 入口配置清单 / 搜索来源之一）各自维护一份，新增一个入口要改三处。

**建议**：`entries(id, kind ENUM('external','internal','module'), key, title, url, domain, status, config_json)` 单表；`siteModules.json` 降级为启动期 seed；`entries` 与 `sites` 两个路由收敛为一个 `/api/v1/directory`（保留旧路径为别名一个发布周期）。

## 2. P1：结构膨胀

### 2.1 超大文件（本轮实测行数）

| 行数 | 文件 | 实际承担 |
|---|---|---|
| 2449 | `apps/web/src/api.ts` | 全站 SDK：认证 / 商城 / 社区 / 漫剧 / IM / 资金 / 管理 |
| 1761 | `services/mim-api/src/routes/catalog.ts` | 分类 + 模块 + 定价 + 订单 + 权益 + 搜索 |
| 1681 | `apps/web/src/views/ComicWorkbench.tsx` | 项目 / 角色 / 分镜 / 任务 / 资产 / 导出 |
| 1624 | `apps/web/src/views/Store.tsx` | 目录 + 筛选 + 详情 + 图形（G6/ECharts 动态加载）+ 权益 |
| 1417 | `services/mim-api/src/capabilities.ts` | 能力矩阵单一真源 |
| 1352 | `services/mim-api/src/routes/comic.ts` | 项目 + 分镜 + 生成 + 导出 + 放映 |
| 1153 | `services/mim-api/src/routes/community.ts` | 论坛 + 付费阅读 + VIP + 钱包 + 商城 + 推广 |
| 1068 | `apps/web/src/views/Chat.tsx` | 会话 + 消息 + 视频通话 + 附件 |
| 1036 | `apps/web/src/views/Community.tsx` | 五个独立业务页塞进一个视图 |
| 865 | `services/mim-api/src/db.ts` | 连接 + 迁移 + 种子 + 事务 |

**改法**：`api.ts` 按域拆 `client/{catalog,community,comic,im,finance,admin}.ts`；`community.ts` 按 tab 拆成 `community/{forum,vip,wallet,shop,referral}.ts`；视图按区块拆组件（`Store/`、`Community/` 目录）。**不做一次性重写**，按域逐个搬，每搬一个跑一遍现有测试。

### 2.2 视图与路由不是一一对应

21 个视图对 16 个路由视图 + 4 个 `hidden`。当前「合并入口」的实现是给 `navDefaults` 加 `hidden: true`，靠字段隐藏，而不是让页面成为子路由。后果：`/products`、`/circles`、`/entry-catalog`、`/deployments` 是「隐藏的一级入口」，面包屑与深链接语义模糊（点进去侧栏无高亮）。

**改法**：子路由化 `/marketplace/list`、`/community/circles`、`/navigation/entries`、`/releases/deployments`，`hidden` 字段随之退役；`ChatPreview.tsx` / `ComicStudio.tsx`（壳）/ `PageBlocks.tsx` 若确为中间层，应移入 `components/` 而不是留在 `views/`。

### 2.3 门禁是「源码字符串断言」，脆弱且会骗人

`scripts/verify-site-modules.mjs` 要求 `App.tsx` 里出现 `view: 'sites'`、`<Sites`、`onOpenView` 等字面量；`verify-deployments.mjs` D39 要求 `App.tsx` 含 `<Deployments`。这是**实现细节断言**：改名、抽组件、换写法都会误报；而只要字符串还在、行为其实坏了，它又会误判为通过。

**改法**：保留少量「清单完整性」断言，其余替换为 (a) OpenAPI schema 契约测试（响应字段 / 状态码）、(b) Playwright 浏览器用例断言 DOM 行为（侧栏项数、路由高亮、下单流程）。现成基础设施已有（`verify-auth-gate` 就带 `--live` 浏览器实测 56/56）。

## 3. P2：治理与口径

1. **版本语义**：`0.0.10` 里塞了 16 个一级模块，semver 只增末位，无法表达「域重构」这类破坏性变更。建议这次重构开 `0.1.0` 里程碑，`CHANGELOG` 按域列迁移项。
2. **部署矩阵膨胀**：11 个平台里 4 个是「从未真实部署」的候选（gitlab / bitbucket / azure-swa / render），生产主机 `mim.mixm.top` 自本轮之前就 443 拒绝 + 回源 521 + CI 私钥被拒。矩阵的真实能力是「3 个静态镜像可用 + 1 个生产长期瘫痪」，但文档读起来像「11 平台全绿」。建议矩阵收敛为「生产 1 + 镜像 3 + 归档 N」，并明确写「镜像 ≠ 生产」。
3. **命名交叠**：商城 / 社区商城 / 商品列表 / 商业化中台 —— 本轮已把社区内商品线改称「社区商城」，但「商品列表」仍是商城视图、`商业化中台` 里也有商品与资产，前台读到第 4 个「商品」概念时需要解释。建议在 IA 层把「商品」限定为模块商城的商品，实物线一律叫「社区商城商品」。

## 4. 建议执行顺序（四期）

| 期 | 范围 | 工期估算 | 风险 | 验收 |
|---|---|---|---|---|
| **P0-A** | 交易域统一（§1.1）：新表 + 回填 + 兼容视图 + 双写 | 2–3 周 | 高（钱相关），必须每步可取回滚 | 三套旧接口返回逐字段一致；下单 / 退款 / 对账各跑通；GMV 与旧口径差额 0 |
| **P0-B** | 内容域 + 消息域统一（§1.2 / §1.3） | 2 周 | 中（数据迁移） | 帖子 / 圈子读写互通；搜索单次查询覆盖两类容器 |
| **P1-A** | 前端 IA 子路由 + 巨型文件拆分（§2.1 / §2.2） | 2 周 | 中（视觉回归） | `/marketplace/list` 等子路由直达 + 侧栏高亮正确；`hidden` 字段删除 |
| **P1-B** | 门禁替换（§2.3） | 1 周 | 低 | 字符串断言 ≤ 5 条；行为用例覆盖 16 个一级入口 |

不建议做的两件事：

- **不要把两个商城的 UI 合并**。数字模块解锁与实物发货是两套履约，只统一数据模型，不统一页面。
- **不要一次性重写前端**。现有视图能跑、能卖，按域搬运即可，避免「重构完功能全丢」。

## 5. 判断边界（避免过度重构）

若项目目标是「能跑、能卖、能部署」，当前架构是可用的；上表是**扩展成本**问题，不是「坏掉」问题。真正会立刻咬人的只有两处：

1. 交易域三套订单（§1.1）——接真实支付、做退款、算 GMV 时必然重复劳动；
2. 门禁靠字符串断言（§2.3）——本轮每次「合并入口 / 删分组 / 改名」都要跟着改断言，稍有遗忘就是假绿。

其余（内容双轨、导航三份、巨型文件）是维护成本递增，能靠分批搬运解决，不必停机式重构。
