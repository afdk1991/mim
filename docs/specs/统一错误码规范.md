| 项 | 值 |

> 全端共用一套错误码。服务端 `code` 字段与前端 `ErrCode` 联合类型**必须一一对应**，任一侧新增码值都必须同步另一侧并升版本。

## 1. 三条铁律

### 铁律一：HTTP 状态码与 `code` 必须一致

- 服务端同时下发二者（`server/src/main.js:52-56`），任一不一致即为缺陷。
- 前端优先取响应体 `code`，取不到（或不是合法 `ErrCode`）才按 HTTP 状态码反推（`src/core/http.ts:91-100`）。
- 后果举例：若返回 `409` 却带 `code:'bad_request'`，前端会把它当成「参数错误」而非「冲突」，重试策略与用户文案全部漂移（`server/src/errors.js:4-6` 注释明确此点）。

### 铁律二：PG 原始错误不得外泄

- 所有未捕获异常统一经 `toApiError()` 收敛（`server/src/errors.js:47-57`）。
- `PG_TO_CODE` 只映射已知码；未知异常一律收敛为 `server / 500`，原始错误仅保留在 `ApiError.cause` 中，且仅服务端打日志，不下发（`server/src/main.js:54`）。
- 响应体只允许 `{ error: { code, message } }`，禁止出现 `detail`、`constraint`、`where`、`stack`、`sqlstate` 等 PG 原生字段。

### 铁律三：`schema` 错误用于缺列降级，不是普通报错

- 缺列提示文案刻意与 PostgREST 完全一致：`Could not find the '<col>' column of '<table>'`（`server/src/errors.js:26-29`）。
- 前端 `writeWithFallback` 解析该文案取出列名，把该列从请求体中剔除后重试，最多 `MAX_DROP_ROUNDS` 轮（`src/data/sync.ts:60-84`）。
- 因此：**任何改动这条文案格式的动作都是破坏性变更**，会让线上库结构落后时前端无法自动降级。

## 2. 全端共用错误码表

| code | HTTP | 服务端来源（`errors.js`） | 前端 `ErrCode`（`result.ts`） | 用户可见文案建议 | 可重试 | 典型触发场景 |
| --- | --- | --- | --- | --- | --- | --- |
| `bad_request` | 400 | `badRequest()`（`errors.js:18`） | `bad_request` | 请求参数不合法，请检查后重试 | 否 | 请求体非 JSON（`main.js:71`）、请求体过大（`main.js:63`）、`eq` 参数格式错误（`rest.js:160`）、数值列收到非数值（`rest.js:169`）、RPC 参数越界（`rpc.js:29/41`）、订单状态非法（`rpc.js:661`）、入账类型非 `recharge`/`income`（`rpc.js:631`） |
| `no_auth` | 401 | `noAuth()`（`errors.js:19`） | `no_auth` | 登录已失效，请重新登录 | 否（需重新登录） | 无令牌（`auth.js:175`）、令牌签名不符 / 已过期 / 已被吊销（`auth.js:177-178`）、账号不存在（`auth.js:157`）、用户名或密码错误（`auth.js:245/247`） |
| `forbidden` | 403 | `forbidden()`（`errors.js:20`） | `forbidden` | 没有操作权限 | 否 | 表禁写（`rest.js:125`）、只能操作自己的资料（`rest.js:315/351`）、只能操作自己的数据（`rest.js:374`）、仅管理员可执行（`auth.js:189`）、缺少权限点（`auth.js:192`）、订单号已被他人占用（`rpc.js:671`）、账号被停用（`auth.js:158/248`） |
| `not_found` | 404 | `notFound()`（`errors.js:21`） | `not_found` | 资源不存在或已被删除 | 否 | 未知接口（`main.js:93/221`）、单条未命中（`rest.js:373`）、秒杀场次不存在（`rpc.js:83`）、订单不存在（`rpc.js:262`）、券码不存在（`rpc.js:527`）、该日期未开放售卖（`rpc.js:219`） |
| `conflict` | 409 | `conflict()`（`errors.js:22`） | `conflict` | 操作冲突，请刷新后重试 | 否（需刷新后由用户重决） | 用户名已被占用（`auth.js:208`）、唯一约束冲突（`rest.js:378`）、库存不足 / 已抢完（`rpc.js:126`）、余票不足（`rpc.js:220/226`）、余额不足（`rpc.js:618`）、今天已经签到过了（`rpc.js:828`）、券码已被核销（`rpc.js:528/540`）、已有管理员（`rpc.js:747`）、秒杀未开始 / 已结束 / 已关闭（`rpc.js:84/87/88`） |
| `busy` | 503 | `busy()`（`errors.js:23`） | `busy` | 系统繁忙，请稍后重试 | 是（退避重试） | PG 序列化失败 `40001`、死锁 `40P01`、连接过多 `53300`（`errors.js:41-43`）；设备网关未配置 / 下发失败 / 超时（`iot.js:152/170/172`） |
| `schema` | 400 | `schemaError()`（`errors.js:24`）、`missingColumn()`（`errors.js:27`） | `schema` | 线上数据结构尚未就绪，已保存在本机 | 否（前端按缺列降级后重试有限轮） | 表未开放访问（`rest.js:89`）、表不存在（未迁移，`rest.js:98`）、表缺归属列配置（`rest.js:102`）、列不存在（`rest.js:111/163/192`）、未开放的 RPC 名（`rpc.js:956`）、PG `42P01` / `42703`（`errors.js:39-40`） |
| `server` | 500 | `toApiError()` 兜底（`errors.js:56`） | `server` | 服务端异常，请稍后重试 | 是（读可重试；写需先查状态再决定） | 任何未被 `ApiError` / `PG_TO_CODE` 覆盖的异常 |
| `offline` | 无（网络层，`status=0`） | 无服务端对应（前端本地判定） | `offline` | 后端未配置或网络不可达，已保存在本机 | 是 | 后端未配置（`http.ts:112-114`）、请求超时 / DNS 不可达（`http.ts:72-79`） |
| `unknown` | 视情况 | 无直接对应（前端兜底） | `unknown` | 操作失败，请稍后重试 | 视情况 | 响应体无合法 `code` 且状态码未落入 `statusToCode` 映射（`http.ts:38-47`） |

> `offline` 与 `unknown` 为前端专有码，服务端**不得**主动下发；二者存在于 `ErrCode` 是为了让前端在「没打到服务端」时有统一表达。

## 3. PG 错误码映射表（`PG_TO_CODE`）

来源：`server/src/errors.js:31-44`。映射结果为 `code`，HTTP 状态码随之确定。

| PG SQLSTATE | 含义 | 映射 code | HTTP |
| --- | --- | --- | --- |
| `23505` | unique_violation | `conflict` | 409 |
| `23503` | foreign_key_violation | `bad_request` | 400 |
| `23502` | not_null_violation | `bad_request` | 400 |
| `23514` | check_violation | `bad_request` | 400 |
| `22P02` | invalid_text_representation | `bad_request` | 400 |
| `22001` | string_data_right_truncation | `bad_request` | 400 |
| `22003` | numeric_value_out_of_range | `bad_request` | 400 |
| `42P01` | undefined_table | `schema` | 400 |
| `42703` | undefined_column | `schema` | 400 |
| `40001` | serialization_failure | `busy` | 503 |
| `40P01` | deadlock_detected | `busy` | 503 |
| `53300` | too_many_connections | `busy` | 503 |
| 其他 / 无 code | — | `server` | 500 |

补充说明：

- REST 写路径另有一份局部映射 `mapWriteError`（`server/src/rest.js:377-384`），覆盖 `23505 / 23503 / 23502 / 23514 / 42703`，文案更具体（例如带上缺字段名）。其余仍交由 `toApiError` 兜底。
- 事务内**不依赖**「唯一冲突报错再回滚」：`on conflict do nothing` 优先于 `try/catch 23505`，因为 PG 语句报错会让整个事务进入中止态（后续语句一律 `25P02`），catch 也救不回来（`server/src/rpc.js:477-481`）。

## 4. 前端行为约定

### 4.1 状态码反推表（`statusToCode`）

来源：`src/core/http.ts:38-47`。仅在响应体未给出合法 `code` 时启用。

| HTTP | 反推 code |
| --- | --- |
| 401 | `no_auth` |
| 403 | `forbidden` |
| 404 | `not_found` |
| 409 | `conflict` |
| 400 / 422 | `bad_request` |
| 429 / 503 | `busy` |
| >= 500 | `server` |
| 其他 | `unknown` |

### 4.2 重试策略

| 规则 | 位置 |
| --- | --- |
| 读（GET）默认重试 1 次，写（POST/PATCH/DELETE）默认不重试 | `src/core/http.ts:115`、`src/core/http.ts:132-138` |
| `no_auth` / `forbidden` / `bad_request` 直接返回不重试 | `src/core/http.ts:121-123` |
| 默认超时 10s | `src/core/http.ts:16` |

### 4.3 文案唯一真源

`ERR_CN`（`src/core/result.ts:68-79`）是错误码到中文文案的唯一映射，页面不得各自翻译。服务端下发 `message` 时优先展示服务端文案（`src/core/http.ts:96-99`）。

| code | `ERR_CN` 文案 |
| --- | --- |
| `offline` | 后端未配置或网络不可达，已保存在本机 |
| `no_auth` | 请先登录 |
| `forbidden` | 没有操作权限 |
| `not_found` | 资源不存在或已被删除 |
| `conflict` | 操作冲突，请刷新后重试 |
| `bad_request` | 请求参数不合法 |
| `schema` | 线上数据结构尚未就绪，已保存在本机 |
| `busy` | 系统繁忙，请稍后重试 |
| `server` | 服务端异常，请稍后重试 |
| `unknown` | 操作失败，请稍后重试 |

## 5. 已知不一致（记录，不在本次修改）

| 位置 | 现象 | 影响 | 建议 |
| --- | --- | --- | --- |
| `server/src/iot.js:35-37` | 设备域错误码为数字 `30101 / 30102 / 30103`，**不在** `ErrCode` 联合类型中 | 前端 `isErrCode` 判定失败，回落到 `statusToCode` 按 HTTP 反推（30101→`not_found`、30102→`conflict`、30103→`forbidden`）；`message` 仍能正确展示，但精细化分类丢失 | 二选一：① 改用 `not_found`/`conflict`/`forbidden` 并在 `message` 携带设备语义；② 扩展 `ErrCode` 与 `ERR_CN` 并同步本规范 |
| `src/core/http.ts:43` | `422` 也反推为 `bad_request`，但服务端从不返回 422 | 无实际影响，属冗余分支 | 保留（防御性） |

## 6. 新增错误码流程

1. 服务端在 `server/src/errors.js` 增加构造器并确定 HTTP 状态码。
2. 前端在 `src/core/result.ts` 的 `ErrCode`、`isErrCode`、`ERR_CN` 三处同步（`ErrCode` 与 `isErrCode` 必须同时改，否则判定与类型不一致）。
3. 在本规范 §2 表格补行，升版本号。
4. 在 `docs/specs/API规范.md` 相关接口备注中补充触发场景。
