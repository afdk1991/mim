## 1. 账号模型

### 1.1 三张表的关系

| 表 | 作用 | 是否可被 REST 访问 | 关键列 |
| --- | --- | --- | --- |
| `users` | 账号真源（凭据 + 状态） | **否，永不在白名单**（`server/src/rest.js:5-6`） | `id`、`username`、`password_hash`、`name`、`emoji`、`status`（`active` / `disabled`）、`created_at`、`updated_at`（`0001_iam.sql:22-31`） |
| `profiles` | 公开资料 | 是（`read:public` / `write:self`） | `id`（= users.id）、`username`、`name`、`emoji`、`color`、`bio`、`followers`、`following`、`verified`（`0001_iam.sql:36-47`） |
| `app_users` | 历史 CloudBase `uid` 对照登记表 | 是（`read:owner` / `write:none`） | `user_id`、`uid`、`username`、`source`（`self` / `cloudbase` / `import`）（`0001_iam.sql:52-59`） |

设计要点：账号表与资料表必须分离。`users` 不在 REST 白名单，因此 `select=*` 不可能把 `password_hash` 带出去；公开资料一律走 `profiles`（`server/src/rest.js:5-6`、`0001_iam.sql:34-35`）。

### 1.2 密码

| 项 | 值 | 位置 |
| --- | --- | --- |
| 算法 | `crypto.scrypt`，N=16384、r=8、p=1、key 长度 64 字节 | `server/src/auth.js:18-21` |
| 盐 | 每用户 16 字节随机 | `server/src/auth.js:34` |
| 存储格式 | `scrypt$N$r$p$saltHex$hashHex` | `server/src/auth.js:36` |
| 校验 | `timingSafeEqual`，长度不等直接失败 | `server/src/auth.js:52-57` |
| 侧信道防护 | 用户不存在时对 `DUMMY_HASH` 做一次等价运算，避免「用户名不存在」被时序区分 | `server/src/auth.js:59-60`、`server/src/auth.js:243-246` |
| 强度 | 6~128 位（注册时校验） | `server/src/auth.js:205` |

## 2. 账号生命周期

### 2.1 注册

| 步骤 | 说明 | 位置 |
| --- | --- | --- |
| 1 | 用户名校验 `/^[\w.@+-]{2,64}$/u`，密码 6~128 位 | `server/src/auth.js:199-205` |
| 2 | 用户名占用检查 → `409 conflict`「用户名已被占用」 | `server/src/auth.js:207-208` |
| 3 | 写 `users`（密码哈希） | `server/src/auth.js:211-215` |
| 4 | 同步建 `profiles` 行 | `server/src/auth.js:216-220` |
| 5 | 授予默认角色 `user` | `server/src/auth.js:221-226` |
| 6 | 同步建 `app_users` 兼容行（`uid = 'u_' + id 去横线`） | `server/src/auth.js:227-231` |
| 7 | 签发令牌，返回 `{ token, user }`，HTTP 201 | `server/src/auth.js:232`、`server/src/main.js:108` |

### 2.2 登录

| 步骤 | 说明 | 位置 |
| --- | --- | --- |
| 1 | 用户名 / 密码非空校验，否则 `400 bad_request` | `server/src/auth.js:238` |
| 2 | 查 `users`；不存在时对 `DUMMY_HASH` 做等价运算后抛 `401 no_auth`「用户名或密码错误」 | `server/src/auth.js:239-246` |
| 3 | 校验密码，失败同上（不区分「用户名错」与「密码错」） | `server/src/auth.js:247` |
| 4 | `status !== 'active'` → `403 forbidden`「账号已被停用」 | `server/src/auth.js:248` |
| 5 | 签发令牌，返回 `{ token, user }`，HTTP 200 | `server/src/auth.js:249` |

### 2.3 登出

| 行为 | 说明 | 位置 |
| --- | --- | --- |
| 服务端 | 按当前令牌的 `jti` 写入 `token_revocations`（`on conflict do nothing`），`expires_at` 取令牌 `exp` | `server/src/auth.js:98-106` |
| 鉴权时 | 每次请求查 `token_revocations` 命中即 `401 no_auth`「令牌已失效，请重新登录」 | `server/src/auth.js:92-96`、`server/src/auth.js:178` |
| 前端 | `signOut()` 先调 `/api/auth/logout`，**服务端失败也照常清本地会话**（否则用户永远退不出去） | `src/data/session.ts:123-130` |
| 端点 | `POST /api/auth/logout`；无有效令牌时静默返回 `true` | `server/src/main.js:111-115` |

> 吊销表使得「登出」对已签发令牌真正生效——无状态令牌否则登出后仍可继续使用（`server/src/auth.js:7-8`）。

### 2.4 注销（账号删除）

**当前未实现**。全仓无注销端点、无 `users` 删除逻辑、无数据清理流程。

| Phase 2 建议 | 内容 |
| --- | --- |
| 端点 | `DELETE /api/auth/me`（需密码二次确认） |
| 语义 | 软删优先：`users.status = 'disabled'` + 令牌全量吊销（`token_revocations` 按 uid 批量写） |
| 数据 | 明确「内容保留但匿名化」还是「级联删除」（现有外键多为 `on delete cascade`，直接删会连带清空该用户全部动态 / 订单 / 流水，须先定策略） |
| 合规 | 与个人信息安全规范要求的删除流程对齐，并落审计 |

## 3. 令牌：签发、校验、轮换

### 3.1 结构

| 项 | 值 | 位置 |
| --- | --- | --- |
| 算法 | HMAC-SHA256 自签（**不是 JWT 库，无第三方依赖**） | `server/src/auth.js:6`、`server/src/auth.js:71` |
| 形态 | `base64url(payload).base64url(sig)` | `server/src/auth.js:72` |
| payload | `{ uid, jti, iat, exp }` | `server/src/auth.js:69` |
| 密钥 | `process.env.JWT_SECRET`，缺省回落到开发用 `mim-dev-secret-change-me` 并打印告警 | `server/src/auth.js:23-29` |
| 有效期 | `TOKEN_TTL_MS`，默认 7 天 | `server/src/auth.js:25` |
| `jti` | 16 字节随机 hex，吊销表主键 | `server/src/auth.js:69`、`0001_iam.sql:112-117` |

### 3.2 校验链

| 步骤 | 失败结果 | 位置 |
| --- | --- | --- |
| 取令牌：`Authorization: Bearer` 优先，回落 `X-Mim-Token` | 无 → `401 no_auth` | `server/src/auth.js:174-175` |
| 重算 HMAC 并 `timingSafeEqual` 比对 | 不符 → `401`「登录已失效，请重新登录」 | `server/src/auth.js:79-81`、`server/src/auth.js:177` |
| 解析 payload，`uid` 必须是非空字符串 | 不符 → `401` | `server/src/auth.js:84` |
| `exp < now` | 过期 → `401` | `server/src/auth.js:85` |
| 查 `token_revocations` | 已吊销 → `401`「令牌已失效，请重新登录」 | `server/src/auth.js:178` |
| 装载身份（`loadIdentity`） | 账号不存在 → `401`；`status !== 'active'` → `403` | `server/src/auth.js:157-158` |

### 3.3 轮换建议（当前未实现）

| 项 | 现状 | 建议 |
| --- | --- | --- |
| 刷新令牌（refresh token） | 无。令牌过期后必须重新登录 | 增加长期 refresh token + 短期 access token |
| 滑动续期 | 无。有效期固定 7 天 | 活跃用户临近过期时静默换新令牌 |
| 密钥轮换 | 手动改 `JWT_SECRET` 会让**所有**已签发令牌立即失效 | 支持 `JWT_SECRET_PREVIOUS` 双密钥验签窗口 |
| 吊销表清理 | 依赖 `expires_at` 索引，但**无清理任务** | 定时删除 `expires_at < now()` 的行（表会随登出无限增长） |
| 生产告警 | 未设 `JWT_SECRET` 仅打印 warn，服务照常启动 | 生产环境（`NODE_ENV=production`）应拒绝启动 |

## 4. 多端登录策略（现状）

| 项 | 现状 | 说明 |
| --- | --- | --- |
| 并发令牌数 | **无上限**。同一账号可在任意多个端同时登录并各自持有独立令牌 | 无会话表 / 设备表约束 |
| 会话可见性 | 无。服务端无法枚举「该账号当前有哪些在线端」 | 缺 sessions 表 |
| 单点登出 | **否**。登出只吊销当前请求的 `jti`，其他端令牌继续有效 | `server/src/auth.js:98-106` |
| 强制下线 | 只能靠改 `users.status = 'disabled'`（下次装载身份时 `403`），无法按端粒度 | `server/src/auth.js:158` |
| 端标识 | 无。令牌 payload 不含端信息 | `server/src/auth.js:69` |

Phase 2 建议：增加 `user_sessions`（`jti`、`uid`、`device`、UA、IP、`last_seen_at`），支撑「多端管理 / 踢下线 / 异常登录提醒」。

## 5. RBAC 模型

### 5.1 四张表

来源：`server/db/migrations/0001_iam.sql:65-94`。

| 表 | 结构 | REST 可见性 | 说明 |
| --- | --- | --- | --- |
| `roles` | `id`、`name`（唯一）、`description`、`created_at`、`updated_at` | `read:public` / `write:admin` | 角色字典 |
| `permissions` | `id`、`key`（唯一）、`description`、`created_at` | `read:public` / `write:admin` | 权限点字典 |
| `user_roles` | `(user_id, role_id)` 复合主键 | `read:admin` / `write:admin` | 用户—角色；前端不给写入口，授权变更必须走服务端（否则绕过审计） |
| `role_permissions` | `(role_id, permission_id)` 复合主键 | `read:admin` / `write:admin` | 角色—权限 |

关系：`users` ←多对多→ `roles` ←多对多→ `permissions`。权限点由角色间接授予，不直接绑用户。

### 5.2 种子角色与权限点

来源：`0001_iam.sql:124-148`。

| 角色 | 说明 | 种子赋予的权限点 |
| --- | --- | --- |
| `admin` | 超级管理员 | 全部（`admin:access`、`audit:view`、`role:manage`、`user:manage`、`device:bind`、`device:manage`） |
| `operator` | 运营 | `admin:access`、`audit:view` |
| `user` | 普通注册用户（注册时自动授予，`server/src/auth.js:221-226`） | **无**（种子 SQL 未给 `user` 任何权限点） |
| `device_admin` | 设备管理员 | `device:bind`、`device:manage` |

| 权限点 | 含义 | 当前使用位置 |
| --- | --- | --- |
| `admin:access` | 进入管理后台（菜单级） | 前端 `AdminGate` 实际判的是**角色** `admin`，未判该权限点（`src/app/admin-gate.tsx:14`） |
| `audit:view` | 查看审计日志 | 前端 `AdminAuditPage`（`perm="audit:view"`） |
| `role:manage` | 角色与权限管理（按钮级） | 前端后台首页入口显隐（`src/pages/system/AdminHomePage.tsx:33`） |
| `user:manage` | 用户管理（按钮级） | 暂无页面使用 |
| `device:bind` | 绑定 / 解绑本人设备 | 暂无（设备激活未实现） |
| `device:manage` | 管理全部设备 | 暂无 |

### 5.3 身份装载

请求级上下文由 `authenticate()` 构造（`server/src/auth.js:180-195`）：

| 成员 | 语义 |
| --- | --- |
| `ctx.uid` | 令牌中的用户 id |
| `ctx.jti` | 当前令牌 id（供吊销 / 审计） |
| `ctx.user` | `{ id, username, name, emoji, roles[], permissions[] }` |
| `ctx.isAdmin()` | `roles.includes('admin')` |
| `ctx.hasRole(name)` | 角色判定 |
| `ctx.hasPerm(key)` | 权限点判定 |
| `ctx.requireAdmin()` | 非 admin 抛 `403 forbidden`「仅管理员可执行该操作」 |
| `ctx.requirePerm(key)` | admin 豁免；否则缺权限点抛 `403`「缺少权限：<key>」 |

角色与权限由 `loadRoles` 一次装载（`server/src/auth.js:110-122`）：角色取 `user_roles ⋈ roles`，权限取 `user_roles ⋈ role_permissions ⋈ permissions` 去重后的 `key`。RPC 内有等价实现 `loadRolesVia`（`server/src/rpc.js:766-778`），返回 `{ roles, permissions }`。

**装载时机**：每次请求都重新查库（`server/src/auth.js:179`）。因此授权变更对下一次请求立即生效，无需重新登录；代价是每请求 3 次查询（identity + roles + permissions）。Phase 2 可加短 TTL 缓存。

### 5.4 首个管理员引导（两条路径）

| 路径 | 触发 | 条件 | 位置 |
| --- | --- | --- | --- |
| 环境变量 | 身份装载时自动 | `BOOTSTRAP_ADMIN_USERNAME` 与当前用户名一致，且库内尚无任何 admin | `server/src/auth.js:129-150` |
| RPC | 前端「成为首个管理员」按钮 | 同上；已有管理员 → `409 conflict`「已有管理员，请让对方在角色管理中授予」 | `server/src/rpc.js:740-764`、`src/app/admin-gate.tsx:48-58` |

两条路径都会写 `audit_logs(action='bootstrap_admin')`。这是「没有管理员就永远进不去后台」的唯一官方出口。

## 6. 管理后台与 C 端隔离

| 层 | 机制 | 位置 |
| --- | --- | --- |
| 路由 | 全站无路由级登录守卫，**仅** `#/admin/*` 由 `AdminGate` 包起来 | `src/app/routes.tsx:8-9`、`src/app/admin-gate.tsx:13-18` |
| 页面 | `AdminGate` 依次判：已登录 → `hasRole('admin')` → `hasPerm(perm)` | `src/app/admin-gate.tsx:13-18` |
| 数据 | 后台概览读 `roles` / `permissions` / `user_roles` 条数 | `src/pages/system/AdminHomePage.tsx:54-56` |
| 服务端 | `checkRead` / `checkWrite` 对 `read:'admin'` / `write:'admin'` 表调 `ctx.requireAdmin()` | `server/src/rest.js:117-127` |
| RPC | `verify_voucher`、`admin_user_lookup`、`admin_wallet_credit`、`admin_wallet_ledger` 内部 `ctx.requireAdmin()` | `server/src/rpc.js:521/862/877/906` |

隔离铁律：

1. 前端显隐只是便利层，**真正的闸门在服务端**。绕过 UI 直接调接口，服务端仍须拒绝。
2. `user_roles` / `role_permissions` 为 `read:admin` + `write:admin`，C 端用户读不到授权关系。
3. 授权变更不得由前端直改 `user_roles`（等于绕过审计），必须走服务端过程——当前**尚无**授权变更 RPC，`AdminRolesPage` 仅为只读展示（`src/pages/system/AdminRolesPage.tsx:6`）。
