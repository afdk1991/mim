## 1. 分支策略

### 1.1 分支类型

| 分支 | 命名 | 来源 | 去向 | 保护 | 现状 |
| --- | --- | --- | --- | --- | --- |
| 主干 | `main` | — | 部署与发布源 | 是（禁止直接 push，须经 PR） | 当前唯一长期分支，全部 298 次提交显示历史为直接提交 |
| 功能 | `feat/<短名>` | `main` | `main` | 否 | **当前未使用**，为待建约定 |
| 修复 | `fix/<短名>` | `main` | `main` | 否 | **当前未使用**，为待建约定 |
| 文档 | `docs/<短名>` | `main` | `main` | 否 | **当前未使用**，为待建约定 |
| 发布 | `release/<版本>` | `main` | 打 tag 后合回 | 否 | 未使用 |

命名约束：

| 项 | 规则 | 示例 |
| --- | --- | --- |
| 字符集 | 小写字母、数字、中划线，禁止下划线与中文 | `feat/ota-shadow` |
| 短名 | 2~4 个词，表达对象而非动作 | `fix/seckill-lock-release` |
| issue 关联 | 有编号时后缀 `-<编号>` | `feat/device-bind-42` |

### 1.2 现状与差距

| 事实 | 位置/依据 |
| --- | --- |
| 当前仓库只有 `main`（外加一个 dependabot 远端分支） | `git branch -a` |
| 历史 298 次提交直接落在 `main` | `git log --oneline | wc -l` |
| 远端只有 `origin` 一个 GitHub 主仓（镜像仓由 `mirror.yml` 单向推送） | `git remote -v`、`.github/workflows/mirror.yml` |
| `.github/workflows/build.yml` 同时监听 `push: [main]` 与 `pull_request: [main]` | `build.yml:7-11` |

**结论**：主干式开发（trunk-based）是既成事实。本节的分支命名约定自本文件生效起执行，不追溯历史。

### 1.3 合入规则

| 规则 | 说明 |
| --- | --- |
| 合入方式 | 优先 squash merge，保持 `main` 线性；feature 分支合入后删除 |
| 前置条件 | 「类型检查 + 构建」闸门绿；若改动后端则 `npm run server:check` 绿 |
| 禁入内容 | 容器化产物（`build.yml` 闸门机器拦截）、真实密钥（`.gitignore` 已排除 `.env`/`.env.*`） |
| 镜像仓纪律 | 镜像仓一律只读，镜像仓上的提交视为事故，需人工回搬（`mirror.yml:3-4`） |

## 2. 提交规范

采用 Conventional Commits。

### 2.1 格式

```text
<type>(<scope>): <subject>

[body]
[footer]
```

| 段 | 要求 |
| --- | --- |
| type | 必填，取值见 §2.2 |
| scope | 可选，用仓库真实存在的域或目录名 |
| subject | 必填，中文或英文短句，动词开头，末尾不加句号 |
| body | 可选，说明「为什么」而非「做了什么」 |
| footer | 可选，`BREAKING CHANGE:`、issue 引用 |

### 2.2 type 枚举（本仓库实际使用的部分，已加粗）

| type | 用途 | 本仓库实际使用 | 示例（取自 `git log`） |
| --- | --- | --- | --- |
| **feat** | 新功能 | 48 次 | `feat: 只读增量同步端点` |
| **docs** | 文档 | 34 次 | `docs: 归档历史文档并刷新现行规范` |
| **fix** | 缺陷修复 | 32 次 | `fix: 秒杀多单累计锁按订单粒度精确释放（BE-002）` |
| **chore** | 杂项/脚手架 | 28 次 | `chore(deploy): 给 install.sh / init-db.sh 加可执行位` |
| **ci** | CI 配置 | 14 次 | `ci: 加禁止容器化闸门；清掉遗留草稿里的 docker-compose 提及` |
| **refactor** | 重构 | 11 次 | — |
| **test** | 测试 | 3 次 | `test: 连库实测 V1-V8 全绿并回填分析文档` |
| perf | 性能 | 未使用 | — |
| build | 构建系统 | 仅以 `fix(build)` 出现过 | `fix(build): 新增 .npmrc 默认 legacy-peer-deps` |
| revert | 回滚 | 未使用 | — |
| style | 格式 | 未使用 | — |

补充约定：

| 项 | 约定 |
| --- | --- |
| 作用域取值 | 与仓库结构对齐：`build` / `ci` / `deploy` / `docs` / `worker` / `edge` / `content` / `social` / `commerce` / `growth` / `identity` / `tools` / `server` / `iot` |
| 一提交一意图 | 一个提交只做一件事；文档与代码混改时分两个提交 |
| 不在提交里带密钥 | `.gitignore` 已排除 `.env`、`server/.env`、`.st.token` 等 |
| 提交钩子的现状 | **本仓库无 husky / commitlint / lint-staged**，格式靠人工遵守与 CR 把关（状态：待建） |

### 2.3 已知历史问题

历史提交中存在大量不合规记录，形如 `轮 24 打通：B5 多媒体——上传转码工作台/直播推拉流连麦/视频弹幕/语音条`、`页脚信息区 5 入口接入全站搜索…`。这些是长句中文描述、无 type 前缀，且**存在所描述的「B5 多媒体——直播推拉流连麦」能力在当前代码中并不存在**的情况（见 ADR-006：本仓库未集成 RTC）。

处理纪律：不追溯修改历史；自本文件生效起新提交必须合规；描述功能时不得声称未实现的能力。

## 3. Code Review 规则

### 3.1 流程

| 步骤 | 内容 |
| --- | --- |
| 1. 自审 | 提交者先自查清单（§3.2）后再开 PR |
| 2. 指定 reviewer | 至少 1 人；涉及后端接口的必须含后端负责人，涉及跨端行为的必须含客户端负责人 |
| 3. 自动化闸门 | 类型检查 + 构建必须通过（见 §4） |
| 4. 人工审查 | 按 §3.2 清单逐项过 |
| 5. 合入 | squash merge，删除源分支 |

### 3.2 审查清单

| 类别 | 检查项 |
| --- | --- |
| 安全 | 是否有新表进入 REST 白名单；`users` 是否仍不开放；是否引入宿主嗅探；是否有密钥/令牌入库；上传路径是否有 `..` 穿越（`storage.js` 的 `safeKey`） |
| 契约 | 新增后端错误码是否已同步 `server/src/errors.js` 与 `src/core/result.ts` 的 `ErrCode`；响应是否为 `{ data }` / `{ error: { code, message } }` |
| 数据 | 迁移文件是否全部幂等（`if not exists`）；是否占用 0009 编号；是否有 owner 列注入 |
| 前端 | 是否触碰了 `src/platform/` 之外的宿主 API；依赖方向是否仍单向（`pages → app → domain → data → core`） |
| 路由 | 新增路由是否同时改了 `src/app/routes.tsx` 与对应域桶文件 `src/pages/<域>/index.ts`；是否同步进 `scripts/verify-routes.mjs` 的 `ROUTES` 数组 |
| 依赖 | 是否在 `server/` 引入第二个运行时依赖（ADR-003 约束：只允许 `pg`） |
| 容器 | 是否新增 Dockerfile / docker-compose / 双扩展名文件（CI 闸门机器拦截） |
| 测试 | 是否补充或更新 `tests/` 用例与 `scripts/verify-*.mjs` 回归基线 |

### 3.3 规模与时效

| 项 | 约定 |
| --- | --- |
| PR 规模 | 建议 ≤ 400 行有效改动；超出应拆分或先做重构提交 |
| 阻塞项 | 安全类与安全契约类问题一律阻塞，不接受「后续补」 |
| 非阻塞项 | 命名、注释、细粒度结构问题可标记为 follow-up |
| 关键人单点 | 后端改动当前依赖单一主力，必须走双人或文档化交接（见 R-012） |

## 5. TypeScript 约定

| `strict` | `true` | 总开关（含 `strictNullChecks` 等） |

### 5.2 未开启（如实标注，属已知欠账）

| 项 | 影响 |
| --- | --- |
| `noUncheckedIndexedAccess` | 数组/索引访问不强制 `T | undefined`，是空指针类缺陷的温床 |

补充：`tsconfig.json` 的 `include` 只有 `["src"]`，因此 **`tests/`、`scripts/`、`server/` 不在类型检查范围内**。后端为纯 JS 无 TS 保护（见 ADR-003 §3.3）。

### 5.3 类型使用约定

| 约定 | 说明 | 依据 |
| --- | --- | --- |
| 类型导入必须带 `type` | `import type { ReactNode } from 'react'` | `verbatimModuleSyntax` |
| 判别联合表达结果 | `Result<T> = { ok: true; data: T } | { ok: false; error: AppError }`，不用 throw 表达可预期失败 | `src/core/result.ts:22-27` |
| 错误码集中定义 | `ErrCode` 联合类型是唯一真源，与后端 `errors.js` 一一对应 | `src/core/result.ts:10-20` |
| 三态写回 | `WriteBack = 'ok' | 'skip' | 'fail'`，`skip` 不算错误 | `src/core/result.ts:48` |
| 禁止 `any` | `strict` 不禁止 `any`，本规范明令禁止新代码使用 `any`；确需时用 `unknown` + 收窄 | 本文件约定 |
| 类型谓词收窄 | 如 `const isChannel = (v): v is MallChannel` | `src/app/routes.tsx:87` |
| 配置类型从单一处导出 | 如 `MallChannel` 从 `domain/commerce/model` 导出 | `src/app/routes.tsx:20` |

## 6. 命名规范

### 6.1 文件与目录

| 对象 | 规则 | 正例 | 反例 |
| --- | --- | --- | --- |
| 目录 | 小写中划线 | `src/domain/commerce/biz/` | `src/domain/commerce/Biz/` |
| 组件文件 | PascalCase | `PostCard.tsx`、`ArticleEditorPage.tsx` | `post-card.tsx` |
| 非组件模块 | 小写中划线 | `router.tsx`、`result.ts`、`contract-check.ts` | `Router.tsx` |
| 后端模块 | 小写单词 | `main.js`、`rest.js`、`rpc.js`、`iot.js`、`errors.js` | `Rest.js` |
| 迁移文件 | `NNNN_<主题>.sql` 四位序号 | `0008_iot_device.sql` | `8_iot.sql` |
| 域桶文件 | `src/pages/<域>/index.ts` | `src/pages/content/index.ts` | 散落 import |
| 验证脚本 | `verify-<对象>.mjs` | `verify-routes.mjs` | `check1.mjs` |

### 6.2 标识符

| 对象 | 规则 | 正例 |
| --- | --- | --- |
| React 组件 | PascalCase，页面组件以 `Page` 结尾 | `MallSeckillPage`、`PostCard` |
| 变量/函数 | camelCase | `resolveRoute`、`segmentsOf` |
| 常量 | UPPER_SNAKE | `MAX_BODY`、`IDENT_RE`、`DUMMY_HASH` |
| 类型/接口 | PascalCase | `AppError`、`MallChannel`、`ErrCode` |
| 私有内部函数 | 小写 camelCase，不加下划线前缀 | `ident`、`derive` |
| 布尔量 | `is` / `has` / `should` 前缀 | `isChannel`、`hasUpdate` |

### 6.3 分层与依赖方向

```text
pages  →  app  →  domain  →  data  →  core
```

| 层 | 目录 | 职责 | 可依赖 |
| --- | --- | --- | --- |
| pages | `src/pages/<域>/` | 页面组件，按域从桶文件导出 | app、domain、ui |
| app | `src/app/` | 路由、壳、守卫、全局状态 | domain、data、core |
| domain | `src/domain/` | 业务模型与规则（content/social/commerce/growth/identity/tools） | data、core |
| data | `src/data/` | 数据访问（client/repo/session/sync） | core |
| core | `src/core/` | 基础设施（result/http/config/storage/events/theme/version/utils） | 无 |
| platform | `src/platform/` | 宿主适配（web/capacitor/miniprogram/mock） | core |

硬约束：

| 编号 | 约束 |
| --- | --- |
| 1 | 依赖方向单向向下，禁止反向依赖（`core` 不得 import `domain`） |
| 2 | 业务代码禁止直接访问宿主 API，宿主能力一律经 `src/platform/` 的 `getPlatform()` |
| 3 | 新增页面必须同时改 `src/app/routes.tsx` 与对应域桶文件，否则拿到 `undefined` 组件 |
| 4 | 路由表不得散落 import，页面组件一律从域桶文件导入 |

### 6.4 路由治理（当前存在不一致，如实记录）

| 口径 | 数值 | 来源 |
| --- | --- | --- |
| `routes.tsx` 文件头注释 | 57 条 | `src/app/routes.tsx:2-4` |
| `scripts/verify-routes.mjs` 的 `ROUTES` 数组 | 59 条 | `scripts/verify-routes.mjs:8-22` |

以 59 条为准。路由数量从 57 增长到 59 而文件头注释未同步，说明**路由新增没有强制的同步点**。本规范因此要求：新增路由必须三处同改（`routes.tsx` 的 switch + 域桶文件 + `verify-routes.mjs` 的 `ROUTES`），并纳入 §3.2 的 CR 清单与 §4.3 的 P1 机器校验。

| 编号 | 约定 |
| --- | --- |
| 1 | `package-lock.json` **有意不入库**，理由是 npm/cli#4828 会按当前平台裁剪可选依赖，跨平台复用会缺 rollup 原生二进制（`.gitignore:4-6`）。代价是构建不可复现，已登记为 R-005 |
| 2 | 缓解手段：`.npmrc` 全仓库默认 `legacy-peer-deps=true`；CI 显式传 `--legacy-peer-deps`；CI 不开 npm cache |
| 3 | `server/` 的运行时依赖只允许 `pg`（ADR-003）；前端依赖新增需说明必要性 |
| 4 | 前端构建 `base: './'` 相对路径，产物可塞进任意路径前缀（`vite.config.ts:11`） |
| 5 | 三端壳的 `dist` 绑定点是 `capacitor.config.ts` 的 `webDir` 与 `src-tauri/tauri.conf.json` 的 `frontendDist` |
| 6 | 后端地址由构建期 `VITE_MIM_API_BASE` 注入；改地址需重新 build + `cap sync`（变量在构建期被内联） |
| 7 | 上传体积三方对齐：前端 `LIMITS.uploadMaxBytes` = nginx `client_max_body_size 3m` = 后端 `UPLOAD_MAX_BYTES` 3MB |
