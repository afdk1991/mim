## 1. 事件命名

### 1.1 规则

```
<域>_<对象>_<动作>
```

- 全小写 `snake_case`，只允许 `[a-z0-9_]`，禁止驼峰、连字符、中文。
- `域`：业务域枚举，见 §1.2。
- `对象`：被作用的实体名词，单数。
- `动作`：过去式或瞬时动词，见 §1.3。
- 当「对象即域本身」时允许省略对象段，写作 `<域>_<动作>`（例：`wallet_debit`、`growth_checkin`）。除此之外不得省略。
- 同一事件名在所有端（Web / iOS / Android / 小程序）必须一致，端差异用公共属性 `platform` 区分，不得靠事件名区分。

### 1.2 域枚举

| 域 | 覆盖范围 | 对应代码位置 |
| --- | --- | --- |
| `app` | 应用生命周期、页面浏览、性能 | 前端路由 `src/app/routes.tsx` |
| `content` | 动态 / 文章 / 代码片段 / 话题 | `src/domain/content`、`posts`、`articles` |
| `social` | 关注 / 私信 / 通知 / 收藏 | `src/domain/social`、`follows`、`messages` |
| `mall` | 商品 / 订单 / 四业务会场 | `src/domain/commerce`、`products`、`mall_orders` |
| `wallet` | 余额 / 流水 / 充值 | `wallet_balances`、`wallet_txs` |
| `growth` | 成长 / 签到 / 徽章 | `src/domain/growth`、`growth_events` |
| `device` | 设备绑定 / 指令 / OTA | `server/src/iot.js`、`devices`、`device_commands` |
| `system` | 登录 / 权限 / 错误 | `server/src/auth.js` |

### 1.3 动作词表（新增动作须从中选取）

| 动作 | 语义 | 例 |
| --- | --- | --- |
| `view` | 曝光 / 浏览 | `content_post_view` |
| `click` | 点击（无业务结果） | `mall_goods_click` |
| `publish` | 发布成功 | `content_post_publish` |
| `create` | 创建成功（含下单） | `mall_order_create` |
| `update` / `delete` | 变更 / 删除 | `content_post_delete` |
| `pay` | 支付提交且成功 | `mall_order_pay` |
| `add` | 新增子资源 | `content_comment_add` |
| `like` / `unlike` | 点赞 / 取消赞 | `content_post_like` |
| `checkin` | 签到 | `growth_checkin` |
| `send` / `ack` | 下发 / 回执 | `device_command_send`、`device_command_ack` |
| `bind` / `unbind` | 绑定 / 解绑 | `device_bind` |
| `report` | 上报（设备侧主动） | `ota_report` |
| `fail` | 明确失败（须带 `reason`） | `device_command_fail` |

> 失败统一用属性 `result` / `reason` 表达，**不新增 `_fail` 事件名**，除非失败本身是需要单独统计的终点（如 `device_command_ack` 的失败态已在 `status` 中）。

## 2. 公共属性（每条事件必带）

| 属性 | 类型 | 说明 | 取值来源 |
| --- | --- | --- | --- |
| `app_version` | string | 应用版本 | `package.json` 的 `version`（当前 `0.1.0`），构建期注入 |
| `platform` | string | 运行端 | `web` / `ios` / `android` / `miniprogram`（`src/platform` 适配层已有平台判定能力） |
| `uid_hash` | string | 用户标识哈希 | 登录用户取 `sha256(uid + 每日盐)` 或服务端下发伪 id；未登录填 `guest` 的本地随机 id 哈希。**禁止**直接上报 uid 明文 |
| `session_id` | string | 会话 id | 单次应用生命周期内唯一，冷启动重新生成 |
| `ts` | int | 事件发生时间（毫秒，Unix epoch） | 客户端本地时间；服务端收到后另记 `recv_ts`，两者差值用于校时 |
| `event` | string | 事件名 | 见 §1 |
| `page` | string | 当前页面（hash 路由根路径 + 关键参数） | 由 `src/app/routes.tsx` 的 root 段映射 |

建议补充（可选）：`os`、`network`（`wifi` / `4g` / `none`）、`device_model`、`channel`（投放渠道）。

### 2.1 禁止采集的字段

| 类别 | 禁止项 | 说明 |
| --- | --- | --- |
| 身份凭据 | 明文手机号、邮箱、身份证号、登录令牌（Bearer token）、密码、密码哈希 | 令牌一旦进埋点等于全量账号可被劫持 |
| 设备凭据 | Device-Token 明文、`device_token_hash` | `0008_iot_device.sql:26` 明确永不外发 |
| 金融信息 | 支付凭证图片 `proof` 内容、银行卡号、完整订单金额明细（允许 `amount_fen` 数值） | `mall_orders.proof` 为 jsonb，只可取字段存在性 |
| 券码 | `local_voucher_codes.code` 明文 | 券码即核销凭证 |
| 精确位置 | 经纬度原始值（`posts.location` 文本按需脱敏到城市粒度） | |
| 用户生成内容正文 | `posts.content`、`messages.content`、评论正文 | 只上报长度 / 是否含图片等派生属性 |

判定原则：**任何可作为凭证或可直接定位到自然人的字段，一律不进埋点**。需要用户维度分析时用 `uid_hash` 关联。

## 3. 上报通道（建议，尚未实现）

| 项 | 约定 |
| --- | --- |
| 端点 | `POST /api/events`（批量数组，单次上限 50 条）——当前未实现 |
| 鉴权 | 登录用户带 `Authorization`；游客允许匿名上报（否则未登录漏斗无法统计） |
| 可靠性 | 写本地队列，`sendBeacon` 或平台 http 能力补传；网络失败缓存并在下次成功时补发，**不得阻塞主流程** |
| 失败语义 | 埋点失败一律按 `skip` 处理（参照写入三态语义），**不得**向用户弹错 |
| 服务端 | 落 `events` 表（`ts`、`recv_ts`、`uid`、`platform`、`app_version`、`event`、`props` jsonb），并建 `(event, ts)` 与 `(uid, ts)` 索引 |
| 采样 | 高频 `view` 类事件允许服务端按 `uid_hash` 稳定采样，采样率写入事件属性 `sample_rate` |

服务端可替代数据源（在端点落地前用于口径计算）：见 §4 表格末列。

## 5. 口径定义

通用约定：

- 自然日切分：`[当日 00:00:00, 次日 00:00:00)`，时区 **Asia/Shanghai（UTC+8）**。
- 去重口径：用户级指标按 `uid_hash`（或服务端 `user_id`）去重，不去重设备。
- 金额一律以「分」（`amount_fen`）为单位，展示时再除以 100。
- 所有比率的分母必须写明，禁止只给分子。

| 指标 | 口径公式 | 数据源（现状） | 备注 |
| --- | --- | --- | --- |
| DAU | `DAU(d) = count(distinct uid where 当日发生任意 app_*/content_*/mall_* 事件)` | 事件表（未实现）。**当前只能用替代口径**：`count(distinct user_id)` from `growth_events` ∪ `mall_orders` ∪ `posts` 当日有行为者 | 替代口径会低估（不含纯浏览用户），报告中必须标注为「活跃用户（窄口径）」 |
| 新增用户数 | 当日 `users.created_at` 落在区间内的行数 | `users.created_at`（`0001_iam.sql:29`，有 `idx_users_created`） | 已具备 |
| 次日留存 | `R1 = count(distinct 第 0 日新增 ∩ 第 1 日活跃 uid) / count(distinct 第 0 日新增 uid)` | 新增侧已具备；活跃侧依赖事件表 | 7 / 30 日留存同构，把第 1 日换成第 N 日 |
| 下单转化率 | `CVR = count(distinct uid with mall_order_create) / count(distinct uid with 商品/会场 view)` | 分子已具备（`mall_orders`）；分母待补采集 | 分渠道（`/mall/biz/<kind>`）单独出数时，分子分母须同渠道 |
| 支付成功率 | `PSR = count(order where status in ('paid','done')) / count(order)`，`order` 为当日创建的 `mall_orders` | 已具备（`mall_orders.status`） | `awaiting_confirm` 为「已传凭证待确认」，**不计成功**；确认通过才转为 `paid`。若需含待确认，须在报告中单列 |
| 钱包支付成功率 | `count(wallet_debit result='success') / count(wallet_debit)` | 成功侧已有（`wallet_txs.kind='consume'`），失败侧待补采集 | 失败主因预期为 `insufficient`（`server/src/rpc.js:618`） |
| 秒杀成功率 | `count(seckill_grab result='success') / count(seckill_grab)`（请求级）；另有用户级 `count(distinct uid success) / count(distinct uid 尝试)` | 成功侧已有（`seckill_lock_items`）；失败侧待补采集 | 两个口径必须分开报：同一用户多次失败会显著拉低请求级成功率 |
| 秒杀售罄率 | `count(distinct session where remaining=0) / count(distinct session where status='active')` | 已具备（`seckill_sessions.remaining` / `total`） | |
| 配网成功率 | `count(device_bind result='success') / count(device_bind)` | **未实现**（BLE 配网未开发） | 需定义超时阈值（建议 120s 未绑定成功即记失败）并单列超时占比 |
| 设备指令成功率 | `count(device_command_ack status='acked') / count(device_command_send result='sent')` | 已具备（`device_commands.status`） | 迟到回执（`expire` 后才到）按 `where status in ('pending','sent')` 的条件更新被忽略，不计入分母之外的成功（`server/src/iot.js:132-137`） |
| 指令端到端时延 | `P50/P95/P99(device_command_ack.latency_ms)`，其中 `latency_ms = acked_at - sent_at` | 已具备 | 服务端时间为准，避免设备时钟漂移 |
| 首帧时间（FCP） | `FCP = performance.getEntriesByName('first-contentful-paint')[0].startTime`（ms，相对 navigationStart）；SPA 路由切换另记 `route_render_ms = 渲染完成时刻 - 路由变更时刻` | **未实现**（全仓无 `PerformanceObserver` / `performance` 采集代码） | Web 用 `paint` 时序；Capacitor / 小程序端用「路由变更 → 首屏内容挂载」的自埋点，两端口径不可直接混比 |

## 6. 埋点自检与验收

### 6.1 自检清单（提测前逐条勾）

| # | 检查项 | 不合格后果 |
| --- | --- | --- |
| 1 | 事件名符合 `<域>_<对象>_<动作>`，全小写 snake_case | 报表无法归类 |
| 2 | 公共属性（`app_version`、`platform`、`uid_hash`、`session_id`、`ts`、`page`）齐全 | 无法分端分版本 |
| 3 | 不含 §2.1 任一禁止字段 | 合规风险 |
| 4 | 触发时机与业务结果一致：成功与失败都在「收到确定结果」后上报，不在点击瞬间上报 | 漏斗虚高 |
| 5 | 上报失败不阻塞主流程、不弹错（按 `skip` 处理） | 埋点故障拖垮业务 |
| 6 | 写操作类埋点不影响业务事务、不参与幂等键 | 重复扣款 / 重复发码 |
| 7 | 列表曝光去重（同一 `post_id` 同会话只报一次，除非定义「每次进入可视区」） | 曝光量虚高 |
| 8 | `view` 类事件有停留阈值或可视区判定 | 口径不可信 |
| 9 | 金额用分、时间用毫秒、比率同时给出分子分母 | 报表算错 |
| 10 | 端上事件名与服务端落库名完全一致（含大小写） | 数据断裂 |

### 6.2 验收方式

| 阶段 | 方式 | 通过标准 |
| --- | --- | --- |
| 联调 | 抓包（浏览器 DevTools / Charles）核对请求体 | 事件名、公共属性、关键属性与 §4 表格逐字段一致 |
| 服务端 | 落库后 `select event, count(*) group by event` 抽查 | 无空事件名、无未知事件名（未知事件名须走评审补录） |
| 对账 | 业务真源 vs 事件数：`mall_orders` 当日行数 vs `mall_order_create` 事件数 | 差异率 < 0.5%，超出需说明丢数原因（采样 / 离线补传失败） |
| 漏斗 | 关键漏斗（`view → order_create → order_pay`）逐级人数单调不增 | 出现下级大于上级即为事件重复上报或去重失效 |
| 回归 | 纳入 `scripts/` 下的验证脚本（现有 `verify:routes` / `verify:backend` / `verify:feed` 等），新增埋点校验项 | 脚本可复跑，不依赖人工点检 |
| 隐私 | 对事件表抽样人工审阅 + 关键字扫描（手机号正则、token 前缀 `Bearer`、16/32 位十六进制串） | 零命中 |
