## ADR-002：MQTT Broker —— EMQX 5.x 自托管 3 节点集群

### 背景

- 假设 A5：Phase 1 目标 **10 万设备长连接**（容量口径，非实际在线）；实际在线从 W10 众测 50 台起步爬坡。
- 前提 P3：后端自研，仅 RTC/推送/短信用 PaaS。
- 人力现实：设备接入仅后端 B 一岗（00 号文 §4），运维负担是真实成本。
- 05 号文云资源模型（16.8 万）按自托管口径编制。

### 选项对比

| 维度 | A：EMQX 5.x 自托管 | B：托管 MQTT（EMQX Cloud / 云厂商微消息队列） |
| --- | --- | --- |
| 成本 @10 万连接 | 3×4C8G ≈ 0.1–0.2 万/月（计入云资源） | 按连接数计费，1–3 万/月量级 |
| 成本 @Phase 1 实际（<1 千台） | 3×2C4G ≈ 0.05–0.1 万/月 | 0.1–0.3 万/月 |
| 运维负担 | 后端 B 承担，CTO 备份 | 近零 |
| W6 压测（M2 验收项） | 压测环境自建，一次性成本 | 压测同样按量计费，成本高 |
| 协议与数据控制 | 完全可控：一机一密、HTTP 认证对接设备服务 | 受平台能力约束，定制受限 |
| 供应商锁定 | 无 | 中高（连接数越大迁移越痛） |

### 决策

**选 A：EMQX 5.x 自托管。** 理由：成本曲线在 10 万连接量级差距达一个数量级；压测可控性直接决定 M2 验收；符合 P3 自研边界。运维单点风险用「CTO 备份 + 选型保守化」对冲——不启用自研插件，只用官方稳定特性。

### 技术基线

- 集群：生产 4C8G×3（压测期弹性扩容），TLS 8883，keepalive 300s；禁匿名连接。
- 认证：一机一密 Device-Token（激活时签发，链路见 01 号文 §2.1），HTTP 认证对接设备服务。
- Topic 规范：`$dev/{device_id}/cmd`（下行指令）、`$dev/{device_id}/up`（上行状态）、`$dev/{device_id}/shadow`（设备影子）；默认 QoS1，OTA 指令 QoS1 + 离线会话。
- 监控：连接数 / 上下行 TPS / 离线率进监控面板并设告警阈值——04 号文 §6 发布检查单「监控告警就位」的依赖项。

### 行动与回退

1. 后端 B：W3（S2）集群上线测试环境；W6 前产出 10 万连接压测报告（M2 验收，02 号文 S3）。
2. 回退条件：集群稳定性连续两个迭代不达标，或后端 B 人力无法支撑运维 → 立新 ADR 评估迁移托管。

## ADR-003：RTC PaaS —— 声网为主，TRTC 备选，信令层 vendor 抽象

### 背景

- 假设 A3：1v1 实时互动，信令自研、媒体走 PaaS（01 号文 §2.2）。
- 硬件端（A1：摄像头+麦克风联网设备，ODM 供板）必须有嵌入式 SDK。
- 06 号文 §4 已定：小程序不做 RTC 通话 → 供应商的微信生态能力**权重为零**。
- 成本口径：双边计费，05 号文 §2 按音频 0.007 / 720P 0.028 / 1080P 0.056 元/分钟建模。

### 选项对比

| 维度 | 声网 Agora | 腾讯 TRTC |
| --- | --- | --- |
| 单价（订阅侧） | 音频 0.007 / 720P 0.028 / 1080P 0.056（与成本模型一致） | 基本持平，以合同为准 |
| 嵌入式 SDK | Linux C SDK 成熟，主流 ODM 方案商多有现成适配 | 有嵌入式方案，方案商适配案例较少 |
| 弱网质量 | SD-RTN 专网，抗丢包与低延迟口碑强 | 良好 |
| 服务端 API | Token 签发 / 频道管理 / 计费详单完整 | 完整 |
| 国内合规 | 齐全 | 齐全 |
| 微信生态加成 | — | 有（本 Phase 权重为零） |

### 决策

**声网为主供应商；信令服务做 vendor 抽象，TRTC 为备选。** 决定性因素是嵌入式 SDK 成熟度——硬件链路是本项目最长板，不能在设备端 SDK 上赌。

### Vendor 抽象（后端 B 信令服务实现）

```
interface RtcProvider {
  issueToken(channelId, uid, ttlSeconds): { token, expireAt }
  closeChannel(channelId): void
  fetchBill(date): BillItem[]   // 双边订阅分钟明细，成本对账用
}
```

切换 TRTC 仅需新增实现 + 配置开关，切换成本 < 1 迭代——这是 07 号文风险 R7（RTC PaaS 单点）的结构性对冲。

### 行动与回退

1. 顾问：W2 前完成商务比价与合同（目标价不高于目录价 9 折）；本 ADR §ADR-003 即顾问 W1 选型报告产出。
2. iOS/Android：W2 完成双端 demo（02 号文 S3 前置）。
3. 每月按供应商对账单核成本面板（05 号文 §2 治理纪律）。
4. 回退条件：接通率连续两周 < 98%（01 号文指标）且定位为供应商网络问题 → 启动 TRTC 切换评估。

## ADR-004：支付双轨对账 —— iOS IAP + Android/小程序微信支付，统一订单 T+1 三方对账

### 背景

- 假设 A4：iOS 虚拟商品（会员/时长包）必须走 IAP（06 号文合规 §6.5）；Android/小程序走微信支付；国内 Android 无强制 IAP。
- 硬要求：幂等（03 号文规范一 §1.5 Idempotency-Key 24h）；T+1 对账差异率 < 0.01%（01 号文 §4 指标）。
- 链路草案已在 01 号文 §2.4，本 ADR 落地为可开发设计。

### 设计决策

**1. 统一订单模型（双保险幂等）**

```sql
orders (
  order_id        text primary key,        -- 内部单号
  user_id         text not null,
  sku_id          text not null,           -- 会员月/年、时长包
  amount_fen      bigint not null,         -- 单位分，03 号文规范一 §1.1
  channel         text not null,           -- 'iap' | 'wxpay'
  status          text not null,           -- created/paid/refunding/refunded/closed
  idem_key        text,                    -- 请求级幂等（客户端 Idempotency-Key）
  channel_txn_id  text,                    -- Apple original_transaction_id / 微信 transaction_id
  paid_at         timestamptz,
  created_at      timestamptz not null
);
unique (channel, channel_txn_id)   -- 业务级幂等硬约束
unique (user_id, idem_key)         -- 请求级幂等（24h，03 号文）
```

**2. iOS 链路（StoreKit 2 + App Store Server API）**：服务端建预订单 → 端上支付得 JWS signed transaction → 服务端验签并向 Apple 核实 → 按 `original_transaction_id` 幂等入账 → 权益生效。订阅 ASSN V2 服务端通知（`DID_RENEW` / `REFUND` / `REVOKE` / `EXPIRED` 等），全量落库并驱动权益状态机。W8 沙箱验证（02 号文 S4 验收）。

**3. 微信链路（支付 V3）**：小程序走 JSAPI、Android 走 APP 支付；平台回调用平台证书验签；按 `transaction_id` 幂等入账；回调重放返回错误码 60102，不重复入账。

**4. 订单状态机**：`created → paid → (refunding → refunded | closed)`，只允许单向迁移；非法迁移尝试触发告警（对账异常的前哨）。

**5. T+1 对账 job（每日 02:00）**：拉取 Apple transaction history 与微信 `/v3/bill/tradebill` → 与内部订单三方核对 → 差异分类：长款（渠道有、我无）/ 短款（我有、渠道无）/ 状态不一致 → 挂起（错误码 60301）进 finance 人工队列；对账报表入 Web 后台；差异率 < 0.01% 为 M3 验收口径。已知坑：Apple 账单最长延迟 48h，**对账以渠道账单为准，迟到单据滚入下一周期**，不做强行调平。

**6. 退款**：finance 角色后台审批（03 号文规范三权限点 `order:refund:approve`）→ 渠道退款 API → 权益回收 + 审计日志全量留痕。

**7. 合规红线**：iOS 端虚拟商品界面不得出现任何外链支付引导；硬件实物购买不属 IAP 范畴，各端均可微信支付。沙箱订单用独立 sku 前缀隔离，不进正式对账。

### 行动

1. 后端 A：按本设计开发，S4 完成沙箱全链路（02 号文 W7 支付沙箱下单 / W8 IAP 沙箱验票）。
2. PM 协办：微信商户号、Apple 开发者资质 W3 前完成申请（资质审核周期是不可控项）。
3. QA：支付幂等与对账差异纳入 P0 阻断级用例（07 号文矩阵）。

### 裁定

**批准。** 本 ADR 自 W2 计划提前至 W1 生效。
