## 1. 一句话定位

**Mim 是一个 pnpm monorepo 形态的「Headless 后端中台 + 两个前端薄壳（用户端 / 管理后台）+ 共享领域包」的全栈单体应用**：Express 提供 `/api/v1` 接口与 WebSocket 实时通道，SQLite（better-sqlite3）单文件落库，React 18 + Vite 构建用户端与后台两套静态产物，社区内容、商城交易、支付履约、钱包积分、IM 聊天、邀请返佣、会员 VIP、账号与 RBAC 权限等业务域集中在同一后端服务内。

- 取证：根 `package.json` 第 6 行 description（`Mim 产品底座（Headless 中台 + 多端薄壳）`）；`pnpm-workspace.yaml`；`services/mim-api/src/index.ts`、`apps/web/src/main.tsx`、`apps/admin/src/main.tsx`。

## 6. 账号体系

### 6.1 Mim ID 发号规则（`identity.ts` + `member-no.ts`）

- **编号形态**：纯十进制数字（`1`、`2`、`3` … 上限 `9,999,999,999`），无前缀、不补零，位数随用户量自然增长；号码由 `member_no_sequence` 单行表在事务内「读 + 自增」分配，多入口并发注册不重号。
- **发号跳过规则**：候选号若是靓号（`classifyPremiumNo(...)` 非空）或已被占用，游标推进到下一个候选；连续跳过次数超过 `MEMBER_NO_SKIP_GUARD` 时快速失败并抛 `MEMBER_NO_EXHAUSTED`，防止规则写错导致无限扫描。
- **存量重排**：启动期按注册顺序（`created_at ASC, id ASC`）全量重排，规则版本键为 `RENUMBER_KEY = 'renumber_v2'`，幂等；改号码规则必须继续升版（v3、v4 …）。旧号逐条写入 `member_no_history` 审计表。

### 6.2 靓号预留类型（`member-no.ts`，共 11 类）

| 类别码 | 含义 | 判定要点 |
|---|---|---|
| `short` | 短号段 | 长度 ≤ 2（`1～99`）整段预留，不自动发放 |
| `repeat` | 豹子号 | 3 位起逐位全同（`111`、`8888`） |
| `ladder` | 顺子号 | 3 位起相邻位差全 +1 或全 -1（`123`、`987`） |

### 7.2 支付意图状态机

- 既有库 `payment_intents.status`：`pending → paid`，旁置 `failed / cancelled`（`schema.sql` 第 665 行）。
- 扩展渠道 `payment_ext_intents`：创建即 `pending`；履约采用 **条件更新抢占**：`UPDATE ... SET status='paid' WHERE id=? AND status='pending'`，只有抢占成功的那一次回调继续履约；重复回调命中已 `paid` 直接返回 `replayed=true`，不重复加钱 / 发权益。
- 退款：扩展渠道写 `payment_ext_refunds`，`status ∈ processed/failed`；主库退款状态回写 `payment_intents.refund_status`。

### 7.3 异步回调验签

- `alipay-ent.ts`：RSA2（`RSA-SHA256`）签名 / 验签，回调以支付宝公钥 `verify` 校验 canonical 排序串与 `sign`，金额与 `app_id` 核对；表单以 `urlencoded` 单独解析，原始报文在 JSON 解析前保留（`app.ts` 第 89–90 行 `rawBody`）。
- 其余适配器在各自 `adapters/*.ts` 内实现回调校验；回调路由公开挂载，下单 / 退款在 router 内逐个挂鉴权与幂等键。

### 7.4 发货履约链路（`deliverShopOrder`，`payments.ts` 第 311 行起）

在线支付落定后按序执行，订单先抢占（`changes=0` 即被其它回调履约，直接返回，不重复扣积分 / 发卡 / 分成）：

1. **扣积分**：`points_spent > 0` 时条件扣减钱包积分（`WHERE points >= ?`），不足则抛 `CONFLICT` 整单回滚；写 `wallet_transactions`（`kind=points`，负数流水）。
2. **核销优惠码**：存在 `coupon_code` 时把对应 `coupons.used_count + 1`，并写 `coupon_redemptions`（折扣金额、订单关联）。
3. **推广分成**：被邀请人首单且关系 `bound` 时，邀请人拿可支付金额的 **5%** 分成；写入邀请人钱包余额与 `wallet_transactions`（`kind=commission`），关系置 `settled`。
4. **交付方式**：
   - 自动发卡：取一张 `status='unused'` 的 `shop_card_keys`，条件占用为 `used` 并绑定购买人；
   - 实物：按数量扣减 `shop_products.stock`（`MAX(0, stock - ?)`），进入待发货；
   - 人工交付：进入待客服交付队列（`shipments` 工单，状态 `pending/picked/transit/delivered/exception`）。
- 履约分支还包括：`recharge` 入钱包、`asset` 发付费资产、`vip` 续会员、`shop_order` 置已支付（`fulfillExtIntent` 与主库 `fulfillIntent` 同口径）。

> 取证：`payments/registry.ts` 第 11–17、41–90、93–108 行；`payments/fulfill.ts` 第 20、55–96、105–127 行；`payments.ts` 第 308–371 行；`schema.sql` 第 573、617、665、692、707 行。

### 8.3 鉴权中间件（`middleware.ts`）

- `requireAuth`：解析 Bearer 令牌并加载当前用户；`requirePermission(permission)` 高阶工厂：未认证 401，已登录但权限不覆盖抛 `FORBIDDEN`（403）并回显缺失权限码。
- 后台管理接口不走全站强制登录门，由每个路由自己的 `requirePermission` 单独校验；冷启动只有一个账号时，可先用环境变量引导令牌进入后台，再把 `rbac:write` 授予真实账号，之后日常一律走 JWT + 权限点。
- 权限读取：`user_roles JOIN role_permissions` 按用户聚合去重权限码集合。
