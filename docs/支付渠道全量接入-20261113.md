# 支付渠道全量接入（2026-11-13）

## 1. 概述与范围

在既有四渠道（支付宝当面付 `alipay`、微信 Native `wechat`、人工转账 `manual`、沙箱 HMAC `sandbox`）之上，补齐五个统一适配器渠道：

| 渠道 id | 名称 | 协议 / 签名 | 落库表 |
| --- | --- | --- | --- |
| `hupijiao` | 虎皮椒聚合支付（微信 / 支付宝扫码） | MD5（字典序 `k=v` 拼接后尾部直拼 APPSECRET） | `payment_ext_*` |
| `xunhu` | 讯虎聚合支付 | HMAC-SHA256（canonical 串，hex），通用聚合契约 | `payment_ext_*` |
| `paypal` | PayPal 在线收银（国际卡 / 钱包） | OAuth2 client_credentials + Orders v2 + Webhook 官方验签 | `payment_ext_*` |
| `stripe` | Stripe PaymentIntent（国际卡） | Webhook `t=...,v1=...` HMAC-SHA256 | `payment_ext_*` |
| `alipay_ent` | 支付宝企业支付（电脑网站 page.pay / 手机网站 wap.pay） | RSA2 签名 / 验签 | `payment_ext_*` |

**关键约束与决策**：主库 `payment_intents.provider` 带四渠道 CHECK 约束，且本包不得修改 `schema.sql`；SQLite 无法去掉既有 CHECK。因此新增五渠道的意图 / 回调审计 / 退款记录全部落在 `schema.d` 新建的 `payment_ext_*` 独立表，既有四渠道链路与 `payment_intents` 保持原样不动。

**未配置降级（硬验收）**：任一渠道凭证不齐全时，`configured=false`；下单返回 `503 PROVIDER_NOT_CONFIGURED`，回调返回 `503 PAYMENT_NOTIFY_NOT_CONFIGURED`，退款返回 `503 PROVIDER_NOT_CONFIGURED`，**不伪造成功订单或到账结果**。

## 3. 统一适配器契约

`ChannelAdapter`（`src/payments/types.ts`）每个渠道实现同一组能力：

- `configured(env)`：凭证是否齐全；不齐全时下单一律 503。
- `sandbox(env)`：是否运行在沙箱 / 测试环境。
- `createOrder(env, intent, opts)`：下单签名 + 调用上游，返回跳转串 / 二维码 / 客户端密钥。
- `parseNotify(env, headers, rawBody, body)`：异步验签 + 报文归一为 `NotifyPayload { intentId, amountCents, currency?, status, providerTxnId, raw }`；验签失败抛 `FORBIDDEN(403)`，报文缺字段抛 `VALIDATION_FAILED(400)`。
- `buildRefundRequest(env, intent, amountCents, reason)`：纯函数构造签名退款请求（便于单测签名而不打网络）。
- `executeRefund(env, request)`：执行退款调用，返回 `{ ok, providerRefundId?, raw }`。
- `ack`：回调成功应答形态；聚合支付回纯文本 `success`，国际渠道回 JSON。

**路由统一校验顺序**：渠道存在性 → 渠道是否配置（503）→ 适配器验签 → 订单号存在性（404）→ 渠道匹配（409）→ 金额一致（409）→ 币种一致（409）→ 已支付重放直接 ack（不重复履约）→ 非成功状态记录 ignored → 事务内幂等履约。

**幂等保障**：
- 意图已 `paid` 的回调重放直接 ack 并落 `replay` 审计事件，不产生第二笔权益；
- `provider_txn_id` 部分唯一索引兜底同一渠道交易号重复；
- 退款按渠道退款单号唯一；退款接口带幂等键，首次响应被回放。

**履约分支**（与主库 `fulfillIntent` 同口径）：`recharge` 入钱包并记流水；`asset` 发资产并记作者收益；`vip` 续会员时长；`shop_order` 置订单已支付。

## 5. 路由工厂与挂载建议

**导出工厂**：`createPaymentChannelRouter(deps: ApiDeps): Router`，位于 `src/payments/router.ts`。

| 端点 | 鉴权 / 中间件 | 说明 |
| --- | --- | --- |
| `GET /payments/channels` | `requireAuth` | 九渠道矩阵，只回 `id/label/enabled/configured/sandbox/methods/note`，不回密钥 |
| `POST /payments/ext/intents` | `requireAuth` + `idempotency` | 新渠道下单；未配置 503；金额以服务端商品 / 订单价格为准（充值除外，按服务端校验区间） |
| `GET /payments/ext/intents/:id` | `requireAuth`（本人） | 查询本人扩展渠道支付单 |
| `POST /payments/:channel/notify` | **公开端点，不挂 `requireAuth`** | 渠道异步回调：验签 → 订单号 / 金额 / 币种校验 → 幂等履约 |
| `POST /payments/ext/intents/:id/refund` | `requireAuth` + `requirePermission('commerce:write')` + `idempotency` | 运营退款；未配置 503；已退款 409；上游失败 502 且退款记录置 `failed` |

**挂载位置建议**：

1. 与既有 `createPaymentsRouter` 同前缀 `/api/v1`；挂在**全局 `requireAuth` 之前的公开路由段**（`notify` 是第三方公开回调，不能经过全局鉴权）；建议置于既有支付路由之后，避免既有路由先匹配。
2. 工厂内部各端点已自行挂 `requireAuth` / `idempotency` / `requirePermission`，无需在 app 层重复包裹。
3. 挂载前确保 `express.json` 保留 `rawBody`（verify 钩子把原始 buffer 挂到 `req.rawBody`），Stripe / PayPal / 支付宝企业回调验签依赖原始报文；测试 mini app 已示范该装配。
4. 本包未改 `app.ts`，由主控统一挂载；mini 测试已验证独立工厂可单独挂载。
