全栈全平台项目的团队配置

“全栈全平台”通常意味着：Web 端 + iOS + Android + 小程序/H5 + 管理后台 + 服务端 + 数据与运维。理论上需要 8～12 个工种，但实际不必一次性配齐——核心是“先配齐能力，再配齐人头”，一个人可以覆盖多个端。

一、先划范围，再定人数

在招人前，需先明确三个问题，否则人数容易翻倍：
平台是否真的都需要？ 若目标用户在国内且以 C 端为主，「小程序 + H5 + 管理后台」往往能覆盖 80% 需求，原生 App 可延后；若涉及硬件、音视频、重度交互或出海，原生端才是刚需。
后端是自研还是 BaaS？ 使用 Supabase、Firebase、云开发等方案，可省去 1～2 个后端人力。
是否上中台/微服务？ 初期不要做，一旦引入就需要额外的架构师和运维。

二、岗位清单（按优先级分三档）

P0：没有就开不了工
角色 | 主要职责 | 最少人数
---|---|---
产品负责人 / PM | 需求梳理、优先级、验收 | 1
UI/UX 设计师 | 交互稿、视觉规范、切图 | 1（可兼职）
前端（Web/H5/小程序） | 用户端页面、后台前端 | 1～2
移动端（iOS / Android 或 Flutter/RN） | App 开发 | 1～2（跨端框架可只要 1 人）
后端工程师 | API、业务逻辑、数据库 | 1～2
测试 / QA | 用例、回归、多端兼容测试 | 1（小团队可由开发互测+PM 兼）
P1：项目能跑，但缺了会疼
DevOps / 运维：CI/CD、服务器、域名证书、监控告警、App 上架流程。小团队可由后端兼任，但上架和发版流程必须有人专职负责，否则极易卡壳。
技术负责人 / 架构师：选型、代码规范、Review、技术债务控制。通常由资深后端或前端兼任。
数据 / BI：埋点方案、看板、基础分析。前期由后端 + PM 用现成工具（神策、GrowingIO、GA）替代。

P2：规模上来后再补

安全工程师、DBA、算法工程师、技术文档工程师、增长/运营、客户成功、合规（隐私政策、等保、ICP、App 备案）。

提醒：国内上线 App 现在需要做 ICP 备案 + App 备案 + 隐私合规自查，这部分工作没人管会直接导致下架，建议早期就指定一个人负责（通常是 PM 或运维）。

三、按阶段给配置（最实用的部分）

阶段 A：验证期（0→1，3～6 个月）
👉 3～5 人：1 全栈后端 + 1 前端（兼顾小程序/H5/后台）+ 1 移动端（跨端框架）+ 1 产品兼设计（或设计外包）+ 创始人兼 PM。
目标：只上一个主平台 + 一个备用入口，其余全部砍掉。

阶段 B：成型期（1→10，6～18 个月）
👉 8～15 人：PM 1、设计 1、前端 2、移动端 2、后端 3、测试 1～2、运维 0.5～1、数据 0.5。
这是最常见的“标准编制”，前后端比大约 1:1.5。

阶段 C：规模化（多产品线）
👉 20 人以上，按“特性小队”拆分：每个小队 6～8 人（PM+设计+前+移+后+测），共享中台、运维、数据、安全等横向团队。

通用配比经验值：
开发 : 测试 ≈ 4:1 ～ 6:1（ToC 多端项目靠下限，ToB 靠上限）
前端（含移动） : 后端 ≈ 1.5:1 ～ 2:1（全平台项目前端工作量明显更大）
产品+设计 : 开发 ≈ 1:4 ～ 1:6

四、省钱的人力组合（现实里多数团队这么干）
Flutter / React Native / Taro / uni-app：用一套代码吃下 iOS、Android、H5、小程序，移动端从 2 人降到 1 人。代价是遇到原生能力深水区时需要临时补原生开发。
Next.js / Nuxt + 一套组件库：Web、H5、管理后台共用，前端 1 人即可撑住。
设计走组件库 + Design Token（Ant Design、TDesign、Arco），设计师可从全职转为按阶段外包。
测试前期用自动化+E2E（Playwright / Cypress）+ 众测平台，正式招 QA 放在用户量起来之后。
运维直接用云 + Serverless + GitHub Actions，第一年基本不需要专职运维。

五、最容易被漏掉的 6 件事（不是岗位，但必须有人背）
多端一致性：同一套文案、同一套状态码、同一套错误提示，需要一个 Owner（通常是前端负责人）。
版本碎片化：Android 机型、iOS 系统版本、微信客户端版本、小程序基础库——兼容性矩阵要有人维护。
发版节奏对齐：Web 随时发，小程序审核 1～3 天，App Store 审核 1～2 天。发版窗口必须错开并预留回滚方案。
账号与权限体系：一套账号打通所有端，早期不设计好，后期就是灾难级返工。
埋点与数据口径：各端埋点规范不统一，最后数据对不上，分析等于白做。
法务合规：用户协议、隐私政策、权限申请说明、未成年人保护、数据跨境——ToC 项目必备。

六、成本粗估（国内一线/新一线，月薪，含社保公积金约 ×1.3）
初级开发 10～18k｜中级 18～30k｜高级/资深 30～50k｜架构/技术总监 50k+
PM 15～35k｜UI/UX 12～25k｜测试 10～22k｜运维 18～35k

据此估算：5 人 MVP 团队月成本约 10～18 万；12 人标准团队约 30～50 万。外包整包开发一个全平台项目，常见报价区间 30～150 万，但后续迭代和维护成本往往被严重低估——长期项目建议核心后端和 PM 掌握在自己手里。

七、几个踩坑提醒
❌ 一开始就招“全栈工程师”当主力：真正的全栈很少，多数是“后端为主会写点前端”，做出来的前端质量会成为长期债务。
❌ 没有专职的发布/上线负责人：导致 App 卡在审核、证书过期、备案没做。
❌ 测试全靠开发自测：多端项目 bug 数量是单端的 2～3 倍，这是最容易省错钱的地方。
✅ 第一个 hires 决定团队基因：前 3 个人应该是能独立交付的人，而不是只会执行的人。
✅ 用“能力地图”而不是“岗位 JD”招人：先把需要的能力列成表（如 API 设计、跨端、上架经验、性能优化），再看每个人覆盖几格，缺口用外包补。

## assistant

你这三条回答，等于把项目从「5 人 MVP」直接抬到了「中型技术团队」的量级。尤其是第 3 条（上中台），它是成本最高的变量，而且它不是“多招几个人”的问题，而是组织结构问题。下面按你的三条约束重新算一遍。

一、逐条解读：每条约束到底多花了谁

约束1：不出海，但硬件 + 音视频 + 重度交互都要
→ 原生端不仅是刚需，而且不是普通的移动端开发能扛的。
重度交互（动画、手势、复杂渲染）意味着 Flutter/RN 在深水区会卡壳，iOS 和 Android 各需 1 名原生主力，跨端框架只能用来做次级页面。
音视频是独立工种。普通后端或移动端写出来的方案，上线后基本都会在卡顿率、首帧时间、弱网对抗上翻车。至少需要 1 名音视频/流媒体工程师（WebRTC、编解码、RTC 服务、CDN 选型），最好 2 人。
硬件也是独立工种。至少 1～2 名嵌入式工程师（固件、BLE/Wi-Fi 协议、OTA、功耗优化），外加硬件联调要有人长期跑工厂和实验室。

这一条单独就把移动端从「1 人跨端」变成了「4～6 人」。

约束2：后端自研
→ 省不了人，反而因为音视频和硬件，后端比常规项目更重。
业务后端（用户、订单、支付、权限）
音视频信令/房间服务/录制转码（和上面那个音视频工程师配对）
设备接入层（IoT 网关、长连接、消息队列、设备影子）——这是硬件项目特有的，普通后端没做过
数据库与缓存、搜索
所以后端不是 2 人，是 4～7 人，且要有 1 个能扛架构的。

约束3：上中台
→ 这是最关键的一条，我上一条说“初期不要做”，你现在决定要做，那就必须按正确的方式做，否则这是整个项目最大的失败风险点。

中台失败的三种典型死法（国内过去五年已经验证过很多次了）：
空转：只有一条业务线，中台没有“复用”的对象，做出来的东西业务线不用，最后变成需求瓶颈。
错位：中台团队背的是“平台稳定性/复用率”，业务线背的是“上线速度”，两边 KPI 天然冲突，吵架成为日常。
过度抽象：为了通用性把接口设计得极其复杂，业务方接入成本高于自己写，于是绕开中台搞影子系统，中台名存实亡。

正确的做法（强烈建议）：
不要先建中台团队再做业务。 先在业务线里做出 2 个以上真实场景，把重复的部分识别出来，再抽人成立中台。顺序反了必死。
起步用「薄中台」：只做三件事——统一账号权限与身份中心、统一数据模型与主数据、统一网关与开放 API。这三样是所有端复用的硬通货，收益确定、争议小。
中台团队规模 = 业务线数量 × 0.5 左右。只有 1 条业务线时，中台最多 2～3 人，多了就是浪费。
中台负责人必须是公司级授权角色（CTO 或架构总监直管），否则推不动业务线改造。

三、分阶段落地（这才是关键，别一次招满）

Phase 1｜0–6 个月：先把一个端跑通（8～10 人）
CTO、PM、设计 1、前端 2、iOS 1、Android 1、后端 2（兼顾设备接入雏形）、QA 1、音视频 1（兼职顾问也行）。

目标：硬件 + App + 后台闭环跑通，拿到真实用户反馈。

Phase 2｜6–15 个月：补平台和第二条入口（14～18 人）
加小程序/H5、加 Android 第二人、加嵌入式、加 DevOps、QA 到 2 人。
此时抽 2 人成立“平台组”：把 Phase 1 的规范落成账号中心 + 网关 + 组件库。注意：这 2 人是从已有团队转岗，不是新增。

Phase 3｜15 个月+：中台正式化（22 人+）

四、你这个组合特有的 5 个坑（比招人更致命）
音视频合规：国内做音视频/直播类，ICP 备案只是底线。涉及直播可能需要《信息网络传播视听节目许可证》（极难拿，多数公司走合作挂靠），UGC 内容需要内容审核团队或第三方审核服务（数美、网易易盾等）。这块没人管，上线即下架。 建议早期指定 PM 或运营负责人对接法务。
硬件认证周期：SRRC（无线电型号核准）、CCC、入网许可，单是排队就要几个月，且固件每次大改可能要重测。产品排期必须往前倒推，否则硬件好了软件等、软件好了证没下来。
发版节奏错配：固件 OTA 一旦发出去很难回滚（有变砖风险），App Store 审核 1～3 天，小程序 1～3 天，Web 随时发。四套发布管道必须有“兼容性契约”：新固件兼容旧 App、新 App 兼容旧固件，至少维持 2 个版本的向下兼容。 这条做不到，线上事故是必然的。
带宽成本：音视频的 CDN/流量费用是随用户量线性甚至超线性增长的，很多项目死在“用户涨了但毛利是负的”。第一天就要算清单用户单分钟成本，并让后端负责人背这个指标。
中台的 KPI 怎么定：不要定“接入了几个业务方”，要定“为业务方节省了多少人日”和“业务方是否愿意主动接入”。后者只能用满意度衡量，但比前者诚实。

五、成本粗估（一线/新一线，月薪 ×1.3 含社保公积金）
最小可行版 14～18 人：月成本约 40～60 万，年 500～700 万
全配版 22～32 人：月成本约 70～110 万，年 900 万～1400 万
另计：服务器+CDN+音视频 PaaS（声网/即构/ZEGO 这类按分钟计费，量大后自建更划算但要养人）、硬件打样与认证（几十万到上百万）、第三方服务（审核、短信、地图）

省钱杠杆（按性价比排序）：
音视频先用 PaaS 而不是自建（省下 1～2 个人 + 半年时间，量起来再迁自建）
中台只做账号+网关+组件库三件套，其余延后

QA 前期靠自动化（Appium + Playwright）+ 内部众测，第 3 个 QA 最后招

你的三个选择里，“上中台”是唯一一个可以安全延后 6～12 个月而不产生技术债的项；“硬件”和“音视频”是一个都不能延后的硬约束。 所以资源分配应该是：先保硬件 + 音视频 + 一个原生端的质量，中台只出规范不出团队。反过来做的团队，我见过太多死在半路上了。

→ 省不了人，反而因为音视频和硬件，后端比常规项目更重。

业务后端（用户、订单、支付、权限）
音视频信令/房间服务/录制转码（和上面那个音视频工程师配对）
设备接入层（IoT 网关、长连接、消息队列、设备影子）——这是硬件项目特有的，普通后端没做过
数据库与缓存、搜索
所以后端不是 2 人，是 4～7 人，且要有 1 个能扛架构的。

约束3：上中台
→ 这是最关键的一条，我上一条说“初期不要做”，你现在决定要做，那就必须按正确的方式做，否则这是整个项目最大的失败风险点。

中台失败的三种典型死法（国内过去五年已经验证过很多次了）：

空转：只有一条业务线，中台没有“复用”的对象，做出来的东西业务线不用，最后变成需求瓶颈。
错位：中台团队背的是“平台稳定性/复用率”，业务线背的是“上线速度”，两边 KPI 天然冲突，吵架成为日常。
过度抽象：为了通用性把接口设计得极其复杂，业务方接入成本高于自己写，于是绕开中台搞影子系统，中台名存实亡。

正确的做法（强烈建议）：
不要先建中台团队再做业务。 先在业务线里做出 2 个以上真实场景，把重复的部分识别出来，再抽人成立中台。顺序反了必死。
起步用「薄中台」：只做三件事——统一账号权限与身份中心、统一数据模型与主数据、统一网关与开放 API。这三样是所有端复用的硬通货，收益确定、争议小。
中台团队规模 = 业务线数量 × 0.5 左右。只有 1 条业务线时，中台最多 2～3 人，多了就是浪费。
中台负责人必须是公司级授权角色（CTO 或架构总监直管），否则推不动业务线改造。

四、你这个组合特有的 5 个坑（比招人更致命）

音视频合规：国内做音视频/直播类，ICP 备案只是底线。涉及直播可能需要《信息网络传播视听节目许可证》（极难拿，多数公司走合作挂靠），UGC 内容需要内容审核团队或第三方审核服务（数美、网易易盾等）。这块没人管，上线即下架。 建议早期指定 PM 或运营负责人对接法务。
硬件认证周期：SRRC（无线电型号核准）、CCC、入网许可，单是排队就要几个月，且固件每次大改可能要重测。产品排期必须往前倒推，否则硬件好了软件等、软件好了证没下来。
发版节奏错配：固件 OTA 一旦发出去很难回滚（有变砖风险），App Store 审核 1～3 天，小程序 1～3 天，Web 随时发。四套发布管道必须有“兼容性契约”：新固件兼容旧 App、新 App 兼容旧固件，至少维持 2 个版本的向下兼容。 这条做不到，线上事故是必然的。
带宽成本：音视频的 CDN/流量费用是随用户量线性甚至超线性增长的，很多项目死在“用户涨了但毛利是负的”。第一天就要算清单用户单分钟成本，并让后端负责人背这个指标。
中台的 KPI 怎么定：不要定“接入了几个业务方”，要定“为业务方节省了多少人日”和“业务方是否愿意主动接入”。后者只能用满意度衡量，但比前者诚实。

省钱杠杆（按性价比排序）：
音视频先用 PaaS 而不是自建（省下 1～2 个人 + 半年时间，量起来再迁自建）

QA 前期靠自动化（Appium + Playwright）+ 内部众测，第 3 个 QA 最后招

你这个项目的测试复杂度来自“组合爆炸”：5 个端 × 多机型 × 多固件版本 × 网络环境 × 音视频质量。1 个人不可能全靠手工，必须靠风险分级 + 自动化 + 众测。

核心职责
测试策略与用例设计：按风险分级（阻断/严重/一般），核心链路（配对、连接、音视频、支付、OTA）必须有完整用例；维护“多端 × 机型 × 固件版本”测试矩阵。
硬件联调测试：与固件同事配合，覆盖弱网、断网重连、蓝牙干扰、低电量、并发操作、异常断电、OTA 中断与恢复。
音视频质量测试：首帧时间、卡顿率、音画同步、回声与噪声、弱网对抗（丢包/延迟模拟）、多端互拨矩阵、长时间通话稳定性（内存与发热）。
自动化建设（Phase 1 就要开始）：接口自动化（pytest/JUnit + 断言 + 数据驱动）、UI 自动化冒烟（Playwright 后台、Appium/Maestro 移动端）、CI 集成与失败告警。
缺陷管理与复盘：缺陷分级与流转、阻塞问题跟踪、版本回归、线上缺陷根因分析（漏测原因归类并反哺用例）。
专项测试：性能（启动、内存、CPU、耗电）、兼容性（机型与系统版本）、安全基础（越权、敏感信息泄露）、安装升级与数据迁移。
发版验证：灰度验证清单、线上冒烟、回滚验证。

硬性要求
3 年以上，有移动端 + 接口自动化实际落地经验
会至少一门编程语言（Python/Java/JS），能自己写脚本与工具
有硬件/IoT 或音视频项目测试经验（强加分）
熟悉抓包（Charles/Fiddler）、日志分析、adb/idevicesyslog

面试考察点
给“设备 OTA 升级”功能，让其现场列测试用例（期待：正常/中断/断电/低电量/弱网/重复升级/版本回退/并发/多设备）
问：如何量化“音视频质量”？（期待：客观指标 + 主观 MOS + 自动化采集）
问：只有 1 个人怎么覆盖 5 个端？（期待：风险分级 + 自动化 + 众测 + 探索性测试）

避坑问题
“你写的自动化用例有多少真正跑在 CI 上？通过率多少？”
“你漏测过线上事故吗？根因是什么？改了什么流程？”

Phase 1 交付物

音视频工程师（兼职顾问，0.5 人力）

定位
Phase 1 不追求自建，而是用 PaaS 把质量与成本守住，同时为 Phase 2 可能的自建做技术储备。兼职形式可以是顾问、外包专家或兼职工程师。

核心职责
选型与方案评审：RTC/流媒体 PaaS 选型（声网、即构、ZEGO、腾讯云、阿里云等），对比延迟、并发、录制、转码、计费模型；输出选型报告与成本测算（单用户单分钟成本模型）。
接入方案与代码评审：Token 鉴权方案、频道与用户管理、推拉流参数（分辨率/码率/帧率/关键帧间隔）、录制与转码配置、CDN 与播放地址签名；评审移动端与后端的接入代码。
质量指标体系定义：首帧时间、卡顿率、端到端延迟、丢包率、音画同步、MOS；定义采集方式与告警阈值，与 QA 的测试基线对齐。
弱网与性能优化指导：拥塞控制、码率自适应、丢包重传、音频 3A（AEC/ANS/AGC）参数、低端机降级策略。
成本治理：识别计费大头（录制、转码、CDN、并发），给出降本措施（按需录制、分辨率分档、转码模板精简、缓存与边缘策略）。
合规与内容安全咨询：直播/UGC 场景的内容审核接入建议、录制文件存储与留存合规。
知识转移：给移动端与后端做 2–3 次内部培训，避免形成“只有顾问懂”的黑盒。

硬性要求
5 年以上音视频经验，精通 WebRTC 或主流 RTC SDK 原理
有编解码（H.264/H.265/AV1、AAC/Opus）、流媒体协议（RTMP/HLS/FLV/SRT）实战
有大规模并发或成本优化案例
能远程协作、能写文档、能评审代码（不接受只出主意不落文档）

面试/筛选考察点
问：端到端延迟由哪些环节构成？分别怎么测量与压缩？
问：如何设计一套“单用户单分钟成本”模型并给出降本 30% 的方案？
问：录制文件成本过高，有哪些可落地的削减手段？

避坑问题

“你服务过的最大并发是多少？当时集群规模与成本是多少？”

## user

我要不是招募人员而是项目实际负责人人员

## assistant

理解了——你不是在写 JD、不是在招人，而是你自己就是这个项目的实际负责人（技术侧或全责侧）。那前面那些"招几个人、面试问什么"就都是别人的事了，你真正要管的是决策、节奏、风险、资产这四样。下面换成"负责人操作手册"来讲。

一、先切换评价标准：你被考核的不再是产出，而是这四件事
维度 | 工程师视角 | 你（负责人）视角
---|---|---
产出物 | 代码、页面、用例 | 决策记录、节奏、风险预案、可复用资产
成功标准 | 功能做完 | 按时上线 + 不出大事 + 成本可控 + 下次更快
时间分配 | 80% 做 | 60% 沟通/评审/拍板，30% 补位写关键代码，10% 想未来
最大风险 | 技术难点 | 关键路径误判、责任真空、不可逆决策
一句话：你的核心价值是"减少团队的不确定性"，而不是"自己多干活"。 凡是让团队猜的事（协议怎么定、字段叫什么、什么时候发版、这个 bug 算不算阻断），都是你的失职。

二、你个人必须背的 5 个数字

没有数字，你就只是在开会。建议 Phase 1 就固定这五个，每周更新，写进周报第一行：
关键路径剩余天数：硬件认证 / 音视频接入 / 协议冻结，三者中最紧的那条，还剩几天到不可逆节点。
核心链路成功率：设备配对成功率、连接成功率、音视频接通率、首帧时间 P90。这是硬件+音视频项目的"体温计"。
阻断缺陷数 + 平均关闭时长：不是总 bug 数（总数没意义），是阻断级。
单用户单分钟成本（音视频）+ 月度云成本 / 活跃用户。毛利杀手，必须你盯。
发版准时率：承诺的日期做到没有。连续两次不准，说明你的排期机制坏了，不是团队不努力。

三、你上任后 90 天的个人交付清单

第 0–2 周：把"不确定性"变成"清单"
画一张系统边界图（不用漂亮，能讲清就行）：终端 / 接入 / 业务服务 / 设备接入 / 音视频链路 / 数据 / 第三方。标出每一块的负责人和当前状态（未开始/进行中/卡住）。
列关键路径与不可逆节点：硬件打样、SRRC/CCC/入网送检、App 备案、音视频 PaaS 合同、协议冻结日。这些是"过期就赔钱"的事，必须排在最前面。
建风险登记册（见第六节），先写 10 条，每条写"触发信号"。
确定四份规范的负责人和冻结日期：API 规范、错误码、账号与权限模型、埋点口径。这四份是后面所有端的公共地基，没冻结之前不允许大规模开发业务页面。

第 3–6 周：把"节奏"建起来
协议冻结：App ↔ 服务端 ↔ 固件 三方协议 v1 定稿，含版本号字段与能力协商机制。这是硬件项目最容易翻车的地方，必须由你主持、三方签字确认。
发版火车：固定节奏（比如双周），四套管道（Web/小程序/App/固件）的窗口与依赖顺序写成一页纸。
质量门禁：什么算"可以发"——崩溃率、核心链路用例通过、性能基线不劣化、合规项过。写成 checklist，发布由你或你授权的人签字。
开始收数据：埋点从第一个可用版本就有，别等上线后补。

第 7–13 周：把"资产"沉下来
中台三件套的 Phase 1 版本：账号中心（统一登录+RBAC+设备绑定）、网关（统一入口+鉴权+限流+错误码）、组件库（Design Token 消费 + 基础组件）。注意：这是你亲自定义边界的活，交给谁做都行，但"做到什么程度算够"必须你拍板。
可观测性：日志、指标、告警、成本面板。没有这个，你后面所有判断都靠感觉。
复盘机制：每个版本一次小复盘（30 分钟，只问三件事：哪里慢了、哪里返工了、下版本改什么）。

四、哪些决策绝对不能下放（你的"不可委托清单"）

这些一旦让别人定，后面返工成本是十倍：
协议与版本兼容策略：字段命名可以下放，"如何向下兼容 2 个版本、OTA 如何回滚"不行。
账号与权限模型：一套账号打通五端 + 设备绑定关系，模型错了后期是灾难级迁移。
中台边界：哪些能力进中台、哪些留在业务线；Phase 1 只做三件事，超出的需求你来挡。
音视频走 PaaS 还是自建：以及成本上限是多少、超过怎么办。
发版与回滚授权：谁有权发固件、什么条件下熔断。
合规红线：哪些资质必须有、UGC 审核方案、隐私政策与权限话术。
砍需求：Phase 1 的"不做清单"由你宣布并对外解释，别让团队自己去挡业务方。

可以放下的：具体技术实现、组件拆分、测试用例细节、UI 走查、日常排期。

五、五个硬约束，作为负责人你要做的具体动作
硬件（最容易拖死项目的部分）
倒排排期：从"期望上市日"往前推，认证送检、打样、量产各留缓冲。SRRC/CCC/入网排队以月计，固件大改可能重测。
指定唯一的硬件联调负责人（团队里某个人兼，写进他的目标），否则 App 组和固件组会互相等。
协议变更走评审：任何固件侧协议改动，必须评估旧 App 兼容性，你签字才生效。
OTA 是高危操作：分批灰度、电量/网络前置校验、失败率熔断、双分区回滚方案。变砖是不可逆损失，这条你亲自过。
音视频
先定指标再写代码：首帧时间 P90、卡顿率、端到端延迟、接通率。指标没定就开发，等于没有验收标准。
成本模型先算：单用户单分钟成本 × 预估时长 = 月度支出。用 PaaS 时按分钟/录制/转码/CDN 分项算，别只看单价。
不要过早自建：Phase 1 用 PaaS，把精力留给业务与硬件；量起来再评估迁移，迁移成本提前评估一次。
合规前置：是否涉及直播/UGC、是否需要内容审核服务、录制文件留存策略。这块没人管就是下架风险。
中台（你之前明确要做的）
作为负责人，你对中台只提三个问题：
现在有几个真实复用场景？ 少于 2 个，就只做规范不建团队。
业务方接入成本比自己写高还是低？ 高了说明抽象过度，立刻简化。
谁为"业务线不用中台"负责？ 如果答案是"没人"，中台会名存实亡。

Phase 1 的克制做法：账号中心 + 网关 + 组件库三件套，其余全部延后。中台的需求由你统一收口，防止业务方把中台当"免费外包"。
多端一致性
一份"多端差异矩阵"：同一功能在 iOS/Android/小程序/H5/后台的差异、文案、错误提示、权限话术。谁维护？指定一个人，你每周抽查。
错误码统一：五端共用一张表，前端不允许自己造文案映射逻辑。
发版顺序：后端先兼容 → 固件/App 后上 → 小程序/H5 最后。回滚顺序相反。
合规与外部依赖
把"外部方"当成项目干系人管理，而不是等他们回复：
硬件方案商/工厂：明确接口人、周例会、交付物清单、验收标准。
云厂商/RTC 供应商：合同里的 SLA、计费口径、压测支持、技术支持响应时效。
法务/备案：ICP、App 备案、隐私政策、权限说明；有直播/UGC 再评估资质与审核方案。
应用商店/小程序审核：被拒是常态，准备一套"审核话术与整改预案"。

八、如果你现在几乎是"一个人扛"（团队还没成型）

这是很多负责人的真实处境，取舍原则：
先做"能验证商业假设"的最小闭环：一个硬件场景 + 一个端（优先 iOS 或 Android 之一）+ 最简后台。另一端、小程序、H5 全部延后。
中台只写文档不写系统：四份规范 + 账号模型设计，成本极低，是后面所有扩张的地基。
外部能力全部买：RTC 用 PaaS、推送用厂商服务、审核用第三方、后台用现成模板、认证找代理。你只保留"差异化能力"自研。
你自己写哪部分代码：只写协议层、账号模型、核心状态机这三块——因为它们最难返工，且写它们等于在定义架构。UI 和 CRUD 一律不要自己写。
明确告诉所有人"现在处于验证期"：降低对代码优雅度的期待，但不降低对协议和数据模型的严谨度。

九、负责人最容易犯的六个错（对照自查）
把"招人计划"当成"项目计划"：人还没到，先花三个月做架构 PPT。硬件项目的关键路径往往不在软件。
协议不冻结就并行开发：五端各自猜字段，联调时集体返工。
中台先建团队后找场景：没有复用对象的中台一定会空转。
只盯进度不盯成本：音视频项目死于毛利，不是死于功能。
责任真空：硬件联调、合规、发版、OTA 这四件事，"大家都在管"等于没人管。
自己成为瓶颈：所有决策都等你，你休假项目就停。解法是把"可下放清单"公开，并培养一个能替你签字的人。

一、CTO / 技术负责人（1 人）

定位：技术侧最终决策者与项目技术风险的第一责任人，负责"定边界、定规范、定节奏、定质量底线"。
架构与选型
定义系统分层与边界：终端层、接入层（网关）、业务服务层、设备接入层、音视频链路、数据层、基础设施层，明确每层职责与故障域。
主导技术选型并出具决策记录（ADR）：跨端策略（原生为主、哪些页面走 H5/跨端）、后端语言与框架、数据库与缓存、消息队列、时序数据存储、部署形态、音视频 PaaS 与自建的取舍。
定义各端与后端的通信契约：协议风格、版本策略、能力协商机制、向下兼容规则（至少兼容 2 个历史版本）。
主持不可逆变更的技术评审：数据模型变更、协议变更、中台接口变更、OTA 方案、存储与成本结构变更。
规范与标准（Phase 1 的核心产出）
主导并冻结四份基础规范：API 规范（RESTful 约定、版本、分页/排序/过滤、幂等、统一响应结构）、统一错误码规范（全端共用一张表）、账号与权限模型、埋点与数据口径规范。
制定代码与工程标准：分支策略、提交规范、代码评审规则、CI 门禁（lint + 单测 + 构建 + 冒烟）、文档要求。
制定日志、监控、告警与链路追踪标准，保证线上问题可定位、可复盘。
中台推进
定义中台边界与 Phase 1 范围：只做账号中心、网关、多端组件库三件套，其余需求统一收口并延后。
判定"何时从规范转为团队"：出现 ≥2 个真实复用场景后才抽人成立平台组，并决定抽谁、抽几人。
仲裁中台与业务线的冲突：接入成本、需求优先级、是否允许业务线自建，避免影子系统。
为中台设定考核口径：以"为业务方节省的人日"和"业务方是否愿意主动接入"为准，而非接入数量。
发版与稳定性
制定发版契约：Web、小程序、App、固件四套管道的发布顺序、窗口、依赖关系与回滚预案。
定义发布质量门禁与放行授权：崩溃率、核心链路用例通过、性能基线不劣化、合规项通过；明确谁有权发固件。
主导重大故障与线上事故的指挥、复盘与改进项跟踪。
主导 OTA 升级策略评审：分批灰度、电量/网络前置校验、失败率熔断、回滚与防变砖方案。
成本与容量
对云成本、音视频带宽与录制转码成本负责，设定单用户单分钟成本上限并要求做成可观测面板。
主导容量评估与压测要求：设备长连接承载、音视频并发、数据库与缓存容量水位。
团队与协作
负责技术岗面试终面与技术梯队建设，识别"能独立交付"与"只会执行"。
指定并考核跨领域兼任责任人（如硬件联调负责人、发版负责人、合规对接人），消除责任真空。
向业务/管理层做技术风险与排期的对外解释，承担砍需求的技术论证。
风险前置
维护技术风险登记册，为每条风险设定触发信号与预案：认证周期、协议兼容、成本失控、中台被绕开、关键人单点。
与 PM 共同把硬件认证、备案、合规节点倒排进技术排期。

二、产品负责人 / PM（1 人）

定位：需求收敛者、跨端一致性 owner、合规与发版窗口的实际推动者。
需求管理与范围控制

合规与外部事务

若涉及直播类业务，评估资质路径与替代方案，并向管理层提示风险。
对接法务、应用商店与小程序审核，准备审核被拒的整改预案与话术。
发版与上线
制定发版日历：四套管道的发布时间、审核缓冲、灰度比例与观察期。
定义灰度与回滚触发条件：观察哪些指标、超阈值如何处理、由谁决策回滚。
组织版本验收与上线后冒烟，收集首批用户反馈并分级（阻断/严重/一般）。

用户与运营接口

与客服/运营对接问题分级与响应机制，推动高频问题进产品迭代。

RACI 使用规则（很重要，否则矩阵会失效）
每行有且只有一个 A；出现两个 A 说明责任没分清，出现零个 A 说明这是"责任真空"（硬件联调、OTA、合规、发版最容易真空）。
A 可以不做（不写 R），但必须签字；R 可以多人，但要指定"主 R"。
标 C 的角色必须在事前被征求意见，事后补通知不算；标 I 的只需事后同步。
矩阵每季度或每个大版本复审一次，人员变动时同步更新，否则很快变成废纸。

附：三张表怎么配合使用
职责说明书（上一轮）回答"这个岗位该干什么"；RACI 回答"这件事谁拍板、谁执行、谁必须被问"；交付物清单回答"做到什么程度算完成"。三者缺一，就会出现"活有人干、事没人负责、验收靠感觉"。
落地顺序建议：先用 RACI 找出没有 A 的行（责任真空），补齐责任人 → 再按交付物清单排 Phase 1 里程碑 → 最后把验收标准写进每个人的试用期/版本目标。
最容易真空的四件事，建议今天就指定 A：硬件联调、OTA 与回滚、合规清单、发版放行。
